# Embedded Relational Persistence (sqlite3)

Files are fine for a settings file. But what if you have 50,000 customers and must find "everyone in Paris who ordered more than twice, newest first"? Reading and filtering a giant JSON file every time does not scale, and updating one record safely is hard. A **relational database** is built for exactly this: structured tables, fast lookups, and **transactions** that keep data consistent when things go wrong. Python ships with one in the standard library: **SQLite**, a full SQL database that lives in a single file (or in memory) and needs no server. This lesson teaches the SQL you need and the `sqlite3` module that runs it.

> **Tip:** The editor runs SQLite for real. We use an **in-memory** database (`":memory:"`) in the examples so nothing needs cleaning up. For a database that survives restarts, pass a file name instead, such as `sqlite3.connect("app.db")`.

## The model: tables, rows and columns

A **table** is like a spreadsheet with fixed, typed columns. Each **row** is one record. A **primary key** uniquely identifies each row.

| id | name | city | age |
|---|---|---|---|
| 1 | Ada | London | 36 |
| 2 | Linus | Helsinki | 28 |

## Connecting and creating a table

```python
import sqlite3

conn = sqlite3.connect(":memory:")       # a database that lives in memory
cur = conn.cursor()

cur.execute("""
    CREATE TABLE users (
        id INTEGER PRIMARY KEY,
        name TEXT NOT NULL,
        city TEXT,
        age INTEGER CHECK (age >= 0)
    )
""")

cur.execute("INSERT INTO users (name, city, age) VALUES ('Ada', 'London', 36)")
cur.execute("INSERT INTO users (name, city, age) VALUES ('Linus', 'Helsinki', 28)")
conn.commit()

for row in cur.execute("SELECT id, name, city, age FROM users ORDER BY id"):
    print(row)
conn.close()
```

```text
(1, 'Ada', 'London', 36)
(2, 'Linus', 'Helsinki', 28)
```

The pieces:

- `connect` opens (or creates) the database. A **cursor** runs statements.
- `execute` runs one SQL statement. `SELECT` returns rows as tuples you can loop over.
- `commit()` makes your changes permanent (more on transactions shortly).
- The column rules (`NOT NULL`, `CHECK`, `PRIMARY KEY`) are enforced **by the database itself**, so bad data cannot get in no matter which program writes it.

## Never build SQL with string formatting

This is the most important security rule in the lesson. If you paste user text into a query, an attacker can rewrite your query. This is **SQL injection**:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE users (name TEXT, secret TEXT)")
conn.executemany("INSERT INTO users VALUES (?, ?)", [("ada", "pw1"), ("linus", "pw2")])

def login_unsafe(name):
    query = f"SELECT name FROM users WHERE name = '{name}'"      # DANGEROUS
    return conn.execute(query).fetchall()

def login_safe(name):
    return conn.execute("SELECT name FROM users WHERE name = ?", (name,)).fetchall()

attack = "x' OR '1'='1"
print(login_unsafe(attack))        # returns EVERY user
print(login_safe(attack))          # returns nothing: the text is just text
```

```text
[('ada',), ('linus',)]
[]
```

The attacker's text `x' OR '1'='1` changed the logic of the unsafe query so that it matched every row. With **placeholders** (`?`) the database treats the value purely as **data**, never as SQL. The rule has no exceptions: **always pass values as parameters**, as a tuple, never with f-strings or `+`.

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE notes (id INTEGER PRIMARY KEY, text TEXT)")

evil = "'); DROP TABLE notes; --"
conn.execute("INSERT INTO notes (text) VALUES (?)", (evil,))
print(conn.execute("SELECT text FROM notes").fetchall())
print(conn.execute("SELECT count(*) FROM notes").fetchone())

conn.executemany("INSERT INTO notes (text) VALUES (?)", [("one",), ("two",), ("three",)])
print(conn.execute("SELECT count(*) FROM notes").fetchone()[0])
```

```text
[("'); DROP TABLE notes; --",)]
(1,)
4
```

The "attack" was stored as harmless text. `executemany` runs one statement for many rows efficiently.

## Reading data: SELECT

`SELECT` is the heart of SQL. Add `WHERE` to filter, `ORDER BY` to sort and `LIMIT` to cap the results:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT, category TEXT, price REAL)")
conn.executemany("INSERT INTO products (name, category, price) VALUES (?, ?, ?)", [
    ("pen", "office", 1.5), ("desk", "furniture", 120.0), ("ink", "office", 8.0),
    ("chair", "furniture", 85.0), ("clip", "office", 0.1),
])

print(conn.execute("SELECT name, price FROM products WHERE category = ? ORDER BY price DESC", ("office",)).fetchall())
print(conn.execute("SELECT name FROM products WHERE price BETWEEN 1 AND 100 ORDER BY name").fetchall())
print(conn.execute("SELECT name FROM products ORDER BY price DESC LIMIT 2").fetchall())
print(conn.execute("SELECT name FROM products WHERE name LIKE '%i%' ORDER BY name").fetchall())
print(conn.execute("SELECT DISTINCT category FROM products ORDER BY category").fetchall())
```

```text
[('ink', 8.0), ('pen', 1.5), ('clip', 0.1)]
[('chair',), ('ink',), ('pen',)]
[('desk',), ('chair',)]
[('chair',), ('clip',), ('ink',)]
[('furniture',), ('office',)]
```

Fetching results: `fetchall()` gives a list of all rows, `fetchone()` the next row (or `None`), `fetchmany(n)` a batch. Iterating the cursor streams rows one at a time.

## Rows that behave like dictionaries

Tuples force you to remember column positions. Set a **row factory** to get rows you can index by column name:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.row_factory = sqlite3.Row
conn.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER)")
conn.execute("INSERT INTO users (name, age) VALUES (?, ?)", ("Ada", 36))

row = conn.execute("SELECT * FROM users").fetchone()
print(row["name"], row["age"], row[0])
print(row.keys())
print(dict(row))
```

```text
Ada 36 1
['id', 'name', 'age']
{'id': 1, 'name': 'Ada', 'age': 36}
```

## Updating and deleting

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE stock (item TEXT PRIMARY KEY, qty INTEGER)")
conn.executemany("INSERT INTO stock VALUES (?, ?)", [("pen", 10), ("ink", 3), ("clip", 0)])

cur = conn.execute("UPDATE stock SET qty = qty + 5 WHERE item = ?", ("ink",))
print("updated rows:", cur.rowcount)
cur = conn.execute("DELETE FROM stock WHERE qty = 0")
print("deleted rows:", cur.rowcount)
cur = conn.execute("UPDATE stock SET qty = 99 WHERE item = ?", ("nothing",))
print("no match:", cur.rowcount)
print(conn.execute("SELECT * FROM stock ORDER BY item").fetchall())
```

```text
updated rows: 1
deleted rows: 1
no match: 0
[('ink', 8), ('pen', 10)]
```

`rowcount` tells you how many rows were affected. A `WHERE` clause is vital: `UPDATE stock SET qty = 0` with **no** `WHERE` would change every row.

## Aggregation: GROUP BY

SQL can compute summaries itself, which is far faster than loading rows into Python:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE orders (id INTEGER PRIMARY KEY, customer TEXT, amount REAL)")
conn.executemany("INSERT INTO orders (customer, amount) VALUES (?, ?)", [
    ("ada", 50), ("linus", 20), ("ada", 70), ("grace", 100), ("linus", 15), ("ada", 30),
])

print(conn.execute("SELECT count(*), sum(amount), avg(amount), max(amount) FROM orders").fetchone())
print(conn.execute("""
    SELECT customer, count(*) AS orders, sum(amount) AS total
    FROM orders
    GROUP BY customer
    ORDER BY total DESC
""").fetchall())
print(conn.execute("""
    SELECT customer FROM orders GROUP BY customer HAVING count(*) >= 2 ORDER BY customer
""").fetchall())
```

```text
(6, 285.0, 47.5, 100.0)
[('ada', 3, 150.0), ('grace', 1, 100.0), ('linus', 2, 35.0)]
[('ada',), ('linus',)]
```

`GROUP BY` makes one output row per group. `WHERE` filters rows **before** grouping, and `HAVING` filters **groups** after.

## Relationships and JOIN

Real data is split across tables so nothing is stored twice. A **foreign key** links a row to a row in another table, and a **JOIN** puts them back together:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("PRAGMA foreign_keys = ON")             # SQLite needs this switched on
conn.execute("CREATE TABLE authors (id INTEGER PRIMARY KEY, name TEXT NOT NULL)")
conn.execute("""
    CREATE TABLE books (
        id INTEGER PRIMARY KEY,
        title TEXT NOT NULL,
        author_id INTEGER NOT NULL REFERENCES authors(id)
    )
""")
conn.executemany("INSERT INTO authors (id, name) VALUES (?, ?)", [(1, "Le Guin"), (2, "Borges"), (3, "Unpublished")])
conn.executemany("INSERT INTO books (title, author_id) VALUES (?, ?)", [
    ("The Dispossessed", 1), ("Earthsea", 1), ("Ficciones", 2),
])

print(conn.execute("""
    SELECT b.title, a.name FROM books b JOIN authors a ON a.id = b.author_id ORDER BY b.title
""").fetchall())

print(conn.execute("""
    SELECT a.name, count(b.id) FROM authors a LEFT JOIN books b ON b.author_id = a.id
    GROUP BY a.id ORDER BY a.name
""").fetchall())

try:
    conn.execute("INSERT INTO books (title, author_id) VALUES ('Ghost', 99)")
except sqlite3.IntegrityError:
    print("foreign key violation: author 99 does not exist")
```

```text
[('Earthsea', 'Le Guin'), ('Ficciones', 'Borges'), ('The Dispossessed', 'Le Guin')]
[('Borges', 1), ('Le Guin', 2), ('Unpublished', 0)]
foreign key violation: author 99 does not exist
```

An `INNER JOIN` (plain `JOIN`) keeps only matches. A `LEFT JOIN` keeps **every** row from the left table (the author with no books still appears, with a count of 0). The database refused to store a book for a non-existent author, so the data cannot drift out of sync.

## Transactions: all or nothing

A **transaction** groups statements so they either **all** happen or **none** do. Transferring money is the classic case: subtract from one account and add to another. If the program dies in between, the money must not vanish.

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER CHECK (balance >= 0))")
conn.executemany("INSERT INTO accounts VALUES (?, ?)", [("alice", 100), ("bob", 50)])
conn.commit()

def transfer(conn, source, target, amount):
    with conn:                                        # commit on success, roll back on any error
        conn.execute("UPDATE accounts SET balance = balance - ? WHERE name = ?", (amount, source))
        conn.execute("UPDATE accounts SET balance = balance + ? WHERE name = ?", (amount, target))

def balances():
    return dict(conn.execute("SELECT name, balance FROM accounts").fetchall())

transfer(conn, "alice", "bob", 30)
print(balances())

try:
    transfer(conn, "alice", "bob", 500)               # would overdraw alice: the CHECK fails
except sqlite3.IntegrityError:
    print("transfer rejected")
print(balances())
```

```text
{'alice': 70, 'bob': 80}
transfer rejected
{'alice': 70, 'bob': 80}
```

Using the **connection as a context manager** (`with conn:`) is the idiomatic way: it commits if the block finishes, and **rolls back** if an exception escapes. The failed transfer left both balances untouched, because the first `UPDATE` was undone when the second one failed. (This is the context-manager "transaction" idea from lesson 3.3.2, built into the database.)

You can also manage it by hand:

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE t (x INTEGER)")
conn.execute("INSERT INTO t VALUES (1)")
conn.commit()

conn.execute("INSERT INTO t VALUES (2)")
conn.rollback()                                       # undo everything since the last commit
print(conn.execute("SELECT x FROM t").fetchall())
```

```text
[(1,)]
```

## Indexes: making lookups fast

Without help, finding a row by an unindexed column scans **every** row. An **index** is a sorted lookup structure (a B-tree, a close cousin of the trees in lesson 2.4) that makes searches fast:

```python
import sqlite3
import time

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE people (id INTEGER PRIMARY KEY, email TEXT, city TEXT)")
conn.executemany("INSERT INTO people (email, city) VALUES (?, ?)", [(f"user{i}@example.com", "c" + str(i % 50)) for i in range(60000)])

plan = lambda: conn.execute("EXPLAIN QUERY PLAN SELECT * FROM people WHERE email = ?", ("user59999@example.com",)).fetchall()[0][-1]
print(plan())

conn.execute("CREATE INDEX idx_people_email ON people (email)")
print(plan())
print(conn.execute("SELECT id FROM people WHERE email = ?", ("user59999@example.com",)).fetchone())
```

```text
SCAN people
SEARCH people USING INDEX idx_people_email (email=?)
(60000,)
```

`EXPLAIN QUERY PLAN` shows what the database will do. Before the index it must `SCAN` the whole table. After it, it `SEARCH`es using the index. Indexes speed up reads but slow down writes slightly and use space, so index the columns you filter or join on often, not everything. A `PRIMARY KEY` and a `UNIQUE` column get an index automatically.

## A small data-access class

Hiding the SQL behind a class keeps the rest of your program clean, and it is where all the lessons of this module meet: custom errors, a context manager, parameterised queries and transactions.

```python
import sqlite3

class NotFound(Exception):
    pass

class TodoStore:
    def __init__(self, path=":memory:"):
        self.conn = sqlite3.connect(path)
        self.conn.row_factory = sqlite3.Row
        with self.conn:
            self.conn.execute("""
                CREATE TABLE IF NOT EXISTS todos (
                    id INTEGER PRIMARY KEY,
                    title TEXT NOT NULL,
                    done INTEGER NOT NULL DEFAULT 0
                )
            """)

    def add(self, title):
        with self.conn:
            cur = self.conn.execute("INSERT INTO todos (title) VALUES (?)", (title,))
        return cur.lastrowid

    def complete(self, todo_id):
        with self.conn:
            cur = self.conn.execute("UPDATE todos SET done = 1 WHERE id = ?", (todo_id,))
        if cur.rowcount == 0:
            raise NotFound(todo_id)

    def pending(self):
        return [r["title"] for r in self.conn.execute("SELECT title FROM todos WHERE done = 0 ORDER BY id")]

    def close(self):
        self.conn.close()

    def __enter__(self):
        return self

    def __exit__(self, *exc):
        self.close()
        return False

with TodoStore() as store:
    a = store.add("write lesson")
    b = store.add("test lesson")
    store.complete(a)
    print(store.pending())
    try:
        store.complete(999)
    except NotFound as err:
        print("no such todo:", err)
```

```text
['test lesson']
no such todo: 999
```

Notice every query is parameterised, every write is inside `with self.conn:`, and a missing row becomes a clear `NotFound` error instead of a silent `0 rows updated`.

## SQLite types and limits

SQLite stores `INTEGER`, `REAL`, `TEXT`, `BLOB` (bytes) and `NULL`. Dates are best stored as text in ISO format (`"2030-01-15"`) or as integer timestamps. SQLite is superb for local apps, tools, caches, tests and small sites. For many simultaneous writers across a network, bigger servers (PostgreSQL, MySQL) are the usual choice, and the SQL you learned here carries over almost unchanged.

## Common mistakes

- **Building SQL with f-strings or `+`,** which allows injection. Always use `?` placeholders.
- **Forgetting `commit()`,** so changes vanish when the connection closes. Use `with conn:`.
- **An `UPDATE` or `DELETE` without `WHERE`,** changing every row.
- **Forgetting `PRAGMA foreign_keys = ON`,** so foreign keys are not enforced in SQLite.
- **Loading a whole table into Python to filter or sum it.** Let SQL do it.
- **Not closing connections,** or sharing one connection across threads without care.
- **Indexing everything,** or nothing. Index the columns you filter and join on.

## Recap

- **SQLite** is a full SQL database in the standard library: `sqlite3.connect(":memory:")` or a file name. Tables hold typed columns, and constraints (`PRIMARY KEY`, `NOT NULL`, `CHECK`, `FOREIGN KEY`) are enforced by the database itself.
- **Always pass values with `?` placeholders**, never string formatting, to prevent SQL injection.
- `SELECT` with `WHERE`, `ORDER BY`, `LIMIT`; `INSERT`, `UPDATE`, `DELETE` (always with a `WHERE`). `GROUP BY` with aggregates and `HAVING` summarise in the database, and `JOIN` (and `LEFT JOIN`) combine related tables via foreign keys (switch them on with `PRAGMA foreign_keys = ON`).
- A **transaction** is all-or-nothing. Use `with conn:` to commit on success and **roll back** on error.
- An **index** turns a table scan into a fast search. Check with `EXPLAIN QUERY PLAN`, and index the columns you filter or join on.
- Hide the SQL behind a small class that raises your own errors, so the rest of the program never deals with raw SQL.
