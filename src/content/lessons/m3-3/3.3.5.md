# Structured Logging & CLI Tools

A program that runs on your laptop can `print` its progress. A program running on a server at 3 a.m., or inside a tool used by hundreds of people, needs two other skills. First, it must **report what it is doing in a way that can be filtered, searched and kept**: that is **logging**. Second, it must be **usable from a terminal** with arguments, options and sensible exit codes: that is a **command-line interface (CLI)**. This lesson covers both, using only the standard library, and ties together everything in this module.

## Why not just print?

```python
import logging
import sys

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s", stream=sys.stdout, force=True)
logging.info("server started")
logging.warning("disk almost full")
logging.error("could not save")
logging.debug("this is hidden at INFO level")
```

```text
INFO server started
WARNING disk almost full
ERROR could not save
```

`print` has no levels, no timestamps, no way to silence the chatter or send errors elsewhere. Logging gives each message a **severity** and lets you decide, in one place, what to show and where to send it.

## Levels

| Level | Number | Use it for |
|---|---|---|
| `DEBUG` | 10 | detailed internals, for developers while diagnosing |
| `INFO` | 20 | normal milestones: "started", "processed 500 rows" |
| `WARNING` | 30 | something unexpected, but the program carries on |
| `ERROR` | 40 | an operation failed |
| `CRITICAL` | 50 | the program may not be able to continue |

A logger shows messages **at or above** its configured level. In production you might run at `INFO`, and switch to `DEBUG` only when investigating a problem, without changing any code.

## Loggers, handlers and formatters

Logging has three cooperating parts:

- A **logger** is what your code calls (`logger.info(...)`). Loggers have names and form a tree (`app`, `app.db`, `app.web`).
- A **handler** decides **where** a record goes: the console, a file, a network service.
- A **formatter** decides **how** the line looks.

```python
import io
import logging

stream = io.StringIO()
handler = logging.StreamHandler(stream)
handler.setFormatter(logging.Formatter("%(levelname)-7s %(name)s: %(message)s"))

logger = logging.getLogger("shop.checkout")
logger.setLevel(logging.INFO)
logger.addHandler(handler)
logger.propagate = False                       # keep this demo's output to ourselves

logger.info("order %s placed by %s", 1001, "ada")
logger.warning("stock low for %s", "pen")
logger.debug("not shown")
print(stream.getvalue(), end="")
```

```text
INFO    shop.checkout: order 1001 placed by ada
WARNING shop.checkout: stock low for pen
```

Two habits to learn now:

- **Pass values as arguments** (`logger.info("order %s placed", order_id)`), not with an f-string. The text is only built if the message is actually going to be shown, which makes disabled debug logging nearly free.
- **Name loggers after the module** with `logging.getLogger(__name__)`. That builds the tree automatically.

## The logger tree: configure once at the top

A message from `app.db` flows **up** to the handlers of `app` and the root logger. So you configure handlers **once**, at the program's entry point, and every module simply does `logging.getLogger(__name__)`:

```python
import io
import logging

stream = io.StringIO()
handler = logging.StreamHandler(stream)
handler.setFormatter(logging.Formatter("%(name)s | %(message)s"))

parent = logging.getLogger("app")
parent.setLevel(logging.INFO)
parent.addHandler(handler)
parent.propagate = False

logging.getLogger("app.db").info("connected")
logging.getLogger("app.web").info("listening")
logging.getLogger("app.web").debug("hidden")
print(stream.getvalue(), end="")
```

```text
app.db | connected
app.web | listening
```

Library code never configures handlers. It only creates loggers and calls them. The application decides what to do with the output.

## Logging exceptions

`logger.exception(...)` (inside an `except` block) logs at `ERROR` level **and includes the traceback**:

```python
import io
import logging

stream = io.StringIO()
logger = logging.getLogger("jobs")
logger.handlers.clear()
logger.setLevel(logging.INFO)
logger.addHandler(logging.StreamHandler(stream))
logger.propagate = False

def run_job(n):
    try:
        return 10 / n
    except ZeroDivisionError:
        logger.exception("job %s failed", n)
        return None

run_job(0)
lines = stream.getvalue().splitlines()
print(lines[0])
print("Traceback" in stream.getvalue(), lines[-1])
```

```text
job 0 failed
True ZeroDivisionError: division by zero
```

You get the message and the full story of what failed, ready for whoever investigates. Remember lesson 3.3.1: **log it, handle it, or re-raise it, but never swallow it silently.**

## Structured logging: logs a machine can read

Plain text lines are readable to humans but awkward to search at scale. **Structured logs** emit one **JSON object per line**, so tools can filter by field (`user=ada`, `status=500`):

```python
import io
import json
import logging

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {"level": record.levelname, "logger": record.name, "message": record.getMessage()}
        payload.update(getattr(record, "fields", {}))          # extra context
        if record.exc_info:
            payload["error"] = repr(record.exc_info[1])
        return json.dumps(payload, sort_keys=True)

stream = io.StringIO()
handler = logging.StreamHandler(stream)
handler.setFormatter(JsonFormatter())
logger = logging.getLogger("api")
logger.handlers.clear()
logger.setLevel(logging.INFO)
logger.addHandler(handler)
logger.propagate = False

logger.info("request handled", extra={"fields": {"user": "ada", "status": 200, "ms": 12}})
try:
    1 / 0
except ZeroDivisionError:
    logger.error("request failed", exc_info=True, extra={"fields": {"user": "linus"}})

for line in stream.getvalue().splitlines():
    print(json.loads(line))
```

```text
{'level': 'INFO', 'logger': 'api', 'message': 'request handled', 'ms': 12, 'status': 200, 'user': 'ada'}
{'error': "ZeroDivisionError('division by zero')", 'level': 'ERROR', 'logger': 'api', 'message': 'request failed', 'user': 'linus'}
```

The `extra={"fields": ...}` mechanism attaches arbitrary key/value context to a record. Each line is valid JSON, so a log tool can answer "show me all errors for user linus" with a simple filter.

## Logging to files

`FileHandler` writes to a file, and `RotatingFileHandler` starts a new file when the old one gets large, so logs never fill the disk:

```python
import logging
from logging.handlers import RotatingFileHandler
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory() as folder:
    path = Path(folder) / "app.log"
    handler = RotatingFileHandler(path, maxBytes=200, backupCount=2)
    handler.setFormatter(logging.Formatter("%(levelname)s:%(message)s"))
    logger = logging.getLogger("rotating")
    logger.handlers.clear()
    logger.setLevel(logging.INFO)
    logger.addHandler(handler)
    logger.propagate = False

    for i in range(30):
        logger.info("event number %d", i)
    handler.close()
    logger.removeHandler(handler)

    files = sorted(p.name for p in Path(folder).iterdir())
    print(files)
    print(path.read_text().splitlines()[-1])
```

```text
['app.log', 'app.log.1', 'app.log.2']
INFO:event number 29
```

When `app.log` reached the size limit it was renamed to `app.log.1`, and so on, keeping only the last two backups.

## Command-line tools: argparse

Terminal tools take **arguments** (`copy a.txt b.txt`), **options** (`--verbose`), and print help (`--help`). The standard library's `argparse` handles parsing, validation, type conversion and usage messages:

```python
import argparse

parser = argparse.ArgumentParser(prog="greet", description="Say hello to someone.")
parser.add_argument("name", help="who to greet")
parser.add_argument("-c", "--count", type=int, default=1, help="how many times")
parser.add_argument("--shout", action="store_true", help="use capitals")

args = parser.parse_args(["Ada", "-c", "2", "--shout"])
print(args.name, args.count, args.shout)

greeting = f"Hello, {args.name}!"
if args.shout:
    greeting = greeting.upper()
print("\n".join([greeting] * args.count))

args = parser.parse_args(["Linus"])
print(args.name, args.count, args.shout)
```

```text
Ada 2 True
HELLO, ADA!
HELLO, ADA!
Linus 1 False
```

In a real program you call `parser.parse_args()` with no argument and it reads `sys.argv` (the actual command line). Passing a list, as here, is how you **test** a CLI without a terminal. Parsing mistakes are reported for you:

```python
import argparse

parser = argparse.ArgumentParser(prog="greet")
parser.add_argument("--count", type=int)

try:
    parser.parse_args(["--count", "many"])
except SystemExit as exit_info:
    print("exit code", exit_info.code)
```

```text
exit code 2
```

`argparse` printed an error message to the terminal's error stream and raised `SystemExit(2)`, the conventional exit code for a usage error.

## Subcommands

Tools like `git commit` and `pip install` have **subcommands**, each with its own arguments:

```python
import argparse

def build_parser():
    parser = argparse.ArgumentParser(prog="todo")
    sub = parser.add_subparsers(dest="command", required=True)

    add = sub.add_parser("add", help="add a task")
    add.add_argument("title")
    add.add_argument("--priority", type=int, choices=[1, 2, 3], default=2)

    done = sub.add_parser("done", help="finish a task")
    done.add_argument("task_id", type=int)

    sub.add_parser("list", help="show tasks")
    return parser

parser = build_parser()
for argv in (["add", "write lesson", "--priority", "1"], ["done", "3"], ["list"]):
    args = parser.parse_args(argv)
    print(vars(args))
```

```text
{'command': 'add', 'title': 'write lesson', 'priority': 1}
{'command': 'done', 'task_id': 3}
{'command': 'list'}
```

## A testable program structure

Put the work in a function that takes `argv` and **returns an exit code**. Only the very bottom touches the real command line. That makes your tool trivial to test:

```python
import argparse
import io

def main(argv=None, out=None):
    out = out if out is not None else io.StringIO()
    parser = argparse.ArgumentParser(prog="calc")
    parser.add_argument("a", type=float)
    parser.add_argument("op", choices=["add", "sub", "mul", "div"])
    parser.add_argument("b", type=float)
    args = parser.parse_args(argv)

    try:
        if args.op == "add":
            result = args.a + args.b
        elif args.op == "sub":
            result = args.a - args.b
        elif args.op == "mul":
            result = args.a * args.b
        else:
            result = args.a / args.b
    except ZeroDivisionError:
        print("error: division by zero", file=out)
        return 1

    print(result, file=out)
    return 0

buffer = io.StringIO()
code = main(["6", "mul", "7"], buffer)
print(code, buffer.getvalue().strip())

buffer = io.StringIO()
code = main(["1", "div", "0"], buffer)
print(code, buffer.getvalue().strip())

# at the very bottom of a real script:
# if __name__ == "__main__":
#     raise SystemExit(main())
```

```text
0 42.0
1 error: division by zero
```

The conventions to follow:

- **Exit code 0 means success.** Any non-zero code means failure (1 for a general error, 2 for bad usage). Shell scripts and other programs rely on it.
- **Normal output goes to standard output, errors go to standard error** (`print(..., file=sys.stderr)`), so users can redirect them separately.
- **`if __name__ == "__main__":`** runs `main()` only when the file is executed directly, not when it is imported (lesson 1.7.4).

## Reading input: files, pipes and stdin

Good tools work in pipelines (`cat data.txt | mytool`). Reading from `sys.stdin` makes that possible, and `argparse.FileType` can default to it:

```python
import io
import sys

def count_words(stream):
    return sum(len(line.split()) for line in stream)

print(count_words(io.StringIO("one two\nthree\n")))

# in a real tool: count_words(sys.stdin) reads whatever is piped in
print(sys.stdin is not None)
```

```text
3
True
```

## Putting logging and the CLI together

A verbose flag that switches the log level is the standard pairing:

```python
import argparse
import io
import logging

def main(argv):
    parser = argparse.ArgumentParser(prog="worker")
    parser.add_argument("-v", "--verbose", action="count", default=0, help="-v for info, -vv for debug")
    args = parser.parse_args(argv)

    level = [logging.WARNING, logging.INFO, logging.DEBUG][min(args.verbose, 2)]
    stream = io.StringIO()
    log = logging.getLogger("worker")
    log.handlers.clear()
    log.addHandler(logging.StreamHandler(stream))
    log.setLevel(level)
    log.propagate = False

    log.debug("detail")
    log.info("progress")
    log.warning("careful")
    return stream.getvalue().splitlines()

print(main([]))
print(main(["-v"]))
print(main(["-vv"]))
```

```text
['careful']
['progress', 'careful']
['detail', 'progress', 'careful']
```

By default only warnings appear, `-v` adds progress messages, and `-vv` adds the fine detail. This is the interface users of command-line tools expect.

## Common mistakes

- **Using `print` for diagnostics** in code that will run unattended. Use `logging`.
- **Formatting log messages with f-strings,** which does the work even when the message is hidden. Pass arguments.
- **Configuring handlers inside library modules,** instead of once at the program's entry point.
- **Logging secrets** (passwords, tokens, full card numbers).
- **Logging an exception and then raising a new one with no chain,** or swallowing it altogether.
- **Returning success (exit code 0) after a failure,** which fools scripts and automation.
- **Hard-wiring `sys.argv`** into your logic, so the tool cannot be tested. Accept `argv` as a parameter.

import argparse, io, logging

def setup_logging(verbosity):
    stream = io.StringIO()
    log = logging.getLogger("demo.setup")
    log.handlers.clear()
    log.addHandler(logging.StreamHandler(stream))
    log.setLevel([logging.WARNING, logging.INFO, logging.DEBUG][min(verbosity, 2)])

log, stream = setup_logging(1)
log.debug("d"); log.info("i"); log.warning("w")

## Recap

- **Logging** replaces `print` for programs that run unattended. Messages have **levels** (`DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`), and a logger shows those at or above its level.
- A **logger** (named with `getLogger(__name__)`) is what code calls, a **handler** decides where records go, and a **formatter** decides how they look. Configure handlers **once** at the entry point. Libraries only create loggers.
- Pass values as arguments (`logger.info("x %s", x)`), use `logger.exception` inside `except` to include the traceback, and emit **JSON lines** (structured logs) when machines will read them. `RotatingFileHandler` keeps log files from growing forever.
- **`argparse`** builds command-line interfaces: positional arguments, options (`--count`, `-v`), `type`, `choices`, `action="store_true"`, and subcommands. It prints usage and errors for you.
- Write `main(argv)` returning an **exit code** (0 success, non-zero failure), send errors to standard error, and call it from `if __name__ == "__main__":`. A tool that accepts `argv` can be tested without a terminal.
