# Exception Hierarchies & Custom Errors

In lesson 1.7.2 you learned to catch errors with `try`/`except`. That was the mechanics. This lesson is about **design**: how to organise errors so a large program can fail **clearly** and **recoverably**. Real systems have layers (user input, business rules, database, network), and each layer needs to tell the one above it exactly what went wrong, without leaking internal details or hiding the real cause.

## Exceptions are a family tree

Every exception is a class, and classes form a hierarchy. Catching a parent catches all its children:

```python
print(ZeroDivisionError.__mro__)
print(issubclass(ZeroDivisionError, ArithmeticError))
print(issubclass(KeyError, LookupError), issubclass(IndexError, LookupError))
print(issubclass(FileNotFoundError, OSError))

try:
    {}["missing"]
except LookupError as err:
    print("caught a", type(err).__name__, "via its parent LookupError")
```

```text
(<class 'ZeroDivisionError'>, <class 'ArithmeticError'>, <class 'Exception'>, <class 'BaseException'>, <class 'object'>)
True
True True
True
caught a KeyError via its parent LookupError
```

The top of the tree matters:

```text
BaseException
 ├── SystemExit, KeyboardInterrupt, GeneratorExit   (not errors: do not catch these)
 └── Exception                                      (all ordinary errors)
      ├── ArithmeticError  (ZeroDivisionError, OverflowError)
      ├── LookupError      (KeyError, IndexError)
      ├── OSError          (FileNotFoundError, PermissionError, TimeoutError)
      ├── ValueError, TypeError, AttributeError, RuntimeError ...
```

The key rule: **catch `Exception` (or something narrower), never `BaseException` or a bare `except:`**. `KeyboardInterrupt` (Ctrl+C) and `SystemExit` derive from `BaseException` precisely so ordinary `except Exception:` handlers do not swallow them.

Catch as **narrowly** as you can. The order of `except` clauses matters: the first match wins, so list specific errors before general ones:

```python
def read_setting(settings, key):
    try:
        return int(settings[key])
    except KeyError:
        return "missing"
    except (ValueError, TypeError):
        return "not a number"
    except Exception:
        return "something else"

print(read_setting({"n": "5"}, "n"))
print(read_setting({}, "n"))
print(read_setting({"n": "abc"}, "n"))
print(read_setting({"n": None}, "n"))
```

```text
5
missing
not a number
not a number
```

## Your own hierarchy

Define errors that describe **your program's problems**, with one base class so callers can catch "anything from this library" in one clause:

```python
class AppError(Exception):
    """Base class for every error this application raises on purpose."""

class ValidationError(AppError):
    """The caller supplied bad data."""

class NotFoundError(AppError):
    """A requested thing does not exist."""

class StorageError(AppError):
    """The storage layer failed."""

def find_user(users, name):
    if not isinstance(name, str) or not name:
        raise ValidationError("name must be a non-empty string")
    if name not in users:
        raise NotFoundError(f"no user named {name!r}")
    return users[name]

users = {"ada": {"age": 36}}
for query in ("ada", "linus", ""):
    try:
        print(find_user(users, query))
    except NotFoundError as err:
        print("not found:", err)
    except AppError as err:
        print("app error:", type(err).__name__, "-", err)
```

```text
{'age': 36}
not found: no user named 'linus'
app error: ValidationError - name must be a non-empty string
```

The hierarchy pays off in two ways:

- Code that cares about **specifics** catches `NotFoundError` (for example, to show a 404 page).
- Code that only needs a **safety net** catches `AppError` (for example, the top-level handler that logs and shows a friendly message), without also hiding genuine bugs like `TypeError`.

### Adding data to errors

Exceptions are objects, so they can carry structured information, not just a message:

```python
class ValidationError(Exception):
    def __init__(self, field, problem):
        super().__init__(f"{field}: {problem}")      # keeps str(err) readable
        self.field = field
        self.problem = problem

def validate(form):
    if "@" not in form.get("email", ""):
        raise ValidationError("email", "must contain @")
    if len(form.get("password", "")) < 8:
        raise ValidationError("password", "too short")
    return True

for form in ({"email": "a.com"}, {"email": "a@b.com", "password": "x"}, {"email": "a@b.com", "password": "longenough"}):
    try:
        print(validate(form))
    except ValidationError as err:
        print(err.field, "->", err.problem, "|", err)
```

```text
email -> must contain @ | email: must contain @
password -> too short | password: too short
True
```

A web form can use `err.field` to highlight exactly the input that failed. A message string alone would force it to parse text.

## Exception chaining: keep the real cause

When a low-level error is turned into a high-level one, **keep the original** with `raise ... from ...`. The chain shows both the cause and the consequence:

```python
class ConfigError(Exception):
    pass

def load_port(text):
    try:
        return int(text)
    except ValueError as err:
        raise ConfigError(f"invalid port {text!r}") from err

try:
    load_port("eighty")
except ConfigError as err:
    print(err)
    print(type(err.__cause__).__name__, "-", err.__cause__)
```

```text
invalid port 'eighty'
ValueError - invalid literal for int() with base 10: 'eighty'
```

`err.__cause__` is the original `ValueError`. In a traceback you would see both, joined by "The above exception was the direct cause of the following exception". That story is what lets someone debug the problem at 3 a.m.

Use `from None` when the low-level cause is only noise to the caller:

```python
def get_setting(config, key):
    try:
        return config[key]
    except KeyError:
        raise LookupError(f"setting {key} is required") from None

try:
    get_setting({}, "host")
except LookupError as err:
    print(err, "|", err.__cause__)
```

```text
setting host is required | None
```

If you raise a new exception **inside** an `except` block without `from`, Python still records the old one as `__context__`, so nothing is lost silently.

## Translating errors at boundaries

Each layer should speak its own language. The database layer raises database errors, but the business layer should not leak them. **Translate at the boundary**:

```python
class StorageError(Exception):
    pass

class FakeDb:
    def __init__(self):
        self.rows = {1: "ada"}

    def fetch(self, row_id):
        return self.rows[row_id]          # raises KeyError

def get_name(db, row_id):
    try:
        return db.fetch(row_id)
    except KeyError as err:
        raise StorageError(f"row {row_id} is missing") from err

db = FakeDb()
print(get_name(db, 1))
try:
    get_name(db, 99)
except StorageError as err:
    print("storage problem:", err, "| cause:", repr(err.__cause__))
```

```text
ada
storage problem: row 99 is missing | cause: KeyError(99)
```

Callers of `get_name` only need to know about `StorageError`. They do not care that the storage happens to be a dictionary today and a real database tomorrow.

## else and finally in practice

`else` holds code that should run **only if the `try` succeeded**, keeping the risky block small. `finally` runs **no matter what**, which is where cleanup belongs:

```python
def process(values):
    log = []
    try:
        total = sum(values)
    except TypeError:
        log.append("bad values")
        return None, log
    else:
        log.append("summed")
        return total, log
    finally:
        log.append("done")

print(process([1, 2, 3]))
print(process([1, "x"]))
```

```text
(6, ['summed', 'done'])
(None, ['bad values', 'done'])
```

Notice that `"done"` is the last entry in **both** lists. `finally` runs just **before** the function actually hands back its result, even though the `return` statements come earlier in the code. Lesson 3.3.2 replaces most hand-written `finally` cleanup with `with` statements.

## Re-raising and cleanup

Sometimes you want to **react** to an error but still let it continue upward. A bare `raise` re-raises the current exception with its traceback intact:

```python
def risky(n):
    if n < 0:
        raise ValueError("negative")
    return n

def wrapper(n, events):
    try:
        return risky(n)
    except ValueError:
        events.append("logged the problem")
        raise                               # same error, same traceback

events = []
try:
    wrapper(-1, events)
except ValueError as err:
    print(err, events)
```

```text
negative ['logged the problem']
```

## Several errors at once: exception groups

Python 3.11 added `ExceptionGroup` for cases where **several** failures happen together, common in concurrent code (lesson 3.4.5). `except*` handles the parts separately:

```python
errors = ExceptionGroup("batch failed", [ValueError("bad id"), TypeError("bad type"), ValueError("bad name")])

try:
    raise errors
except* ValueError as group:
    print("value errors:", [str(e) for e in group.exceptions])
except* TypeError as group:
    print("type errors:", [str(e) for e in group.exceptions])
```

```text
value errors: ['bad id', 'bad name']
type errors: ['bad type']
```

You will meet this properly with `asyncio.TaskGroup`. For now, know that it exists.

## Adding context with notes

`add_note` (Python 3.11) attaches extra explanation to an error as it travels upward:

```python
def parse_line(number, line):
    try:
        return int(line)
    except ValueError as err:
        err.add_note(f"while parsing line {number}")
        raise

try:
    parse_line(7, "x")
except ValueError as err:
    print(err.__notes__)
```

```text
['while parsing line 7']
```

## Warnings: problems that are not errors

When something is wrong but not fatal (a deprecated function, a suspicious value), raise a **warning**, not an exception:

```python
import warnings

def old_api():
    warnings.warn("old_api is deprecated, use new_api", DeprecationWarning, stacklevel=2)
    return "result"

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    value = old_api()

print(value, len(caught), caught[0].category.__name__)
```

```text
result 1 DeprecationWarning
```

The program carries on, and users or tests can decide whether warnings should be displayed, ignored or turned into errors.

## Designing good errors: a checklist

1. **Name them for the problem,** not the place: `InsufficientFunds`, not `BankError2`.
2. **One base class** for the application so there is one safety net.
3. **Carry data** (`field`, `limit`, `id`) as attributes, plus a readable message.
4. **Keep the cause** with `raise ... from err`.
5. **Translate at boundaries** so layers do not leak details.
6. **Fail early and loudly** with a clear message. Do not return `None` or `-1` to signal an error that callers will forget to check.
7. **Never swallow silently.** If you catch it, handle it, log it or re-raise it.

## Common mistakes

- **Catching `Exception` everywhere,** turning real bugs (typos, `TypeError`s) into quiet wrong answers.
- **Catching in the wrong order,** so a general `except` hides a specific one.
- **Using exceptions for ordinary control flow** where an `if` is clearer.
- **Raising bare `Exception("something")`,** which callers cannot catch precisely.
- **Losing the cause** by raising a new error without `from err`.
- **Returning error codes** (`None`, `False`, `-1`) instead of raising.
- **Putting a lot of code in `try`,** so you cannot tell which line failed.

## Practice

1. Create `ShopError` with subclasses `OutOfStock(item)` and `PaymentDeclined(reason)`. Write a `checkout` that raises them, and a handler that catches `ShopError` once.
2. Write `parse_age(text)` that raises `ValidationError` (custom) for non-numbers and for ages outside 0 to 150, chaining the original `ValueError`.
3. Write `safe_call(func, *args)` that returns `(True, result)` or `(False, error_message)` without catching `BaseException`.
4. Why is `except Exception: pass` a bug magnet? Name two real bugs it would hide.

+++ Solutions
```python
class ShopError(Exception):
    pass

class OutOfStock(ShopError):
    def __init__(self, item):
        super().__init__(f"{item} is out of stock")
        self.item = item

class PaymentDeclined(ShopError):
    def __init__(self, reason):
        super().__init__(f"payment declined: {reason}")
        self.reason = reason

def checkout(stock, item, funds, price):
    if stock.get(item, 0) <= 0:
        raise OutOfStock(item)
    if funds < price:
        raise PaymentDeclined("insufficient funds")
    return "ok"

for args in (({"pen": 1}, "pen", 5, 2), ({}, "ink", 5, 2), ({"pen": 1}, "pen", 1, 2)):
    try:
        print(checkout(*args))
    except ShopError as err:
        print("failed:", err)
```

```python
class ValidationError(Exception):
    pass

def parse_age(text):
    try:
        age = int(text)
    except ValueError as err:
        raise ValidationError(f"age must be a number, got {text!r}") from err
    if not 0 <= age <= 150:
        raise ValidationError("age out of range")
    return age

def safe_call(func, *args):
    try:
        return True, func(*args)
    except Exception as err:
        return False, str(err)

print(safe_call(parse_age, "42"), safe_call(parse_age, "x"), safe_call(parse_age, "200"))
```

`except Exception: pass` hides typos such as a misspelled attribute (`AttributeError`), a wrong argument type (`TypeError`), and any genuine failure you should have known about (a missing file, a lost connection). The program keeps running with wrong or missing data.

## Recap

- Exceptions are classes in a **hierarchy**. Catching a parent catches its children, and the first matching `except` wins, so order specific before general.
- Catch **`Exception` or narrower**, never `BaseException` or a bare `except:`, which would swallow Ctrl+C and exit requests.
- Build your own hierarchy with **one base class** per application, give errors **names that describe the problem**, and attach data as attributes.
- Chain with `raise NewError(...) from err` to keep the cause (`__cause__`). Use `from None` to hide noise, and a bare `raise` to re-raise unchanged.
- **Translate errors at layer boundaries** so callers see your layer's errors, not the internals of the layer beneath.
- `else` runs on success, `finally` always runs. `ExceptionGroup`/`except*` handle several simultaneous failures, `add_note` adds context, and `warnings` report problems that are not fatal.
- Fail early and loudly, carry useful data, and never swallow an error silently.
