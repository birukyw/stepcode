# CPU-Bound vs. I/O-Bound & The GIL

A modern computer can do many things at once, and most of the programs you have written so far do **one thing at a time**. That is fine for a calculator. It is a problem for a web server handling a thousand visitors, a scraper fetching a hundred pages, or a data job crunching a billion numbers. **Concurrency** is the set of techniques for making a program do more in the same time. But there is no single "go faster" switch: the right tool depends entirely on **what your program is waiting for**. This lesson teaches you to diagnose that, and explains the famous Python quirk that surprises everyone: the **GIL**.

> **Tip:** Threads and processes need a real operating system, so the snippets marked **run it on your computer** cannot run in the course editor. They have a **Copy code** button. Paste them into a file, run `python3 file.py`, and compare with the output shown. The pure-Python snippets (no marker) run right here in the editor.

## Two words people mix up

- **Concurrency** is about **dealing with** many things at once: several tasks are in progress, and the program switches between them. One cook juggling three pans.
- **Parallelism** is about **doing** many things at the same instant, on several CPU cores. Three cooks, each with a pan.

Concurrency is a way of structuring a program. Parallelism needs hardware. You can have concurrency without parallelism (one core, switching quickly), and that already helps a lot, as you will see.

## What is your program waiting for?

Every slow program is slow for one of two reasons:

| | **CPU-bound** | **I/O-bound** |
|---|---|---|
| The program is waiting for... | its own calculation | something outside the CPU |
| Examples | image processing, number crunching, compressing, sorting 50 million items | web requests, database queries, reading files, waiting for user input |
| The CPU is... | busy near 100% | mostly idle, waiting |
| Making it faster needs... | **more CPU cores working** | **overlapping the waiting** |

This is the single most important question in concurrency: *is my program computing, or waiting?* Everything else follows from the answer.

Here is a CPU-bound task and an I/O-bound one. (We simulate the waiting with a sleep, which is what a network wait looks like to your program: nothing happens for a while.)

```python local
import time

def cpu_task(n=3_000_000):
    total = 0
    for i in range(n):
        total += i * i
    return total

def io_task(seconds=0.2):
    time.sleep(seconds)          # pretend this is a network request
    return "response"

start = time.perf_counter()
cpu_task()
cpu_time = time.perf_counter() - start

start = time.perf_counter()
io_task()
io_time = time.perf_counter() - start

print("cpu task took real work:", cpu_time > 0.05)
print("io task took about 0.2s:", 0.19 < io_time < 0.35)
```

```text
cpu task took real work: True
io task took about 0.2s: True
```

While `io_task` sleeps, the CPU does **nothing**. That wasted time is the opportunity: if you can start the next request while waiting for the first, ten requests take about as long as one.

## Overlapping the waiting: threads for I/O

A **thread** is an independent path of execution inside your program. Several threads can wait at the same time:

```python local
import time
from concurrent.futures import ThreadPoolExecutor

def fetch(i):
    time.sleep(0.2)              # a pretend 0.2 second request
    return i * 10

start = time.perf_counter()
sequential = [fetch(i) for i in range(5)]
sequential_time = time.perf_counter() - start

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=5) as pool:
    threaded = list(pool.map(fetch, range(5)))
threaded_time = time.perf_counter() - start

print(sequential == threaded)
print("sequential takes about 1 second:", sequential_time >= 1.0)
print("threads take about 0.2 seconds:", threaded_time < 0.6)
```

```text
True
sequential takes about 1 second: True
threads take about 0.2 seconds: True
```

Five 0.2 second waits finished in about 0.2 seconds instead of 1.0, because the waits overlapped. You did not need five CPU cores for that. The cores were not the bottleneck. **For I/O-bound work, threads (or async, lesson 3.4.4) give a huge speedup.**

## The surprise: threads do not speed up CPU work

Now try the same trick on a CPU-bound task:

```python local
import time
from concurrent.futures import ThreadPoolExecutor

def burn(n=2_000_000):
    total = 0
    for i in range(n):
        total += i * i
    return total

start = time.perf_counter()
sequential = [burn() for _ in range(4)]
sequential_time = time.perf_counter() - start

start = time.perf_counter()
with ThreadPoolExecutor(max_workers=4) as pool:
    threaded = list(pool.map(lambda _: burn(), range(4)))
threaded_time = time.perf_counter() - start

print(sequential == threaded)
print("four threads are NOT four times faster:", threaded_time > sequential_time * 0.5)
```

```text
True
four threads are NOT four times faster: True
```

Four threads on a machine with four or more cores did not give a four-times speedup. Usually the threaded version is no faster at all, and sometimes slightly slower. The reason has a name.

## The GIL

CPython (the standard Python) has a **Global Interpreter Lock**, the **GIL**. It is a lock that allows **only one thread to execute Python bytecode at a time**, even on a machine with many cores. Threads take turns: one runs for a short slice, then the interpreter switches to another.

Why does it exist? CPython manages memory by **reference counting** (lesson 3.5.5): every object keeps a count of how many names point at it, and is freed when the count hits zero. Those counts are updated constantly, from everywhere. Making every update individually thread-safe would be slow and complex. One big lock makes the interpreter simple and fast for single-threaded programs, and makes C extensions easy to write.

The consequences:

- **CPU-bound threads cannot run Python code in parallel.** They take turns, so there is no speedup (and some switching overhead).
- **Waiting releases the GIL.** When a thread blocks on a socket, a file, `time.sleep`, or a database call, it releases the lock, and other threads can run. That is why threads work well for I/O.
- **Many C libraries release the GIL** while doing heavy work: NumPy, image libraries, compression, hashing. Threads can overlap those too.
- **A few operations are atomic** because they are a single bytecode step, but you must not rely on that (lesson 3.4.2).

> **Note:** Since Python 3.13 there is an experimental **free-threaded** build with the GIL switched off, and it is becoming more capable with each release. The standard build you have installed still has the GIL, and almost all existing code and libraries assume it. Learn the model above, because it is how production Python works today.

## So how do you use all the cores?

If threads cannot parallelise Python code, you have three main options:

1. **Multiple processes.** Each process has its **own interpreter and its own GIL**, so several can run on several cores. This is `multiprocessing` (lesson 3.4.3).
2. **Native code that releases the GIL.** NumPy, pandas, Cython, Rust or C extensions do the heavy loops outside Python's rules.
3. **A better algorithm.** Before adding cores, ask whether you can do less work. Replacing an O(n²) loop with O(n log n) (module 2) beats any amount of parallelism.

## Choosing the right tool

| Your problem | Reach for | Why |
|---|---|---|
| Many slow network or disk waits, simple code | **threads** (`ThreadPoolExecutor`) | the GIL is released while waiting |
| Thousands of connections, waiting dominates | **asyncio** | one thread, tiny cost per task |
| Heavy Python computation | **processes** (`ProcessPoolExecutor`) | each has its own GIL |
| Heavy numeric work | **NumPy** or similar | the loop runs in C |
| It is just slow | **profile and fix the algorithm** | measure first |

A rule many engineers repeat: **"threads for waiting, processes for computing, async for lots of waiting."**

## Cost: processes, threads and coroutines

| | Process | Thread | Coroutine (asyncio) |
|---|---|---|---|
| Memory shared? | no (separate) | yes (same objects) | yes |
| Creation cost | high (milliseconds, a copy of the interpreter) | medium | very low (a small object) |
| Parallel Python code? | **yes** | no (GIL) | no (single thread) |
| Typical count | a handful (one per core) | tens to hundreds | thousands to millions |
| Main danger | slow data transfer (pickling) | **race conditions** | one blocking call freezes everything |

Memory sharing is a double-edged sword. Threads can read each other's data instantly, and that is exactly why they can **corrupt** each other's data. The next lesson is about that.

## How much speedup can you ever get? Amdahl's law

Even perfect parallelism has a limit. If a fraction `p` of the work can run in parallel and the rest (`1 - p`) must run serially, then with `n` workers:

```python
def amdahl(p, n):
    return 1 / ((1 - p) + p / n)

for p in (0.50, 0.90, 0.99):
    print(p, [round(amdahl(p, n), 2) for n in (2, 4, 16, 1000)])
```

```text
0.5 [1.33, 1.6, 1.88, 2.0]
0.9 [1.82, 3.08, 6.4, 9.91]
0.99 [1.98, 3.88, 13.91, 90.99]
```

If only 90% of the program can be parallelised, then **even with a thousand workers the speedup stops near 10x**, because the serial 10% dominates. This is why "just add more threads" disappoints, and why finding and shrinking the serial part matters more than adding workers.

## Measure, do not guess

Concurrency adds complexity. Prove you need it, and prove it helped:

```python
import time

def timed(func, *args):
    start = time.perf_counter()
    result = func(*args)
    return result, time.perf_counter() - start

result, seconds = timed(sum, range(1_000_000))
print(result, seconds >= 0)
```

```text
499999500000 True
```

`time.perf_counter()` is the right clock for measuring durations: it is high resolution and never goes backwards. For small snippets, `timeit` repeats the measurement for you and reduces noise. Lesson 3.5.5 covers profilers that tell you **where** the time goes.

## A decision flow

1. **Is it fast enough?** Then stop. Concurrency is not free.
2. **Profile.** Is the time spent computing or waiting?
3. **Waiting?** Overlap it: threads for simple code, asyncio for very many connections.
4. **Computing?** Improve the algorithm, use NumPy, then use processes.
5. **Measure again.** Keep it only if it truly helped.

## Common mistakes

- **Using threads to speed up a CPU-bound loop** and being surprised that nothing improves.
- **Using processes for tiny tasks,** where the cost of starting them and moving data costs more than the work.
- **Assuming "more workers" always means faster.** Amdahl's law, and shared bottlenecks (one disk, one API rate limit), cap the gain.
- **Timing with `time.time()` and one run.** Use `perf_counter` and repeat.
- **Adding concurrency before profiling.**
- **Believing the GIL makes threaded code automatically safe.** It does not (next lesson).

```python
# 1. resizing photos: CPU. downloading: I/O. sorting: CPU. reading files: I/O (disk). training: CPU.

def amdahl(p, n):
    return 1 / ((1 - p) + p / n)

for n in (4, 8, 16, 32):
    print(n, round(amdahl(0.95, n), 2))
# about 8 workers give roughly 5.9x, and 7 give about 5.4x, so around 6 workers reach 5x
```

500 web pages: **I/O-bound**, so threads (or asyncio for efficiency). Primes up to 50 million: **CPU-bound**, so multiple processes (or a better algorithm such as a sieve, or NumPy).

```python
import time

def best_of_three(func, *args):
    best = None
    for _ in range(3):
        start = time.perf_counter()
        func(*args)
        elapsed = time.perf_counter() - start
        best = elapsed if best is None else min(best, elapsed)
    return best

print(best_of_three(sum, range(100_000)) >= 0)   # True
```

## Recap

- **Concurrency** structures a program to handle many things at once. **Parallelism** runs things at the same instant on several cores.
- First diagnose: is the program **CPU-bound** (computing) or **I/O-bound** (waiting)? The answer picks the tool.
- The **GIL** lets only one thread run Python bytecode at a time. Threads therefore **do not speed up CPU-bound Python**, but they do overlap **waiting**, because blocking calls release the GIL.
- For CPU-bound work use **multiple processes** (each with its own GIL), **native libraries** like NumPy, or a **better algorithm**.
- Threads share memory (fast, but dangerous), processes do not (safe, but data must be copied), and coroutines are the cheapest of all.
- **Amdahl's law:** the serial fraction caps the speedup no matter how many workers you add.
- Measure with `perf_counter`, and add concurrency only after profiling shows you need it.
