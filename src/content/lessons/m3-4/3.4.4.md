# Cooperative Multitasking & The Event Loop

Threads and processes are **preemptive**: the operating system interrupts them whenever it likes, which is exactly why shared data is dangerous. There is a completely different way to run many things at once: **cooperative multitasking**. Each task runs until it **chooses** to pause (usually because it is waiting for something), and only then does another task get a turn. Nobody is ever interrupted in the middle of a step, so most race conditions simply cannot happen. Python's `asyncio` is built on this idea, and it can juggle **tens of thousands** of waiting tasks on a single thread. This lesson builds the idea from scratch so that `async` and `await` stop being magic.

> **Tip:** Everything in this lesson runs in the course editor. In the editor, `asyncio.run(...)` is handled for you, and your code stays exactly as it would be on your own computer.

## The idea: tasks that pause on purpose

Imagine a waiter serving three tables. He does not stand at table 1 until the customer finishes eating. He takes an order, goes to table 2 while the kitchen cooks, comes back. One waiter, many tables, because most of the time is waiting. That is an **event loop**: one worker that moves between tasks whenever a task says "I am waiting, do something else".

The trick that makes it possible in Python is something you already know: the **generator**. A generator can **pause** at a `yield` and **resume** exactly where it left off (lesson 3.1.3). That is all a coroutine is.

## Step 1: a tiny scheduler from generators

Here are three "tasks", written as generators that `yield` whenever they want to give up control:

```python
def task(name, steps):
    for i in range(1, steps + 1):
        print(f"{name} step {i}")
        yield                          # pause: let someone else run

def run_round_robin(tasks):
    queue = list(tasks)
    while queue:
        current = queue.pop(0)
        try:
            next(current)              # run until its next yield
            queue.append(current)      # not finished: back of the line
        except StopIteration:
            pass                       # finished: drop it

run_round_robin([task("A", 3), task("B", 2), task("C", 1)])
```

```text
A step 1
B step 1
C step 1
A step 2
B step 2
A step 3
```

The three tasks **interleaved**: A, B, C, A, B, A. No threads, no locks, no OS involvement. The "scheduler" is a twelve-line loop. Each task decided when to pause, so a task is never interrupted halfway through a thought.

## Step 2: tasks that wait for time

Real tasks do not just yield. They wait for **something**: a timer, a network reply. Let tasks yield **how long they want to sleep**, and let the loop keep a **heap** of sleeping tasks ordered by wake-up time (lesson 2.4.4). To keep the demo fast and predictable we use **virtual time**, a clock that simply jumps forward:

```python
import heapq

def worker(name, delays):
    for d in delays:
        print(f"  {name} starts a {d}s wait")
        yield d                        # "wake me in d seconds"
    print(f"  {name} finished")

def run(tasks):
    now = 0
    counter = 0                        # tie-breaker so the heap never compares generators
    heap = []
    for t in tasks:
        heapq.heappush(heap, (now, counter, t))
        counter += 1
    while heap:
        now, _, current = heapq.heappop(heap)        # the task that wakes up soonest
        print(f"t={now}")
        try:
            delay = next(current)
            heapq.heappush(heap, (now + delay, counter, current))
            counter += 1
        except StopIteration:
            pass
    return now

total = run([worker("A", [3, 1]), worker("B", [1, 1, 1])])
print("total time:", total)
```

```text
t=0
  A starts a 3s wait
t=0
  B starts a 1s wait
t=1
  B starts a 1s wait
t=2
  B starts a 1s wait
t=3
  A starts a 1s wait
t=3
  B finished
t=4
  A finished
total time: 4
```

Follow the clock: at `t=0` both start waiting. At `t=1` B wakes and waits again. At `t=3` A wakes, and so on. The program took **4 units** of virtual time, while doing the waits one after another would have taken 4 + 3 = 7. The waits **overlapped**, which is the entire point. This little `run` function is, in spirit, exactly what `asyncio` does: keep tasks, keep a heap of timers, always run whichever is ready, and jump to the next wake-up.

## Step 3: the real thing, async and await

Python bakes this pattern into the language with two keywords:

- `async def` defines a **coroutine function**: a function that can pause.
- `await something` pauses the coroutine **until `something` is done**, and lets the event loop run other tasks meanwhile.

```python
import asyncio

async def greet(name, delay):
    await asyncio.sleep(delay)         # pause here, let others run
    return f"hello {name}"

async def main():
    message = await greet("Ada", 0.01)
    print(message)

asyncio.run(main())                    # start the event loop and run main() to completion
```

```text
hello Ada
```

Three things to know about the shape of a program:

1. **Calling a coroutine function does not run it.** `greet("Ada", 0.01)` returns a coroutine **object**, a paused computation. Only `await` (or the event loop) runs it.
2. **`await` can only appear inside `async def`.**
3. **`asyncio.run(main())`** is the single entry point: it creates the event loop, runs `main()` until it finishes, and cleans up. You call it once, at the bottom of your program.

```python
import asyncio

async def compute():
    return 42

coroutine = compute()
print(type(coroutine).__name__)        # a coroutine object, nothing has run yet

async def main():
    print(await coroutine)

asyncio.run(main())
```

```text
coroutine
42
```

## Awaiting one after another is still sequential

A common beginner mistake is to expect `await` to be concurrent by itself. It is not. `await` means "wait for this, right here":

```python
import asyncio
import time

async def fetch(name, delay):
    await asyncio.sleep(delay)
    return name

async def main():
    start = time.perf_counter()
    a = await fetch("a", 0.1)
    b = await fetch("b", 0.1)
    c = await fetch("c", 0.1)
    elapsed = time.perf_counter() - start
    print([a, b, c], "sequential, about 0.3s:", 0.28 < elapsed < 0.5)

asyncio.run(main())
```

```text
['a', 'b', 'c'] sequential, about 0.3s: True
```

Each `await` waited for the previous one to finish. To get concurrency you must **start several things before waiting for any of them**.

## Running things concurrently: gather and create_task

`asyncio.gather(...)` starts several coroutines at once and waits for **all** of them:

```python
import asyncio
import time

async def fetch(name, delay):
    await asyncio.sleep(delay)
    print("finished", name)
    return name.upper()

async def main():
    start = time.perf_counter()
    results = await asyncio.gather(fetch("slow", 0.15), fetch("fast", 0.05), fetch("medium", 0.1))
    elapsed = time.perf_counter() - start
    print(results)
    print("concurrent, about 0.15s not 0.3s:", elapsed < 0.25)

asyncio.run(main())
```

```text
finished fast
finished medium
finished slow
['SLOW', 'FAST', 'MEDIUM']
concurrent, about 0.15s not 0.3s: True
```

Note two things. The tasks **finished in the order of their delays** (fast, medium, slow), not the order they were listed. But `gather` returns the **results in the order you passed them**, so `results` lines up with your inputs. Three waits that would take 0.3 seconds took 0.15.

`asyncio.create_task(coro)` is the more flexible tool: it **schedules** a coroutine to run on the loop right away and gives you a `Task` handle you can await later:

```python
import asyncio

async def worker(name, delay, log):
    log.append(f"{name} start")
    await asyncio.sleep(delay)
    log.append(f"{name} end")
    return name

async def main():
    log = []
    t1 = asyncio.create_task(worker("one", 0.05, log))
    t2 = asyncio.create_task(worker("two", 0.02, log))
    log.append("main continues immediately")
    await asyncio.sleep(0)                  # give the new tasks their first turn
    log.append("main resumed")
    r1, r2 = await t1, await t2
    print(log)
    print(r1, r2)

asyncio.run(main())
```

```text
['main continues immediately', 'one start', 'two start', 'main resumed', 'two end', 'one end']
one two
```

Read the log carefully, because it shows how cooperative scheduling works. `create_task` did **not** run the worker. It only scheduled it. The tasks first ran when `main` **gave up control** at `await asyncio.sleep(0)`. The task `two` finished before `one` because its delay was shorter. Control only moves at `await` points. Between two awaits, a task has the loop **entirely to itself**.

## `await asyncio.sleep(0)`: just yield

`sleep(0)` waits for nothing, but it hands control back to the loop for one round, letting other ready tasks run. It is the async version of the generator's bare `yield` from Step 1:

```python
import asyncio

async def chatty(name, n, log):
    for i in range(n):
        log.append(f"{name}{i}")
        await asyncio.sleep(0)             # let the others have a turn

async def main():
    log = []
    await asyncio.gather(chatty("a", 3, log), chatty("b", 3, log))
    print(" ".join(log))

asyncio.run(main())
```

```text
a0 b0 a1 b1 a2 b2
```

The tasks alternate perfectly, just like the generators of Step 1: because it is the same mechanism.

## The golden rule: never block the event loop

There is **one** thread. If a coroutine calls something slow that does **not** `await`, the whole loop freezes: nothing else can run until it returns.

```python
import asyncio

def heavy_computation():
    total = 0
    for i in range(3_000_000):           # no await inside: this hogs the loop
        total += i
    return total

async def ticker(log):
    for i in range(3):
        log.append(f"tick {i}")
        await asyncio.sleep(0)

async def blocker(log):
    log.append("blocker starts")
    heavy_computation()                   # blocks everything else
    log.append("blocker ends")

async def main():
    log = []
    await asyncio.gather(blocker(log), ticker(log))
    print(log)

asyncio.run(main())
```

```text
['blocker starts', 'blocker ends', 'tick 0', 'tick 1', 'tick 2']
```

The ticker could not run **at all** while `blocker` was busy. All of "blocker starts", "blocker ends" came first. In a real server, one blocking call means **every connected user freezes** for that long. This is the one big danger of cooperative multitasking: tasks must be **well behaved**.

The classic offenders:

- `time.sleep(...)`: use `await asyncio.sleep(...)` instead.
- Synchronous network or database libraries such as `requests`: use async libraries (`httpx`, `aiohttp`, `asyncpg`).
- Heavy CPU work: push it to a **process pool**.
- Reading huge files in one go.

When you must call blocking code, hand it to a thread so the loop stays free:

```python local
import asyncio
import time

def blocking_io():
    time.sleep(0.2)                       # a blocking call, like requests.get()
    return "done"

async def ticker(log):
    for i in range(5):
        log.append(i)
        await asyncio.sleep(0.05)

async def main():
    log = []
    result, _ = await asyncio.gather(asyncio.to_thread(blocking_io), ticker(log))
    print(result, log)

asyncio.run(main())
```

```text
done [0, 1, 2, 3, 4]
```

`asyncio.to_thread` runs the blocking function in a worker thread and lets you `await` its result. The ticker kept ticking while it waited. (Threads cannot run in the course editor, so this one is marked for your computer.) For CPU-bound work use `loop.run_in_executor` with a `ProcessPoolExecutor`.

## What the event loop actually does

Inside `asyncio.run`, the loop repeats three steps forever:

1. **Run every task that is ready**, each until its next `await`.
2. **Move tasks whose timers have expired** into the ready list.
3. **Ask the operating system which sockets and files are ready** (using `select`, `epoll` or `kqueue`), and mark the tasks waiting on them as ready. If nothing is ready, **sleep** until the next timer or I/O event.

That is it. A task that `await`s something simply registers "wake me when this is done" and returns control. Our Step 2 scheduler was a toy version of this loop.

## Awaitables: what can you await?

```python
import asyncio

async def coro():
    return "from a coroutine"

async def main():
    task = asyncio.create_task(coro())          # a Task
    future = asyncio.get_running_loop().create_future()   # a Future: a result that does not exist YET
    future.set_result("from a future")

    print(await coro())
    print(await task)
    print(await future)
    print(asyncio.iscoroutine(coro()), asyncio.isfuture(task), asyncio.isfuture(future))

asyncio.run(main())
```

```text
from a coroutine
from a coroutine
from a future
True True True
```

You can `await` a **coroutine** (runs it to completion), a **Task** (a coroutine scheduled on the loop) or a **Future** (a placeholder that something will fill in later). Anything with an `__await__` method qualifies.

## Exceptions flow through await

```python
import asyncio

async def risky(n):
    await asyncio.sleep(0.01)
    if n == 2:
        raise ValueError(f"task {n} failed")
    return n

async def main():
    try:
        await risky(2)
    except ValueError as err:
        print("caught:", err)

    outcomes = await asyncio.gather(risky(1), risky(2), risky(3), return_exceptions=True)
    print([repr(o) if isinstance(o, Exception) else o for o in outcomes])

asyncio.run(main())
```

```text
caught: task 2 failed
[1, "ValueError('task 2 failed')", 3]
```

An error raised in a coroutine arrives at the `await`, where you handle it with a normal `try`/`except`. With `gather(..., return_exceptions=True)`, failures are **returned as values** instead of raised, so one failure does not hide the other results.

## Async or threads?

| | **asyncio** | **threads** |
|---|---|---|
| Concurrency | cooperative, one thread | preemptive, several threads |
| Switches at | `await` points only | anywhere |
| Race conditions | rare (only across awaits) | common |
| Cost per task | tiny (tens of thousands fine) | larger (hundreds) |
| Needs async libraries? | **yes** | no, any library works |
| Blocking call | freezes **everything** | freezes one thread |
| Best for | very many connections, waiting-heavy servers and clients | simpler code, existing blocking libraries |

`async` code is **viral**: an `await` can only live inside `async def`, so a whole call chain tends to become async. That is the price of the efficiency.

## Common mistakes

- **Forgetting `await`.** `greet()` alone creates a coroutine and never runs it. Python warns: "coroutine ... was never awaited".
- **Awaiting in a sequence** when you wanted concurrency. Use `gather` or `create_task`.
- **Calling blocking code** (`time.sleep`, `requests`) inside a coroutine.
- **Calling `asyncio.run` inside a running loop,** or more than once in the same program's structure. Call it once at the entry point.
- **Fire-and-forget tasks** (`asyncio.create_task(x())` without keeping the result). The loop only keeps a weak reference, so the task can be garbage collected before it finishes, and its exceptions vanish. Keep a reference, or use a TaskGroup (next lesson).
- **Shared state across `await` points** assuming nothing changes. Another task can run at every `await`.

2. Write `async def fetch_all(names)` that fetches each name with a delay of 0.01 times its length, **concurrently**, returning results in input order.
3. Make this faster without changing `slow_square`: `for n in range(5): results.append(await slow_square(n))` where `slow_square` awaits `asyncio.sleep(0.05)`.
4. Explain what is wrong with `async def main(): time.sleep(2); print("done")` in a server that handles many users.

+++ Solutions
```python
import asyncio

async def fetch_all(names):
    async def fetch(name):
        await asyncio.sleep(0.01 * len(name))
        return name.upper()
    return await asyncio.gather(*(fetch(n) for n in names))

async def slow_square(n):
    await asyncio.sleep(0.05)
    return n * n

async def main():
    print(await fetch_all(["bob", "alexander", "al"]))
    results = await asyncio.gather(*(slow_square(n) for n in range(5)))   # was sequential
    print(results)

asyncio.run(main())
```

`time.sleep(2)` blocks the **only** thread, so for those two seconds the event loop cannot run any other task: every other user's request freezes. It must be `await asyncio.sleep(2)`, which suspends just this task and lets the loop serve others.

## Recap

- **Cooperative multitasking**: tasks run until they **choose** to pause. Nothing is interrupted mid-step, so shared data is far safer than with threads.
- A **generator** can pause and resume, and a tiny scheduler that loops over generators (with a heap of timers) **is** an event loop in miniature.
- `async def` creates a **coroutine function**. Calling it returns a coroutine **object** that does nothing until awaited. `await` pauses until the awaitable is done and lets other tasks run. Start the loop once with `asyncio.run(main())`.
- Awaiting one thing after another is **sequential**. Use `asyncio.gather(...)` (results come back in input order) or `asyncio.create_task(...)` to run things **concurrently**.
- Control moves **only at `await` points**, and `await asyncio.sleep(0)` simply yields.
- **Never block the event loop**: no `time.sleep`, no synchronous network or heavy CPU work inside coroutines. Use async libraries, `asyncio.to_thread`, or a process pool.
- You can await coroutines, Tasks and Futures, and errors arrive at the `await` (or are returned with `return_exceptions=True`).
