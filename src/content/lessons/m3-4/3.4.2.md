# Threads, Race Conditions & Synchronization

Threads share memory, and that is both their strength and their curse. Two threads can read and write the same variable, which makes cooperation cheap. It also lets them **step on each other's work**, producing bugs that appear only sometimes, vanish when you add a `print`, and make senior engineers weep. This lesson shows exactly **how** those bugs happen (with a demonstration you can run in the editor and get the same answer every time), and then the tools that prevent them: locks, queues, events and semaphores.

> **Tip:** Real threads cannot run in the course editor, so those snippets are marked **run it on your computer** and have a **Copy code** button. The first half of this lesson uses a small simulation that **does** run in the editor, because it makes the problem completely predictable.

## Starting a thread

```python local
import threading

def greet(name, results):
    results.append(f"hello from {name}")

results = []
threads = [threading.Thread(target=greet, args=(name, results)) for name in ("a", "b", "c")]
for t in threads:
    t.start()                    # begin running
for t in threads:
    t.join()                     # wait for it to finish

print(sorted(results))
print(threading.current_thread().name, threading.active_count())
```

```text
['hello from a', 'hello from b', 'hello from c']
MainThread 1
```

`Thread(target=func, args=...)` creates a thread, `start()` launches it, and `join()` waits for it. Without `join` your main program might finish (or read results) before the threads do. The order in which threads run is **decided by the operating system**, not by you, which is why the example sorts the results before printing them.

## The classic bug: the lost update

Here is the problem in its smallest form. Two workers each add 1 to a shared counter. The statement `counter += 1` looks like one step, but it is really **three**:

1. **Read** the current value.
2. **Add** one to it (in a temporary place).
3. **Write** the result back.

If worker A reads, then worker B reads (before A has written), then both write, the counter goes up by **one instead of two**. One update is **lost**. This is a **race condition**: the answer depends on the exact timing of who runs when.

Because real thread timing is unpredictable, let us **simulate** the interleaving with generators. Each `yield` marks a point where the "thread" may be paused, and we control the schedule ourselves:

```python
def increment(shared, name):
    value = shared["counter"]            # step 1: read
    yield f"{name} read {value}"
    value = value + 1                    # step 2: compute
    yield f"{name} computed {value}"
    shared["counter"] = value            # step 3: write
    yield f"{name} wrote {value}"

def run(schedule):
    shared = {"counter": 0}
    tasks = {"A": increment(shared, "A"), "B": increment(shared, "B")}
    log = []
    for name in schedule:                # the schedule decides who runs next
        log.append(next(tasks[name]))
    return shared["counter"], log

# A finishes completely, then B: the sensible order
print(run("AAABBB"))

# A and B interleave: both read 0 before either writes
counter, log = run("ABABAB")
print(counter)
for line in log:
    print("  ", line)
```

```text
(2, ['A read 0', 'A computed 1', 'A wrote 1', 'B read 1', 'B computed 2', 'B wrote 2'])
1
   A read 0
   B read 0
   A computed 1
   B computed 1
   A wrote 1
   B wrote 1
```

With the schedule `AAABBB` the answer is **2**, as expected. With `ABABAB` both workers read `0`, both compute `1`, both write `1`, and the final counter is **1**. Two increments happened, and one vanished.

This is not a theoretical worry. Any time two threads **read, modify, then write** shared data without protection, some schedule will break it, and in production, over millions of operations, that schedule will eventually happen.

## Seeing the real thing

On real threads, you can provoke it on purpose by inserting a tiny pause between the read and the write:

```python local
import threading
import time

counter = 0

def add_many(n):
    global counter
    for _ in range(n):
        value = counter          # read
        time.sleep(0)            # let another thread run right here
        counter = value + 1      # write back (possibly stale)

threads = [threading.Thread(target=add_many, args=(1000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print("expected 4000")
print("lost updates happened:", counter < 4000)
```

```text
expected 4000
lost updates happened: True
```

(`time.sleep(0)` just offers the interpreter a chance to switch threads. Without it, a short loop often runs without a switch, and the bug stays hidden, which is exactly what makes races so nasty in the real world: they pass the tests and fail in production.)

> **Note:** "But the GIL makes only one thread run at a time, so surely `+= 1` is safe?" No. The interpreter can switch between threads **between bytecode instructions**, and `counter += 1` is several of them. The GIL protects the interpreter's own data structures, **not your logic**.

## The fix: a lock

A **lock** (mutex) lets only one thread into a protected section at a time. Anyone else who arrives waits at the door. Use it as a context manager:

```python local
import threading
import time

counter = 0
lock = threading.Lock()

def add_many(n):
    global counter
    for _ in range(n):
        with lock:                       # only one thread inside at a time
            value = counter
            time.sleep(0)
            counter = value + 1

threads = [threading.Thread(target=add_many, args=(1000,)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(counter)
```

```text
4000
```

Now the answer is exactly 4000, every time. The whole **read-modify-write** sequence became one **critical section** that cannot be interleaved. You can see the same fix in the simulation: if A's three steps cannot be interrupted, only the schedule `AAABBB` is possible.

```python
def run_locked(schedule):
    shared = {"counter": 0}
    holder = {"owner": None}                 # who holds the lock

    def increment(name):
        while holder["owner"] not in (None, name):
            yield f"{name} waits"            # blocked: someone else holds the lock
        holder["owner"] = name               # acquire
        value = shared["counter"]
        yield f"{name} read {value}"
        value += 1
        yield f"{name} computed {value}"
        shared["counter"] = value
        holder["owner"] = None               # release
        yield f"{name} wrote {value}"

    tasks = {"A": increment("A"), "B": increment("B")}
    log = []
    for name in schedule:
        try:
            log.append(next(tasks[name]))
        except StopIteration:
            pass                             # that task already finished
    return shared["counter"], log

counter, log = run_locked("AB" * 8)          # the same nasty alternating schedule, long enough to finish
print(counter)
for line in log[:8]:
    print("  ", line)
```

```text
2
   A read 0
   B waits
   A computed 1
   B waits
   A wrote 1
   B read 1
   B computed 2
   B wrote 2
```

The same nasty alternating schedule now ends with **2**. Look at the log: whenever `B` gets a turn while `A` holds the lock, it just **waits**, and it only reads the counter after `A` has written it.

## Lock rules

```python local
import threading

lock = threading.Lock()

print(lock.acquire())                    # True: we got it
print(lock.acquire(timeout=0.1))         # False: already held, gave up after 0.1s
lock.release()

rlock = threading.RLock()                # re-entrant: the SAME thread may lock again
with rlock:
    with rlock:
        print("re-entered safely")
```

```text
True
False
re-entered safely
```

- Always use `with lock:` so the lock is **released even if an error happens**. Forgetting to release freezes every other thread forever.
- Keep critical sections **short**. A lock held while doing slow I/O makes threads queue up and wastes the whole point of threads.
- A normal `Lock` cannot be taken twice by the same thread (that would deadlock itself). An `RLock` (re-entrant lock) can.
- Use `acquire(timeout=...)` if waiting forever would be a problem.

## Deadlock: when locks wait for each other

With two or more locks, threads can freeze each other. Thread 1 holds lock A and wants lock B. Thread 2 holds lock B and wants lock A. Neither can ever proceed:

```python local
import threading

lock_a = threading.Lock()
lock_b = threading.Lock()
results = []

def worker_1():
    with lock_a:
        threading.Event().wait(0.1)            # give worker_2 time to take lock_b
        got = lock_b.acquire(timeout=0.3)      # gives up first
        results.append(("worker_1", got))
        if got:
            lock_b.release()

def worker_2():
    with lock_b:
        threading.Event().wait(0.1)
        got = lock_a.acquire(timeout=1.5)      # waits much longer
        results.append(("worker_2", got))
        if got:
            lock_a.release()

t1, t2 = threading.Thread(target=worker_1), threading.Thread(target=worker_2)
t1.start(); t2.start(); t1.join(); t2.join()
print(results)
```

```text
[('worker_1', False), ('worker_2', True)]
```

For 0.3 seconds each thread held one lock and waited for the other: a deadlock. `worker_1` then **gave up** (`False`) and left its `with lock_a:` block, which released `lock_a`, so `worker_2` could finally get it (`True`). **Without timeouts, both threads would have waited forever.** The standard cures:

1. **Always acquire multiple locks in the same global order** (for example, sort them by id).
2. **Avoid holding more than one lock** whenever you can.
3. **Use timeouts** so a stuck program reports an error instead of freezing.
4. **Prefer designs with no shared state at all** (the next sections).

## Better than locks: pass messages with a Queue

The safest way to share data between threads is to **not share it**. Instead, send it through a `queue.Queue`, which is built to be thread-safe. One thread produces work, others consume it:

```python local
import queue
import threading

jobs = queue.Queue()
results = queue.Queue()

def worker():
    while True:
        item = jobs.get()
        if item is None:                 # a sentinel meaning "no more work"
            break
        results.put(item * item)

threads = [threading.Thread(target=worker) for _ in range(3)]
for t in threads:
    t.start()

for n in range(10):
    jobs.put(n)
for _ in threads:
    jobs.put(None)                       # one stop signal per worker
for t in threads:
    t.join()

collected = []
while not results.empty():
    collected.append(results.get())
print(sorted(collected))
```

```text
[0, 1, 4, 9, 16, 25, 36, 49, 64, 81]
```

No locks in sight. Each item is handled by exactly one worker, and the queue takes care of the synchronisation internally. This **producer-consumer** pattern is the backbone of countless real systems: job queues, pipelines, logging, download managers.

You can bound a queue (`Queue(maxsize=10)`) so a fast producer **blocks** instead of flooding memory, which is called **backpressure**.

## ThreadPoolExecutor: the easy way

For most tasks you do not manage threads by hand. A **thread pool** reuses a few threads for many jobs and gives you results through **futures**:

```python local
from concurrent.futures import ThreadPoolExecutor, as_completed
import time

def work(n):
    time.sleep(0.05 * (4 - n))          # later jobs finish first
    return n * n

with ThreadPoolExecutor(max_workers=4) as pool:
    ordered = list(pool.map(work, [1, 2, 3, 4]))
    print(ordered)

    futures = {pool.submit(work, n): n for n in [1, 2, 3, 4]}
    finished = [futures[f] for f in as_completed(futures)]
    print(finished)

    def risky(n):
        if n == 3:
            raise ValueError("bad input")
        return n

    outcomes = []
    for f in [pool.submit(risky, n) for n in (1, 3)]:
        try:
            outcomes.append(f.result())
        except ValueError as err:
            outcomes.append("error: " + str(err))
    print(outcomes)
```

```text
[1, 4, 9, 16]
[4, 3, 2, 1]
[1, 'error: bad input']
```

- `pool.map` returns results **in input order**, even if the jobs finished in a different order.
- `as_completed` yields futures **in completion order**, useful for showing progress.
- `future.result()` returns the value, or **re-raises the exception** the job raised. Errors in worker threads are not lost, but you must ask for the result to see them.

## Other tools: Event, Semaphore and Condition

```python local
import threading
import time

# Event: one thread signals, others wait
ready = threading.Event()
log = []

def waiter():
    ready.wait()                          # blocks until set()
    log.append("go")

t = threading.Thread(target=waiter)
t.start()
time.sleep(0.05)
log.append("setting")
ready.set()
t.join()
print(log)

# Semaphore: allow at most N threads inside at once
slots = threading.Semaphore(2)
inside = 0
peak = 0
guard = threading.Lock()

def limited():
    global inside, peak
    with slots:
        with guard:
            inside += 1
            peak = max(peak, inside)
        time.sleep(0.05)
        with guard:
            inside -= 1

threads = [threading.Thread(target=limited) for _ in range(6)]
for th in threads:
    th.start()
for th in threads:
    th.join()
print("never more than 2 at once:", peak <= 2)
```

```text
['setting', 'go']
never more than 2 at once: True
```

An `Event` is a simple on/off flag threads can wait for. A `Semaphore(n)` is a lock that admits `n` threads at once, ideal for limiting how many simultaneous connections you open to a server.

## Thread-local data and daemons

```python local
import threading

local = threading.local()                 # each thread gets its own copy of these attributes
seen = []

def task(name):
    local.name = name
    seen.append(local.name)

threads = [threading.Thread(target=task, args=(n,)) for n in "xyz"]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(sorted(seen), hasattr(local, "name"))

def forever():
    while True:
        threading.Event().wait(1)

daemon = threading.Thread(target=forever, daemon=True)   # will not keep the program alive
daemon.start()
print("daemon:", daemon.daemon, "alive:", daemon.is_alive())
```

```text
['x', 'y', 'z'] False
daemon: True alive: True
```

`threading.local()` gives every thread its own private attributes, handy for per-request data. A **daemon** thread is killed automatically when the main program exits, which suits background chores like heartbeats. Never rely on daemons for work that must finish.

## Rules for thread-safe code

1. **Prefer not sharing.** Pass data in and results out with queues, or return values from futures.
2. **If you must share, protect it,** with a lock held for the shortest time possible.
3. **Make shared data immutable** when you can (tuples, frozen dataclasses). Nothing to race on.
4. **Lock the whole read-modify-write,** not just the write.
5. **Take multiple locks in a fixed order,** or use timeouts.
6. **Test under pressure:** many threads, many iterations, a `sleep(0)` in the gap. Concurrency bugs hide until you stress them.

## Common mistakes

- **Assuming `x += 1` is atomic.** It is read, add, write.
- **Forgetting `join()`,** and reading results before the threads finish.
- **Holding a lock during slow I/O,** serialising the whole program.
- **Releasing locks manually** instead of `with`, then leaking them on errors.
- **Swallowing exceptions in threads.** An uncaught error in a thread prints a message and the thread dies quietly. Return results through futures so errors reach you.
- **Creating a thread per task** for thousands of tasks. Use a pool.
- **Using a plain `list` or `dict` as a message channel** between threads and assuming it is always safe. Use `Queue`.

```python local
import threading

class SafeCounter:
    def __init__(self):
        self._lock = threading.Lock()
        self.value = 0

    def increment(self):
        with self._lock:
            self.value += 1

counter = SafeCounter()

def hammer():
    for _ in range(10_000):
        counter.increment()

threads = [threading.Thread(target=hammer) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter.value)   # 40000
```

Each worker thread blocks on `jobs.get()` until something arrives. A single `None` is consumed by whichever worker gets it first, and that worker exits. The other workers would still be waiting forever, so you need **one sentinel per worker**.

## Recap

- A **thread** is an independent path of execution that **shares memory** with the others. Start with `Thread(target=...)`, `start()`, and always `join()`.
- A **race condition** happens when threads **read, modify, then write** shared data without protection. `counter += 1` is three steps, so updates can be **lost**. The GIL does not prevent this.
- A **lock** (`with lock:`) turns a read-modify-write into a **critical section** that cannot be interleaved. Keep it short, always release it with `with`, and use `RLock` for re-entry.
- **Deadlock** happens when threads hold locks the others need. Acquire locks in a fixed order, use timeouts, or hold only one.
- Prefer **message passing**: `queue.Queue` is thread-safe, supports the **producer-consumer** pattern and **backpressure** (`maxsize`), and needs one stop sentinel per worker.
- `ThreadPoolExecutor` runs jobs on a few reused threads. `map` keeps input order, `as_completed` gives completion order, and `result()` re-raises worker errors.
- `Event`, `Semaphore`, `Condition`, `threading.local()` and daemon threads cover signalling, limiting, per-thread data and background chores.
