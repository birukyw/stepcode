# True Parallelism with multiprocessing

Threads cannot run Python code on several cores because of the GIL (lesson 3.4.1). The way around it is blunt and effective: start **several separate Python processes**. Each process is its own interpreter with its **own GIL and its own memory**, so the operating system can run them on different cores at the same time. This lesson covers the tools: `Process`, `Pool`, `ProcessPoolExecutor`, how data crosses between processes, and the traps that catch everybody.

> **Tip:** Processes need a real operating system, so every snippet in this lesson is marked **run it on your computer**, with a **Copy code** button. Save each one as a `.py` file and run `python3 file.py`. Every example keeps the `if __name__ == "__main__":` guard, which is **required**, and you will see why.

## Why separate processes work

Compare the two models:

| | Threads | Processes |
|---|---|---|
| Interpreter | one, shared | one **per process** |
| GIL | one, shared | one **per process** |
| Memory | shared (fast, risky) | **separate** (safe, slower to share) |
| Can use many cores for Python code | no | **yes** |
| Start-up cost | small | larger (a whole interpreter) |
| Data exchange | direct | must be **copied** (pickled) |

Separate memory is both the price and the protection. A process cannot corrupt another's variables, so there are **no race conditions on ordinary variables**. But to exchange data, you must send copies.

## The simplest start: Process

```python local
import multiprocessing as mp
import os

def worker(name):
    print(f"{name}: running in a separate process:", os.getpid() != PARENT_PID)

PARENT_PID = os.getpid()

if __name__ == "__main__":
    p = mp.Process(target=worker, args=("child",))
    p.start()
    p.join()
    print("exit code:", p.exitcode)
```

```text
child: running in a separate process: True
exit code: 0
```

The API deliberately mirrors `threading.Thread`: `start()` then `join()`. The child printed its own message from a different process, with its own process id. `exitcode` 0 means it finished normally.

## The `if __name__ == "__main__":` guard is mandatory

On many systems (always on Windows and macOS, and in Python 3.14 on Linux) a new process starts by **importing your script again** from the top. Without the guard, that import would start more processes, which import the script again, and so on. Python detects this and stops with an error. **Everything that starts processes must live under the guard.** Put function and class definitions at the top level, and the launching code under `if __name__ == "__main__":`.

## Pool: many jobs, a few workers

You rarely want one process per job. A **pool** starts a fixed number of workers (often one per core) and feeds them jobs:

```python local
from multiprocessing import Pool

def square(n):
    return n * n

def is_prime(n):
    if n < 2:
        return False
    return all(n % d for d in range(2, int(n ** 0.5) + 1))

if __name__ == "__main__":
    with Pool(processes=4) as pool:
        print(pool.map(square, range(8)))
        flags = pool.map(is_prime, [97, 100, 7919, 7917])
        print(flags)
        print(pool.starmap(pow, [(2, 5), (3, 3), (10, 2)]))
```

```text
[0, 1, 4, 9, 16, 25, 36, 49]
[True, False, True, False]
[32, 27, 100]
```

`pool.map(func, items)` splits the items across the workers, runs `func` on each, and returns the results **in the original order**. `starmap` unpacks tuples into arguments. Leaving the `with` block shuts the pool down cleanly.

## ProcessPoolExecutor: the same interface as threads

`concurrent.futures` offers a **uniform interface** for both kinds of pool. Switching between threads and processes is often a one-word change:

```python local
from concurrent.futures import ProcessPoolExecutor, as_completed

def heavy(n):
    total = 0
    for i in range(n):
        total += i * i
    return n, total

if __name__ == "__main__":
    sizes = [300_000, 100_000, 200_000]
    with ProcessPoolExecutor(max_workers=3) as pool:
        print([result for result in pool.map(heavy, sizes)])

        futures = [pool.submit(heavy, n) for n in sizes]
        done = sorted(f.result()[0] for f in as_completed(futures))
        print(done)

        failing = pool.submit(divmod, 1, 0)
        try:
            failing.result()
        except ZeroDivisionError:
            print("worker error re-raised in the parent")
```

```text
[(300000, 8999955000050000), (100000, 333328333350000), (200000, 2666646666700000)]
[100000, 200000, 300000]
worker error re-raised in the parent
```

An exception raised **inside a worker process** is shipped back and re-raised when you call `result()`, just as with threads. Prefer this interface for new code: it is simpler, and `submit`/`map`/`as_completed` mean the same thing for threads and processes.

## What can cross the process boundary: pickling

Processes cannot share objects directly. Arguments and results are **serialised with `pickle`**, sent through a pipe, and rebuilt on the other side. That has consequences:

```python local
import pickle
from multiprocessing import Pool

def top_level(x):
    return x + 1

if __name__ == "__main__":
    # Functions defined at module top level can be pickled (by name)
    print(len(pickle.dumps(top_level)) > 0)

    # A lambda has no importable name, so it cannot be pickled
    try:
        pickle.dumps(lambda x: x)
    except Exception as err:
        print("lambda:", type(err).__name__)

    with Pool(2) as pool:
        print(pool.map(top_level, [1, 2, 3]))
        try:
            pool.map(lambda x: x, [1, 2, 3])
        except Exception as err:
            print("pool.map with a lambda:", type(err).__name__)
```

```text
True
lambda: PicklingError
[2, 3, 4]
pool.map with a lambda: PicklingError
```

Rules to remember:

- **The function you send must be defined at the top level** of a module, not a lambda or an inner function.
- **Arguments and return values must be picklable.** Numbers, strings, lists, dicts, tuples and most classes are. Open files, database connections, locks and generators are not.
- **Data is copied.** Changing a list inside a worker does not change the parent's list.

```python local
from multiprocessing import Pool

def append_one(items):
    items.append(1)               # changes the worker's COPY
    return items

if __name__ == "__main__":
    original = [0]
    with Pool(1) as pool:
        returned = pool.apply(append_one, (original,))
    print(original, returned)
```

```text
[0] [0, 1]
```

The parent's list is untouched. To get data back, **return it**.

## The cost of copying: chunk your work

Because every call involves pickling and a round trip, **tiny jobs are slower in processes than in a plain loop**. Send **chunks** big enough that the computation dwarfs the transfer:

```python local
import time
from multiprocessing import Pool

def add_one(n):
    return n + 1

def add_one_chunk(chunk):
    return [n + 1 for n in chunk]

def split(items, parts):
    size, extra = divmod(len(items), parts)
    chunks, start = [], 0
    for i in range(parts):
        end = start + size + (1 if i < extra else 0)
        chunks.append(items[start:end])
        start = end
    return chunks

if __name__ == "__main__":
    data = list(range(20_000))
    with Pool(4) as pool:
        one_by_one = pool.map(add_one, data, chunksize=1)
        by_chunks = [x for part in pool.map(add_one_chunk, split(data, 4)) for x in part]
    print(one_by_one == by_chunks == [n + 1 for n in data])
    print([len(c) for c in split(list(range(10)), 3)])
```

```text
True
[4, 3, 3]
```

`pool.map` has a `chunksize` argument for exactly this reason, and a good default is many items per chunk. Doing the chunking yourself, as `split` does, makes the idea explicit: **few big messages beat many tiny ones.** (The sizes also show how to split 10 items across 3 workers as evenly as possible: 4, 3, 3.)

## Sharing data on purpose

Sometimes processes really do need shared state. There are a few safe channels:

```python local
from multiprocessing import Process, Queue, Value, Lock

def producer(q):
    for i in range(3):
        q.put(i * 10)
    q.put(None)                      # sentinel: no more items

def counter_worker(counter, lock):
    for _ in range(1000):
        with lock:
            counter.value += 1

if __name__ == "__main__":
    # a Queue moves data between processes (it pickles items for you)
    q = Queue()
    p = Process(target=producer, args=(q,))
    p.start()
    items = []
    while (item := q.get()) is not None:
        items.append(item)
    p.join()
    print(items)

    # a Value is shared memory with ONE number, and it needs a lock to be safe
    counter = Value("i", 0)
    lock = Lock()
    workers = [Process(target=counter_worker, args=(counter, lock)) for _ in range(4)]
    for w in workers:
        w.start()
    for w in workers:
        w.join()
    print(counter.value)
```

```text
[0, 10, 20]
4000
```

- `Queue` is the message-passing channel (the process version of `queue.Queue`). It is the preferred way.
- `Value` and `Array` are blocks of **shared memory** holding simple numbers. Unlike ordinary variables, they **can** suffer race conditions across processes, so protect read-modify-write with a lock, as lesson 3.4.2 taught.
- `multiprocessing.shared_memory` and managers (`Manager().dict()`) offer more, with more overhead. Reach for them only when message passing does not fit.

## Map-reduce: the pattern behind it all

Most parallel jobs have the same shape: **split** the data, **map** each part in its own process, **reduce** the partial results:

```python local
from multiprocessing import Pool
from collections import Counter

def count_words(lines):
    counts = Counter()
    for line in lines:
        counts.update(line.lower().split())
    return counts

def split(items, parts):
    size, extra = divmod(len(items), parts)
    chunks, start = [], 0
    for i in range(parts):
        end = start + size + (1 if i < extra else 0)
        chunks.append(items[start:end])
        start = end
    return chunks

if __name__ == "__main__":
    lines = ["the cat sat", "the dog sat", "a cat and a dog", "the end"] * 1000
    with Pool(4) as pool:
        partials = pool.map(count_words, split(lines, 4))        # map
    total = sum(partials, Counter())                              # reduce
    print(total.most_common(3))
    print(total == count_words(lines))
```

```text
[('the', 3000), ('cat', 2000), ('sat', 2000)]
True
```

Each process counted its own quarter of the lines, and the parent merged the four small counters. Only compact counters crossed the process boundary, not the data. That is the shape of Hadoop, Spark and every "big data" system, at small scale.

## How many workers?

For CPU-bound work, **one worker per core** is the usual ceiling. More just fight over the same cores:

```python local
import os
from multiprocessing import cpu_count

print(cpu_count() >= 1, (os.cpu_count() or 1) >= 1)
```

```text
True True
```

`cpu_count()` tells you how many cores the machine reports. `ProcessPoolExecutor()` and `Pool()` default to that number when you pass nothing.

## Start methods: fork, spawn and forkserver

How does a new process come to life? There are three **start methods**:

- **fork** (Linux traditionally): copy the parent's whole memory. Fast, but unsafe if the parent has threads or open resources.
- **spawn** (the only one on Windows, and default on macOS): start a fresh interpreter and import your module. Safe and portable, slower to start.
- **forkserver** (the default on Linux since Python 3.14): a small clean server process forks the workers.

Write code that works under **spawn**, and it works everywhere. That means: top-level functions, picklable arguments, and the `__main__` guard. You can choose explicitly with `mp.set_start_method("spawn")` (once, inside the guard) or `mp.get_context("spawn")`.

## Processes versus threads: a summary

| You have... | Use |
|---|---|
| CPU-heavy Python, independent chunks | `ProcessPoolExecutor` / `Pool` |
| Waiting on network and disk | threads or asyncio |
| Heavy numerics | NumPy first (it already uses fast C code) |
| Tiny tasks | neither: a plain loop wins |
| Lots of shared mutable state | rethink the design, or use threads with locks |

## Common mistakes

- **Missing the `__main__` guard,** causing an error or a storm of processes.
- **Passing a lambda or an inner function** to a pool. Define workers at the top level.
- **Expecting changes to arguments to be visible** in the parent. Return results.
- **Sending huge objects** to every task. Pass small descriptions (a file name, a range) and let each worker load its own data.
- **Using processes for tiny jobs,** where startup and pickling cost more than the work.
- **Sharing a `Value` without a lock.**
- **Forgetting that print output from workers is not ordered.** Collect results and print in the parent.

```python local
from concurrent.futures import ProcessPoolExecutor

def chunk_sum(bounds):
    lo, hi = bounds
    return sum(i * i for i in range(lo, hi))

def parallel_sum_of_squares(n, workers=4):
    step = -(-n // workers)                       # ceiling division
    bounds = [(lo, min(lo + step, n)) for lo in range(0, n, step)]
    with ProcessPoolExecutor(max_workers=workers) as pool:
        return sum(pool.map(chunk_sum, bounds))

def square(x):
    return x * x

def parallel_map(func, items, workers=3):
    with ProcessPoolExecutor(max_workers=workers) as pool:
        return list(pool.map(func, items))

if __name__ == "__main__":
    print(parallel_sum_of_squares(100_000) == sum(i * i for i in range(100_000)))   # True
    print(parallel_map(square, [1, 2, 3, 4]))                                       # [1, 4, 9, 16]
```

Each worker process has its **own copy** of the module and its own `results` list. Appending in a worker changes that process's list, which is discarded when the process ends. The parent's list is never touched. Workers must **return** their results.

```python local
from multiprocessing import Process, Queue

def worker(inbox, outbox):
    while (n := inbox.get()) is not None:
        outbox.put(n * n)

if __name__ == "__main__":
    inbox, outbox = Queue(), Queue()
    procs = [Process(target=worker, args=(inbox, outbox)) for _ in range(2)]
    for p in procs:
        p.start()
    for n in range(6):
        inbox.put(n)
    for _ in procs:
        inbox.put(None)                           # one sentinel per worker
    results = sorted(outbox.get() for _ in range(6))
    for p in procs:
        p.join()
    print(results)                                # [0, 1, 4, 9, 16, 25]
```

## Recap

- Each **process** has its own interpreter, its own GIL and its own memory, so processes run Python code on **several cores at once**. Memory is not shared, so ordinary variables cannot be corrupted by another process.
- Use `ProcessPoolExecutor` (or `multiprocessing.Pool`) to run jobs on a few worker processes. `map` returns results in order, `submit`/`as_completed` give futures, and worker errors are re-raised in the parent.
- Arguments and results are **pickled**: workers must be **top-level functions** (no lambdas), arguments must be picklable, and data is **copied**, so you must return results.
- Process start-up and pickling cost real time: send **big chunks**, not tiny jobs. The **map-reduce** pattern (split, map in processes, merge small results) is the standard shape.
- Share state through a `Queue`, or `Value`/`Array` with a lock, only when you must.
- Always keep the `if __name__ == "__main__":` guard, and write for the **spawn** start method so the code works on every system. Use about one worker per core for CPU-bound work.
