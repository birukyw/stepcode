# Divide & Conquer Sorting: Merge, Quick & Timsort

Sorting is where many people first meet a real algorithmic trade-off. The slow sorts are easy to write and too slow past a few thousand items. The fast ones use one big idea, **divide and conquer**: split the problem, solve the pieces, combine the answers. This lesson builds merge sort and quicksort from scratch, then shows what Python actually uses.

## The slow baseline

Insertion sort walks through the list and slides each item left until it sits in the right place:

```python
def insertion_sort(items):
    items = list(items)
    moves = 0
    for i in range(1, len(items)):
        current = items[i]
        j = i - 1
        while j >= 0 and items[j] > current:
            items[j + 1] = items[j]
            j -= 1
            moves += 1
        items[j + 1] = current
    return items, moves

print(insertion_sort([5, 2, 4, 6, 1, 3]))
print(insertion_sort(list(range(10, 0, -1)))[1])
```

```text
([1, 2, 3, 4, 5, 6], 9)
45
```

A reversed list causes the most work: roughly n²/2 moves, so **O(n²)**. Ten thousand items means fifty million moves.

## Merge sort

The idea: a list of one item is already sorted. Split a list in half, sort each half **recursively**, then **merge** the two sorted halves, which is a cheap linear pass.

```python
def merge(left, right):
    out = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            out.append(left[i])
            i += 1
        else:
            out.append(right[j])
            j += 1
    out.extend(left[i:])
    out.extend(right[j:])
    return out

def merge_sort(items):
    if len(items) <= 1:
        return items
    mid = len(items) // 2
    return merge(merge_sort(items[:mid]), merge_sort(items[mid:]))

print(merge([1, 4, 9], [2, 3, 10]))
print(merge_sort([38, 27, 43, 3, 9, 82, 10]))
```

```text
[1, 2, 3, 4, 9, 10]
[3, 9, 10, 27, 38, 43, 82]
```

### Why it is O(n log n)

Halving a list of `n` items takes `log₂ n` levels. At every level the merges together touch each item once, so each level costs O(n). Total: **n × log n**. A million items needs about 20 million steps, not 500 billion.

Two properties matter in practice:

- It is **stable**: equal items keep their original order, thanks to `<=` in the merge. That matters when you sort records by one field after another.
- It needs **O(n) extra memory** for the merged lists.

## Quicksort

Quicksort divides differently. Pick a **pivot**, partition the items into those smaller than, equal to, and larger than it, then sort the outer two groups recursively. There is no merge step: after partitioning, the pivot is already in its final place.

```python
import random

def quicksort(items):
    if len(items) <= 1:
        return items
    pivot = random.choice(items)
    smaller = [x for x in items if x < pivot]
    equal = [x for x in items if x == pivot]
    larger = [x for x in items if x > pivot]
    return quicksort(smaller) + equal + quicksort(larger)

print(quicksort([38, 27, 43, 3, 9, 82, 10, 27]))
```

```text
[3, 9, 10, 27, 27, 38, 43, 82]
```

On average each partition splits the list reasonably evenly, giving **O(n log n)**. The worst case happens when the pivot is always the smallest or largest item (picking the first item of an already sorted list is the classic trap): the recursion goes n levels deep and the cost becomes **O(n²)**. A **random pivot** makes that vanishingly unlikely.

The classic in-place version swaps items within the same array and needs only O(log n) extra memory, which is why quicksort is the usual choice in compiled languages.

## Counting inversions: what merge sort can teach

An **inversion** is a pair that is out of order: `a[i] > a[j]` with `i < j`. A sorted list has none, a reversed list has the most. Counting them by brute force is O(n²). During a merge, though, whenever an item from the **right** half is placed before items still waiting in the left half, each of those waiting items forms an inversion with it:

```python
def sort_count(items):
    if len(items) <= 1:
        return items, 0
    mid = len(items) // 2
    left, a = sort_count(items[:mid])
    right, b = sort_count(items[mid:])
    out, cross = [], 0
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            out.append(left[i])
            i += 1
        else:
            out.append(right[j])
            cross += len(left) - i      # everything left in `left` is bigger
            j += 1
    out.extend(left[i:])
    out.extend(right[j:])
    return out, a + b + cross

print(sort_count([2, 4, 1, 3, 5]))
print(sort_count([5, 4, 3, 2, 1])[1])
```

```text
([1, 2, 3, 4, 5], 3)
10
```

Divide and conquer often hides extra information inside the "combine" step.

## What Python really uses: Timsort

`sorted()` and `list.sort()` use **Timsort**, a hybrid of merge sort and insertion sort, built for real data. It looks for existing sorted stretches called **runs**, extends short ones with insertion sort, then merges runs. Two results follow:

- It is **O(n log n)** in the worst case and **O(n)** on data that is already (or nearly) sorted.
- It is **stable**.

```python
import time, random

def measure(label, data):
    start = time.perf_counter()
    sorted(data)
    return label, time.perf_counter() - start < 0.5

n = 300_000
shuffled = random.sample(range(n), n)
print(measure("shuffled", shuffled))
print(measure("already sorted", list(range(n))))
```

```text
('shuffled', True)
('already sorted', True)
```

Stability lets you sort in passes. Sort by the secondary key first, then by the primary key:

```python
people = [("Ada", 36), ("Linus", 28), ("Grace", 36), ("Guido", 28)]
people.sort(key=lambda p: p[0])      # by name
people.sort(key=lambda p: p[1])      # then by age: names stay ordered within an age
print(people)
```

```text
[('Guido', 28), ('Linus', 28), ('Ada', 36), ('Grace', 36)]
```

## Which sort when?

| Situation | Choice |
|---|---|
| In Python | `sorted()` / `list.sort()`, always |
| Need to explain or modify the algorithm | merge sort (predictable) |
| Compiled language, memory tight | in-place quicksort with a random pivot |
| Small or nearly sorted data | insertion sort is competitive |
| Integers in a small range | counting sort, O(n + k), no comparisons |

No sort that works by comparing items can beat **O(n log n)** in general. That is a proven lower bound.

## Common mistakes

- **Slicing in recursion without noticing the cost.** `items[:mid]` copies. It is fine here, but it adds memory.
- **Using `<` instead of `<=` in the merge.** Still sorts, but it breaks stability.
- **First-item pivot on sorted input.** It triggers quicksort's O(n²) worst case.
- **Writing your own sort in production.** Use the built-in. Write your own to learn.
- **Forgetting the base case.** `len(items) <= 1` stops the recursion.

import random

def kth_smallest(items, k):          # k starts at 1
    pivot = random.choice(items)
    smaller = [x for x in items if x < pivot]
    equal = [x for x in items if x == pivot]
    larger = [x for x in items if x > pivot]
    if k <= len(smaller):
        return kth_smallest(smaller, k)
    if k <= len(smaller) + len(equal):
        return pivot
    return kth_smallest(larger, k - len(smaller) - len(equal))

## Recap

- Divide and conquer: split, solve the pieces recursively, combine.
- **Merge sort** is always O(n log n), stable, and uses O(n) extra memory. The work happens in the merge.
- **Quicksort** partitions around a pivot: O(n log n) on average, O(n²) with consistently bad pivots, so choose them randomly.
- Counting inversions shows how the combine step can carry extra information.
- Python's **Timsort** is stable, O(n log n) worst case and close to O(n) on nearly sorted data. Use `sorted` and `key=`, and sort in passes thanks to stability.
