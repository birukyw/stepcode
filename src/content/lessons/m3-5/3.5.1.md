# Static Type Systems & Structural Protocols

Python is **dynamically typed**: a variable can hold anything, and mistakes like `"5" + 3` only show up when that line actually runs, possibly months later in production. **Type hints** let you write down what you *intend* (`age: int`, `names: list[str]`) so that a **static type checker** can read your code **without running it** and catch whole families of bugs: wrong arguments, `None` where a value was expected, misspelled attributes, forgotten return values. Large projects use them for another reason too: they are the best documentation that can never go stale. This lesson teaches how to read and write hints, what they do and do not do at run time, and the feature that makes them feel Pythonic: **structural protocols**.

## Hints do not change how code runs

This surprises everyone: Python **ignores** annotations when running.

```python
def double(n: int) -> int:
    return n * 2

print(double(21))
print(double("ab"))        # the hint says int, but Python does not check
print(double([1, 2]))
```

```text
42
abab
[1, 2, 1, 2]
```

All three calls ran. The hints are **metadata**, not rules. They are checked by **separate tools** you run before your code, such as `mypy` or `pyright`, and shown by your editor as red squiggles:

```bash
pip install mypy
mypy my_program.py
```

```text
my_program.py:4: error: Argument 1 to "double" has incompatible type "str"; expected "int"  [arg-type]
my_program.py:5: error: Argument 1 to "double" has incompatible type "list[int]"; expected "int"  [arg-type]
Found 2 errors in 1 file (checked 1 source file)
```

The checker found both mistakes **without running a line**. That is the payoff.

## The basic syntax

```python
name: str = "Ada"                       # a variable annotation
scores: list[int] = [90, 85]
lookup: dict[str, float] = {"pi": 3.14}
pair: tuple[str, int] = ("Ada", 36)
anything_goes: list[object] = [1, "a", None]

def greet(user: str, times: int = 1) -> str:
    return (f"hello {user} ") * times

def log(message: str) -> None:          # returns nothing
    print(message)

print(greet("Ada", 2).strip())
print(greet.__annotations__)
```

```text
hello Ada hello Ada
{'user': <class 'str'>, 'times': <class 'int'>, 'return': <class 'str'>}
```

- `name: type` after a parameter, `-> type` after the parentheses for the return value.
- **Built-in generics** since Python 3.9: `list[int]`, `dict[str, int]`, `set[str]`, `tuple[int, str]`, and `tuple[int, ...]` for a variable-length tuple of ints.
- `-> None` means the function returns nothing useful.

## None and unions

The most valuable thing a checker does is notice **`None` where you assumed a value**. Python 3.10+ writes "either-or" with `|`:

```python
def find_user(users: dict[str, int], name: str) -> int | None:
    return users.get(name)

def describe(user_id: int | None) -> str:
    if user_id is None:
        return "no such user"
    return f"user #{user_id}"         # a checker knows user_id is an int here

users = {"ada": 1}
print(describe(find_user(users, "ada")), "|", describe(find_user(users, "bob")))
```

```text
user #1 | no such user
```

`int | None` (also spelled `Optional[int]`) is the type of "an int or nothing". After the `is None` check, the checker **narrows** the type to a plain `int` in the rest of the function. Forget the check and it complains that you used a possibly-`None` value. That single rule prevents a huge share of `AttributeError: 'NoneType' ...` crashes.

`str | int` means "either". `Any` means "no checking at all" (an escape hatch), and `object` means "any object, but you can only use what every object can do".

## Abstract parameter types, concrete return types

A good rule for function signatures: **accept the most general type that works, return a specific one.** If a function only loops over its input, say so:

```python
from collections.abc import Iterable, Sequence, Mapping, Callable

def total(numbers: Iterable[float]) -> float:           # accepts lists, tuples, sets, generators...
    return sum(numbers)

def last(items: Sequence[str]) -> str:                   # needs indexing, so a Sequence
    return items[-1]

def apply(func: Callable[[int], int], values: list[int]) -> list[int]:
    return [func(v) for v in values]

print(total([1, 2.5]), total(x for x in range(4)), last(("a", "b")))
print(apply(lambda n: n * n, [1, 2, 3]))
```

```text
3.5 6 b
[1, 4, 9]
```

`Iterable[float]` means "anything you can loop over", so callers can pass a list, a set or a generator. `Callable[[int], int]` is a function taking an `int` and returning an `int`. Narrow parameter types such as `list[float]` would needlessly reject a tuple.

## Generics: types that depend on other types

How do you type a function like `first(items)` that returns **whatever kind of item** the list holds? A **type variable** says "the same type here and there":

```python
from typing import TypeVar
from collections.abc import Sequence

T = TypeVar("T")

def first(items: Sequence[T]) -> T:
    return items[0]

def pair_up(a: T, b: T) -> list[T]:
    return [a, b]

print(first([10, 20]), first("hello"), first([(1, 2)]))
print(pair_up("x", "y"))
```

```text
10 h (1, 2)
['x', 'y']
```

If you call `first([10, 20])`, a checker infers `T` is `int`, so the result is an `int`. If you call it with a list of strings, the result is a `str`. One definition, correct types everywhere. A generic **class** works the same way:

```python
from typing import Generic, TypeVar

T = TypeVar("T")

class Stack(Generic[T]):
    def __init__(self) -> None:
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        return self._items.pop()

numbers: Stack[int] = Stack()
numbers.push(1)
numbers.push(2)
print(numbers.pop())
```

```text
2
```

(`Stack[int]` tells the checker that `push("text")` is a bug.) Python 3.12 added a lighter syntax for the same idea, `def first[T](items: Sequence[T]) -> T:` and `class Stack[T]:`, with no `TypeVar` import needed. The meaning is identical.

## Reading hints at run time

Annotations are stored on the function, and tools such as FastAPI and pydantic use them to **do things** at run time: validate input, generate documentation. You can read them too:

```python
import typing

def make_user(name: str, age: int, tags: list[str] | None = None) -> dict:
    return {"name": name, "age": age, "tags": tags or []}

hints = typing.get_type_hints(make_user)
print(hints["name"], hints["age"], hints["return"])
print(typing.get_args(hints["tags"]))
```

```text
<class 'str'> <class 'int'> <class 'dict'>
(list[str], <class 'NoneType'>)
```

Here is the idea in miniature, a **runtime checker** driven by the hints (a tiny cousin of what pydantic does):

```python
import typing

def enforce(func):
    hints = typing.get_type_hints(func)
    names = list(func.__code__.co_varnames[: func.__code__.co_argcount])

    def wrapper(*args):
        for name, value in zip(names, args):
            expected = hints.get(name)
            if expected in (int, str, float, bool) and not isinstance(value, expected):
                raise TypeError(f"{name} must be {expected.__name__}, got {type(value).__name__}")
        return func(*args)
    return wrapper

@enforce
def double(n: int) -> int:
    return n * 2

print(double(4))
try:
    double("ab")
except TypeError as err:
    print(err)
```

```text
8
n must be int, got str
```

This combines three lessons: a decorator (3.1.5), reflection on the function's code, and hints used as data.

## Structural typing: Protocols

How should a type checker handle duck typing? "Anything with a `.read()` method" is not a class, so you cannot name it with inheritance. A **Protocol** describes **shape** instead of ancestry: *any class that has these methods counts, no inheritance needed.* This is called **structural typing**, in contrast to the **nominal typing** of normal classes and ABCs (lesson 3.2.4), where a class must explicitly declare its parent.

```python
from typing import Protocol

class Speaker(Protocol):
    def speak(self) -> str: ...

class Dog:
    def speak(self) -> str:
        return "Woof"

class Robot:
    def speak(self) -> str:
        return "Beep"

class Rock:
    pass

def announce(thing: Speaker) -> str:
    return thing.speak()

print(announce(Dog()), announce(Robot()))
# announce(Rock()) is rejected by a type checker: Rock has no speak method
```

```text
Woof Beep
```

`Dog` and `Robot` never mention `Speaker`. They satisfy it simply by having a matching `speak`. A checker accepts them, and rejects `Rock`. You get the flexibility of duck typing with the safety of checking. With `@runtime_checkable` the same protocol also works with `isinstance`:

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class SupportsClose(Protocol):
    def close(self) -> None: ...

class Connection:
    def close(self) -> None:
        print("closed")

print(isinstance(Connection(), SupportsClose), isinstance(42, SupportsClose))
```

```text
True False
```

Protocols are how the standard library types things: `Iterable` is a protocol (anything with `__iter__`), as are `Sized`, `Hashable` and `SupportsInt`. Prefer a Protocol whenever you want to accept "anything that can do X".

## Typed dictionaries and literals

JSON-shaped data is usually a dictionary with known keys. `TypedDict` describes it. `Literal` limits a value to specific constants:

```python
from typing import TypedDict, Literal

class User(TypedDict):
    name: str
    age: int
    role: Literal["admin", "user"]

def label(u: User) -> str:
    return f"{u['name']} ({u['role']})"

ada: User = {"name": "Ada", "age": 36, "role": "admin"}
print(label(ada))
print(User.__annotations__["role"])
print(type(ada).__name__)
```

```text
Ada (admin)
typing.Literal['admin', 'user']
dict
```

At run time a `TypedDict` is just a `dict`. The checker is what verifies that `{"name": "Ada"}` is missing `age` and that `role="boss"` is not allowed. For validation at run time, you would write checks or use a library such as pydantic.

## Typed data classes and other helpers

```python
from dataclasses import dataclass
from typing import Final, NewType, cast

@dataclass
class Point:
    x: float
    y: float

UserId = NewType("UserId", int)          # a distinct type that is an int at run time

def load(user_id: UserId) -> str:
    return f"loading user {user_id}"

MAX_RETRIES: Final = 3                   # a checker flags any reassignment

print(Point(1, 2), load(UserId(7)), MAX_RETRIES)
value = cast(int, "5")                   # tells the checker "trust me"; does nothing at run time
print(value, type(value).__name__)
```

```text
Point(x=1, y=2) loading user 7 3
5 str
```

- `NewType` stops you from passing an order id where a user id is expected, though both are plain ints underneath.
- `Final` marks constants.
- `cast` overrides the checker without changing the value. Use it rarely, and only when you know something the checker cannot.

## Narrowing and `TYPE_CHECKING`

Checkers follow your `if` statements. After `isinstance` or `is None` tests, they know more about a variable:

```python
def normalise(value: int | str | list[int]) -> str:
    if isinstance(value, int):
        return str(value + 1)                 # an int here
    if isinstance(value, str):
        return value.upper()                  # a str here
    return ",".join(str(v) for v in value)   # only a list[int] is left

print(normalise(1), normalise("a"), normalise([1, 2]))
```

```text
2 A 1,2
```

To avoid circular imports used only for hints, wrap them in `if TYPE_CHECKING:`. That code runs for the checker and is skipped at run time:

```python
from __future__ import annotations
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from decimal import Decimal              # imported only for the type checker

def price(cents: int) -> Decimal:
    from decimal import Decimal
    return Decimal(cents) / 100

print(price(1999))
```

```text
19.99
```

## Adopting types gradually

You do not need to annotate everything. **Gradual typing** lets you start with the public functions and the code where bugs hurt most, and checkers treat unannotated code as `Any`. Practical advice:

1. Annotate **function signatures** first. Locals are inferred.
2. Run the checker in your editor and in continuous integration.
3. Fix errors as they appear, and use `# type: ignore[code]` only with a comment saying why.
4. Aim to **tighten over time**: fewer `Any`s, stricter checker settings.

## Common mistakes

- **Believing hints are enforced at run time.** They are not, unless a library you use (pydantic, FastAPI) checks them.
- **Annotating parameters too narrowly** (`list[int]` when `Iterable[int]` would do).
- **Returning `None` on some paths** without declaring `| None`, so callers are never warned.
- **Using `Any` everywhere,** which silently turns checking off.
- **Mutable defaults in annotations,** such as `def f(x: list[int] = [])`: the bug from lesson 1.5.4 survives typing.
- **Over-using `cast` and `# type: ignore`,** hiding real errors.
- **Confusing `Protocol` with `ABC`:** protocols are about shape (no inheritance), ABCs about declared ancestry.

## Practice

2. Write `find_first(items: Sequence[T], predicate: Callable[[T], bool]) -> T | None` and test it.
3. Define a `Protocol` called `HasLength` with `__len__`, and a function `longest(items: list[HasLength])`.
4. Print the return annotation of a function you wrote, using `typing.get_type_hints`.

+++ Solutions
```python
from collections.abc import Sequence, Callable
from typing import TypeVar, Protocol

def average(numbers: Sequence[float]) -> float:
    return sum(numbers) / len(numbers)     # len() needs a Sequence: a generator has no length

T = TypeVar("T")

def find_first(items: Sequence[T], predicate: Callable[[T], bool]) -> T | None:
    for item in items:
        if predicate(item):
            return item
    return None

class HasLength(Protocol):
    def __len__(self) -> int: ...

def longest(items: list[HasLength]) -> HasLength:
    return max(items, key=len)

print(average([1, 2, 3]), find_first([1, 4, 9], lambda n: n > 3), find_first("abc", str.isdigit))   # 2.0 4 None
print(longest(["aa", [1, 2, 3], (1,)]))   # [1, 2, 3]
```
+++

## Recap

- **Type hints** (`name: str`, `-> int`, `list[int]`, `int | None`) describe your intent. Python **ignores them at run time**. A **static checker** (`mypy`, `pyright`, your editor) reads them to find bugs without running the code.
- The biggest wins: catching `None` misuse (`X | None` forces the check, and `isinstance`/`is None` **narrow** types), wrong arguments, and missing returns.
- **Accept abstract types** (`Iterable`, `Sequence`, `Mapping`, `Callable`) and **return concrete ones**.
- **Generics** (`TypeVar`, `Generic[T]`, or the 3.12 `def f[T]` syntax) tie types together.
- A **`Protocol`** describes **shape**, so any class with the right methods qualifies without inheriting (structural typing). `@runtime_checkable` allows `isinstance`.
- `TypedDict`, `Literal`, `Final`, `NewType` and `cast` model JSON-like data, fixed choices, constants and distinct ids. Hints are readable at run time via `get_type_hints`, which is how frameworks build on them.
- Adopt types **gradually**: public signatures first, run the checker in CI, and avoid `Any` and `# type: ignore` where you can.
