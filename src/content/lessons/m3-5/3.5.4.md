# Packaging, Virtual Environments & Architecture

A single file is a script. A project with a dozen files, some third-party libraries, tests and a command that users can install is **software**, and software needs a **structure**. This lesson is about the part of programming that has nothing to do with algorithms and everything to do with whether other people (and you, in six months) can **understand, run, test and install** your work: modules and packages, how imports find things, how a project is laid out, how it declares its dependencies, how it is isolated and shipped, and how to arrange the code **inside** so that it can grow without turning into spaghetti.

> **Tip:** Lesson 1.7.7 showed how to run scripts and use `pip` and virtual environments on your computer. The commands here are typed in a terminal, so they are shown as plain code (not runnable in the editor). The Python examples that **build a package on the fly** do run here.

## Modules and packages

- A **module** is one Python file. `import geometry` loads `geometry.py`.
- A **package** is a **folder of modules** with an `__init__.py` file. It lets you group related code under one name.

```tree
shapes/
    __init__.py
    circle.py
    rectangle.py
```

With that layout, `import shapes.circle` or `from shapes import rectangle` works. The `__init__.py` runs when the package is first imported, and its main job is to decide **what the package exposes**.

You can build such a package, import it and inspect it, all in one script. This is the machinery behind every `import`:

```python
import importlib
import sys
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory() as root:
    pkg = Path(root) / "shapes"
    pkg.mkdir()
    (pkg / "circle.py").write_text("import math\n\ndef area(r):\n    return round(math.pi * r * r, 2)\n")
    (pkg / "rectangle.py").write_text("def area(w, h):\n    return w * h\n")
    (pkg / "__init__.py").write_text(
        "from .circle import area as circle_area\n"
        "from .rectangle import area as rectangle_area\n"
        "__all__ = ['circle_area', 'rectangle_area']\n"
    )

    sys.path.insert(0, root)            # make the folder importable
    importlib.invalidate_caches()
    try:
        import shapes
        print(shapes.circle_area(2), shapes.rectangle_area(3, 4))
        print(shapes.__all__)
        print(sorted(name for name in sys.modules if name.startswith("shapes")))
    finally:
        sys.path.remove(root)
        for name in [n for n in sys.modules if n.startswith("shapes")]:
            del sys.modules[name]
```

```text
12.57 12
['circle_area', 'rectangle_area']
['shapes', 'shapes.circle', 'shapes.rectangle']
```

The `__init__.py` imported the real functions and gave them friendly names, so users write `shapes.circle_area(2)` and never need to know which file it lives in. `__all__` lists what `from shapes import *` should expose (and documents the public surface).

## How Python finds what you import

When you write `import something`, Python:

1. Checks `sys.modules`, a cache of everything **already imported**. A module is loaded **once**, no matter how many files import it.
2. If absent, it searches the folders in **`sys.path`**, in order: the script's own folder, standard-library folders, then installed packages (`site-packages`).
3. It runs the module's code once, and stores the module object in `sys.modules`.

```python
import sys

print(type(sys.path).__name__, len(sys.path) > 0)
print("json" in sys.modules, "this_never_imported" in sys.modules)
import json
print("json" in sys.modules, sys.modules["json"] is json)
```

```text
list True
False False
True True
```

This explains the bug from lesson 1.7.4: if you create your own file called `random.py`, the script folder is searched **first**, so `import random` finds **yours** instead of the standard one.

## Absolute and relative imports

Inside a package you can name modules by their full path (**absolute**) or relative to the current module (**relative**):

```tree
shop/
    __init__.py
    models.py
    pricing.py
    reports/
        __init__.py
        summary.py
```

```py
# shop/pricing.py
from shop.models import Product        # absolute: always works, easy to read
from .models import Product            # relative: the same, from a sibling module
from ..models import Product           # relative: one package up (from inside shop/reports/)
```

Prefer **absolute imports** for clarity. Use relative imports within a package so it survives being renamed. A relative import only works inside a package, not in a script run directly.

### Circular imports

If `a.py` imports `b.py` and `b.py` imports `a.py`, one of them sees a half-built module and fails. The fix is almost always **design**: move the shared code into a third module that both import, or import inside the function that needs it.

```python
import importlib
import sys
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory() as root:
    (Path(root) / "cyc_a.py").write_text("import cyc_b\n\ndef a_value():\n    return 'a'\n")
    (Path(root) / "cyc_b.py").write_text("from cyc_a import a_value\n\ndef b_value():\n    return 'b'\n")
    sys.path.insert(0, root)
    importlib.invalidate_caches()
    try:
        import cyc_a
    except ImportError as err:
        print("circular import:", type(err).__name__)
    finally:
        sys.path.remove(root)
        for name in ("cyc_a", "cyc_b"):
            sys.modules.pop(name, None)
```

```text
circular import: ImportError
```

`cyc_a` started importing `cyc_b`, which tried to take `a_value` from the **half-initialised** `cyc_a`, which does not have it yet. Break the cycle by moving shared pieces elsewhere.

## Running modules: `python -m` and `__main__`

Every module has a `__name__`. When it is run **directly** it is `"__main__"`, and when imported it is its module name. That is why `if __name__ == "__main__":` separates "run me" from "import me" (lesson 1.7.4).

For a package, add a `__main__.py` and users can run the whole package:

```bash
python3 -m shop            # runs shop/__main__.py
python3 -m pytest          # runs the installed pytest package as a program
python3 -m venv .venv      # the venv module as a command
python3 -m pip install x   # the safest way to call pip: it always matches this Python
```

`python3 -m name` is preferred over running files by path, because Python puts the **current folder** on the path and imports resolve the way they will when installed.

## A real project layout

Here is a layout used by thousands of projects:

```tree
my_project/
├── pyproject.toml          # name, version, dependencies, tool settings
├── README.md
├── LICENSE
├── src/
│   └── shopkit/            # the importable package
│       ├── __init__.py
│       ├── models.py
│       ├── pricing.py
│       └── cli.py
├── tests/
│   ├── test_models.py
│   └── test_pricing.py
└── .gitignore              # includes .venv/, __pycache__/, dist/
```

Why a `src/` folder? It stops tests from accidentally importing the **local source files** instead of the **installed package**, which catches packaging mistakes (missing files, wrong imports) before your users do. Tests live **outside** the package so they are not shipped.

## pyproject.toml: describing your project

`pyproject.toml` is the single standard file that says what your project is:

```toml
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "shopkit"
version = "0.3.0"
description = "Small helpers for shop pricing."
readme = "README.md"
requires-python = ">=3.10"
dependencies = [
    "requests>=2.31,<3",
]

[project.optional-dependencies]
dev = ["pytest>=8", "mypy"]

[project.scripts]
shopkit = "shopkit.cli:main"      # installs a "shopkit" command that calls main()

[tool.pytest.ini_options]
testpaths = ["tests"]
```

You can read the file with the standard library to see it is just data (the `tomllib` module, new in 3.11):

```python
import tomllib

text = """
[project]
name = "shopkit"
version = "0.3.0"
dependencies = ["requests>=2.31,<3"]

[project.scripts]
shopkit = "shopkit.cli:main"
"""
data = tomllib.loads(text)
print(data["project"]["name"], data["project"]["version"])
print(data["project"]["dependencies"])
print(data["project"]["scripts"])
```

```text
shopkit 0.3.0
['requests>=2.31,<3']
{'shopkit': 'shopkit.cli:main'}
```

The key parts: `dependencies` (what your code needs to run), `optional-dependencies` (extras such as development tools), `requires-python` (which Python versions work), and `[project.scripts]` (the **entry point**: it turns the function `shopkit.cli:main` into a command that pip installs for users).

## Dependencies and versions

Libraries change. Version **specifiers** say which versions you accept:

| Specifier | Meaning |
|---|---|
| `requests==2.31.0` | exactly this version |
| `requests>=2.31` | this version or newer |
| `requests>=2.31,<3` | newer, but not the next major version (it may break you) |
| `requests~=2.31` | compatible release: `>=2.31, <3.0` |

Most projects follow **semantic versioning**: `MAJOR.MINOR.PATCH`. A patch (`2.31.1`) fixes bugs, a minor (`2.32.0`) adds features compatibly, and a major (`3.0.0`) may **break** your code. A tiny helper shows the rule:

```python
def parse(version):
    return tuple(int(part) for part in version.split("."))

def compatible(installed, required_min, next_major):
    return parse(required_min) <= parse(installed) < parse(next_major)

print(compatible("2.31.5", "2.31.0", "3.0.0"))
print(compatible("3.0.0", "2.31.0", "3.0.0"))
print(parse("1.10.0") > parse("1.9.0"), "1.10.0" > "1.9.0")
```

```text
True
False
True False
```

The last line is the classic trap: compared as **text**, `"1.10.0"` is smaller than `"1.9.0"`, but compared as numbers it is larger. Version parsing must compare numbers.

Two kinds of dependency files serve different needs:

- **Abstract** requirements (`pyproject.toml`): "needs `requests` 2.31 or later". This is what a **library** declares.
- **Locked** requirements (`pip freeze > requirements.txt`, or tools like `pip-tools`, `uv` or `poetry`): the **exact** versions that worked. An **application** commits these so that every machine installs the same thing.

## Virtual environments, once more

An isolated environment per project stops dependency clashes (lesson 1.7.7):

```bash
python3 -m venv .venv                    # create it
source .venv/bin/activate                # activate (Windows: .venv\Scripts\activate)
pip install -e ".[dev]"                  # install YOUR project in editable mode, plus dev tools
pytest                                   # run the tests against the installed package
deactivate
```

`pip install -e .` (editable install) links your source folder into the environment, so edits take effect immediately and `import shopkit` works anywhere inside it. That is the standard workflow while developing.

Building and sharing a package:

```bash
python3 -m pip install build
python3 -m build                        # creates dist/shopkit-0.3.0.tar.gz and a .whl wheel
python3 -m pip install twine
twine upload dist/*                     # publish to PyPI (after you test on TestPyPI)
```

A **wheel** (`.whl`) is the ready-to-install package format: users get it with `pip install shopkit`.

## Configuration: environment variables

Settings that change between your laptop, the test server and production (database address, API keys) must **not** be written into the code. Read them from **environment variables**, which are set outside the program:

```python
import os

def load_config(env=None):
    env = os.environ if env is None else env
    return {
        "debug": env.get("APP_DEBUG", "0") == "1",
        "port": int(env.get("APP_PORT", "8000")),
        "database_url": env.get("DATABASE_URL", "sqlite:///dev.db"),
    }

print(load_config({}))
print(load_config({"APP_DEBUG": "1", "APP_PORT": "9000"}))
```

```text
{'debug': False, 'port': 8000, 'database_url': 'sqlite:///dev.db'}
{'debug': True, 'port': 9000, 'database_url': 'sqlite:///dev.db'}
```

Notice `load_config` takes the environment as a **parameter** (dependency injection again), so tests pass a plain dictionary. Secrets (passwords, tokens) belong in environment variables or a secrets manager, **never in git**.

## Architecture: layers and the direction of dependencies

How should the code **inside** your package be arranged? A durable idea: separate **what the business does** from **how it talks to the outside world**, and make dependencies point **inward**:

```tree
   +-----------------------------------------+
   |  Interfaces: CLI, web API, scheduled job |   (outer: things that change often)
   +-----------------------------------------+
   |  Services: use cases, workflows          |
   +-----------------------------------------+
   |  Domain: models and business rules       |   (inner: pure Python, no I/O)
   +-----------------------------------------+
       Adapters (database, email, files) plug in from the side
```

The domain (rules like "an order total is the sum of its lines") knows nothing about databases or web frameworks. It is plain Python that is trivial to test. The services call the domain and use **abstractions** of the outside world. The **adapters** (a real database, a real mailer) implement those abstractions, and can be swapped for fakes in tests. This is called **hexagonal architecture** or **ports and adapters**, and it is lesson 3.2.6's Dependency Inversion applied to a whole project:

```python
from dataclasses import dataclass
from typing import Protocol

# ----- domain: pure rules, no I/O -----
@dataclass(frozen=True)
class Order:
    id: int
    amounts: tuple[float, ...]

    @property
    def total(self) -> float:
        return round(sum(self.amounts), 2)

# ----- port: what the service needs, described as a Protocol -----
class OrderRepository(Protocol):
    def get(self, order_id: int) -> Order: ...

# ----- service: a use case, depends only on the port -----
def order_summary(order_id: int, repo: OrderRepository) -> str:
    order = repo.get(order_id)
    return f"order {order.id}: {len(order.amounts)} lines, total {order.total}"

# ----- adapters: real or fake, interchangeable -----
class InMemoryRepo:
    def __init__(self, orders):
        self._orders = {o.id: o for o in orders}

    def get(self, order_id):
        return self._orders[order_id]

repo = InMemoryRepo([Order(1, (9.99, 5.01)), Order(2, (20.0,))])
print(order_summary(1, repo))
print(order_summary(2, repo))
```

```text
order 1: 2 lines, total 15.0
order 2: 1 lines, total 20.0
```

Swap `InMemoryRepo` for a SQL-backed class with the same `get` method and `order_summary` does not change. In tests you use the in-memory one, with no database at all.

## Habits that keep a project healthy

- **One responsibility per module.** A file named `utils.py` that grows to 2,000 lines is a warning sign.
- **Public API in `__init__.py`.** Hide internals behind a leading underscore.
- **No work at import time.** Importing a module should define things, not connect to databases or print.
- **Keep scripts thin.** A `cli.py` parses arguments and calls functions that live in the package, where tests can reach them.
- **Document with a README** that says what it is, how to install, a 5-line example, and how to run tests.
- **Automate checks:** run formatting, type checking and tests in continuous integration (for example, GitHub Actions) so every change is verified.
- **Pin and lock** application dependencies, **range** library dependencies.

## Common mistakes

- **Naming your file after a library** (`random.py`, `json.py`), which shadows it.
- **Circular imports,** fixed by restructuring, not by clever tricks.
- **Running tests against source files** instead of the installed package. Use the `src/` layout.
- **Committing `.venv/`, secrets or `__pycache__/`.**
- **Dependencies with no version bounds,** so a new major release breaks you overnight.
- **Hard-coding configuration** (paths, URLs, passwords) in the code.
- **A domain full of database calls,** making the core logic impossible to test without infrastructure.
- **Work at import time** (connecting, reading files), which makes importing slow and surprising.

+++ Solutions
```python
import importlib
import sys
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory() as root:
    pkg = Path(root) / "greeter"
    pkg.mkdir()
    (pkg / "__init__.py").write_text("")
    (pkg / "hello.py").write_text("def say(name):\n    return 'hello ' + name\n")
    sys.path.insert(0, root)
    importlib.invalidate_caches()
    try:
        from greeter import hello
        print(hello.say("Ada"))   # hello Ada
    finally:
        sys.path.remove(root)
        for name in [n for n in sys.modules if n.startswith("greeter")]:
            del sys.modules[name]

def load_settings(env):
    return {"name": env.get("APP_NAME", "app"), "workers": int(env.get("APP_WORKERS", "2"))}

def newer(a, b):
    return tuple(map(int, a.split("."))) > tuple(map(int, b.split(".")))

print(load_settings({"APP_WORKERS": "8"}), newer("1.10.0", "1.9.0"))   # {'name': 'app', 'workers': 8} True
```

Text comparison goes character by character, so `"1.10.0"` sorts before `"1.9.0"` (`"1"` is less than `"9"`). Numbers must be compared as numbers.

For the to-do app: the **domain** holds `Task` (title, done flag) and rules like "a completed task cannot be completed twice". The **port** is something like a `TaskRepository` protocol with `add`, `get` and `list`. **Adapters** are an in-memory repository (for tests), an SQLite repository (for real use), and the CLI or web layer that calls the service.

## Recap

- A **module** is a file, a **package** is a folder with `__init__.py`. Imports look in `sys.modules` (a cache: a module loads once), then in `sys.path` (script folder first, which is why naming a file `random.py` breaks things).
- Prefer **absolute imports**, use **relative** ones inside a package, and fix **circular imports** by moving shared code out. Run packages with `python -m`, and use `if __name__ == "__main__":` for scripts.
- A standard layout: `pyproject.toml`, `src/<package>/`, `tests/`, `README`. `pyproject.toml` declares the name, version, **dependencies** (with sensible version ranges and **semantic versioning** in mind), optional extras and **entry-point scripts**.
- Use a **virtual environment** per project and `pip install -e .` while developing. **Library** dependencies are ranges, an **application** locks exact versions. Build with `python -m build` to make wheels.
- Keep configuration in **environment variables**, injected as a parameter, and keep secrets out of git.
- Arrange code in **layers** with dependencies pointing inward: a pure **domain**, **services** (use cases) that depend on **ports** (Protocols), and swappable **adapters** (database, mail, CLI). This is hexagonal architecture, and it keeps the core testable.
