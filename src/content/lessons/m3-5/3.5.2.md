# Unit Testing, Fixtures & Parameterization

How do you know your code works? You run it and look. That works once. But code changes, and every change can silently break something that used to work. **Automated tests** are small programs that check your code for you, in milliseconds, every time you change anything. They are the reason professional teams can change a large codebase without fear. This lesson teaches how to write good unit tests with Python's built-in `unittest`, how to structure them, how to reuse setup with **fixtures**, how to test many cases at once with **parameterization**, and the habits (like test-driven development) that make testing pleasant instead of a chore.

> **Tip:** The editor can run `unittest` right here. The helper `run_tests` in the examples runs a test class and prints a short summary, so the output is the same every time. On your own computer you would simply run `python3 -m unittest` (or use `pytest`, shown later).

## What a test is

A test **calls your code with a known input and checks that the result is what you expected**. If it is not, the test fails and tells you exactly what differed.

```python
def add(a, b):
    return a + b

# the simplest possible test, by hand
assert add(2, 3) == 5
assert add(-1, 1) == 0
print("both checks passed")

try:
    assert add(2, 2) == 5, "2 + 2 should be 4, not 5"
except AssertionError as err:
    print("failure:", err)
```

```text
both checks passed
failure: 2 + 2 should be 4, not 5
```

`assert` works, but a single failure stops everything and gives poor reports. Test frameworks run **every** test, collect all the results, and print a clear report.

## unittest: the standard framework

A test is a **method whose name starts with `test`**, inside a class that extends `unittest.TestCase`:

```python
import io
import unittest

def add(a, b):
    return a + b

def divide(a, b):
    if b == 0:
        raise ZeroDivisionError("cannot divide by zero")
    return a / b

class TestMath(unittest.TestCase):
    def test_add_positive(self):
        self.assertEqual(add(2, 3), 5)

    def test_add_negative(self):
        self.assertEqual(add(-1, -1), -2)

    def test_divide(self):
        self.assertAlmostEqual(divide(1, 3), 0.3333, places=3)

    def test_divide_by_zero_raises(self):
        with self.assertRaises(ZeroDivisionError):
            divide(1, 0)

def run_tests(case):
    suite = unittest.defaultTestLoader.loadTestsFromTestCase(case)
    result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
    return result.testsRun, len(result.failures), len(result.errors)

print(run_tests(TestMath))     # (tests run, failures, errors)
```

```text
(4, 0, 0)
```

Four tests ran, none failed. When you run tests on your own computer, you see a report like this:

```text
....
----------------------------------------------------------------------
Ran 4 tests in 0.001s

OK
```

Each dot is a passing test. A failure prints the test name, the line, and a diff of expected versus actual.

### The assertion methods

Use the **specific** assertion for each check. They produce far better failure messages than a bare `assert`:

| Method | Checks |
|---|---|
| `assertEqual(a, b)` | `a == b` |
| `assertNotEqual(a, b)` | `a != b` |
| `assertTrue(x)` / `assertFalse(x)` | truthiness |
| `assertIs(a, b)` / `assertIsNone(x)` | identity |
| `assertIn(item, container)` | membership |
| `assertAlmostEqual(a, b, places=7)` | floats are close |
| `assertGreater(a, b)` and friends | ordering |
| `assertRaises(Error)` (a context manager) | an exception is raised |
| `assertCountEqual(a, b)` | same items, any order |

Never compare floats with `assertEqual`: `0.1 + 0.2 == 0.3` is false (lesson 1.1.3). Use `assertAlmostEqual`.

## What a failure looks like

Seeing a failing test is how you learn to read one. This test is deliberately wrong:

```python
import io
import unittest

def shout(text):
    return text.upper() + "!"

class TestShout(unittest.TestCase):
    def test_wrong_expectation(self):
        self.assertEqual(shout("hi"), "HI")

stream = io.StringIO()
suite = unittest.defaultTestLoader.loadTestsFromTestCase(TestShout)
result = unittest.TextTestRunner(stream=stream).run(suite)
report = stream.getvalue()

print(result.wasSuccessful(), len(result.failures))
print("AssertionError" in report)
print([line.strip() for line in report.splitlines() if line.startswith(("- ", "+ ", "?"))])
```

```text
False 1
True
['- HI!', '?   -', '+ HI']
```

The report contains the `-` and `+` lines showing the **actual** value (`HI!`) next to the **expected** one (`HI`), pinpointing the difference. A failing test is not a disaster. It is the tool doing its job.

## Structure: Arrange, Act, Assert

Every good test has three clear parts:

1. **Arrange** the situation (create objects, set up data).
2. **Act** (call the one thing being tested).
3. **Assert** the outcome.

```python
import io
import unittest

class ShoppingCart:
    def __init__(self):
        self.items = {}

    def add(self, name, price, qty=1):
        if qty <= 0:
            raise ValueError("quantity must be positive")
        _, old = self.items.get(name, (price, 0))
        self.items[name] = (price, old + qty)

    def total(self):
        return sum(price * qty for price, qty in self.items.values())

class TestShoppingCart(unittest.TestCase):
    def test_total_of_two_items(self):
        # arrange
        cart = ShoppingCart()
        cart.add("pen", 2.0, 3)
        cart.add("ink", 5.0)
        # act
        total = cart.total()
        # assert
        self.assertEqual(total, 11.0)

    def test_empty_cart_is_free(self):
        self.assertEqual(ShoppingCart().total(), 0)

    def test_adding_same_item_twice_accumulates(self):
        cart = ShoppingCart()
        cart.add("pen", 2.0)
        cart.add("pen", 2.0, 2)
        self.assertEqual(cart.items["pen"], (2.0, 3))

    def test_rejects_zero_quantity(self):
        with self.assertRaises(ValueError):
            ShoppingCart().add("pen", 2.0, 0)

def run_tests(case):
    suite = unittest.defaultTestLoader.loadTestsFromTestCase(case)
    result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
    return result.testsRun, len(result.failures), len(result.errors)

print(run_tests(TestShoppingCart))
```

```text
(4, 0, 0)
```

Notice each test is **small, independent, and has a name that states the behaviour**: `test_rejects_zero_quantity` tells you what broke before you read a line of code.

## Fixtures: shared setup

Most tests need the same starting objects. Copying the "arrange" lines into every test is noise, so **fixtures** build the world for you. In `unittest`, `setUp` runs **before each test** and `tearDown` **after each test**, so every test starts with a **fresh** state:

```python
import io
import unittest

class TestWithFixture(unittest.TestCase):
    def setUp(self):
        self.cart = {"items": []}          # a fresh, empty cart for EVERY test
        self.log = ["setUp"]

    def tearDown(self):
        self.log.append("tearDown")        # cleanup: close files, remove temp data

    def test_starts_empty(self):
        self.assertEqual(self.cart["items"], [])

    def test_can_add(self):
        self.cart["items"].append("pen")
        self.assertEqual(len(self.cart["items"]), 1)

    def test_unaffected_by_other_tests(self):
        # runs with a brand new cart, so the previous test's pen is gone
        self.assertEqual(self.cart["items"], [])

suite = unittest.defaultTestLoader.loadTestsFromTestCase(TestWithFixture)
result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
print(result.testsRun, result.wasSuccessful())
```

```text
3 True
```

This **isolation** is the most important testing principle: **tests must not depend on each other or on their order.** If `test_can_add` leaked its pen into the next test, results would depend on which ran first, and you would chase bugs that exist only in the tests.

The other fixture hooks:

- `setUpClass` / `tearDownClass` (class methods): run **once** for the whole class. Use for expensive setup such as starting a test server. Beware of sharing mutable state.
- `addCleanup(func)`: register a cleanup **right where you create the resource**, guaranteed to run even if `setUp` fails.
- Temporary resources: `tempfile.TemporaryDirectory()` gives a throwaway folder.

```python
import io
import os
import tempfile
import unittest
from pathlib import Path

def save_note(folder, name, text):
    path = Path(folder) / f"{name}.txt"
    path.write_text(text)
    return path

class TestSaveNote(unittest.TestCase):
    def setUp(self):
        self.tmp = tempfile.TemporaryDirectory()
        self.addCleanup(self.tmp.cleanup)          # the folder is removed after each test

    def test_creates_file_with_text(self):
        path = save_note(self.tmp.name, "todo", "buy milk")
        self.assertTrue(path.exists())
        self.assertEqual(path.read_text(), "buy milk")

    def test_each_test_gets_its_own_folder(self):
        self.assertEqual(os.listdir(self.tmp.name), [])

suite = unittest.defaultTestLoader.loadTestsFromTestCase(TestSaveNote)
result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
print(result.testsRun, result.wasSuccessful())
```

```text
2 True
```

## Parameterization: many cases, one test

Testing a function with ten inputs should not mean ten copy-pasted methods. With `subTest`, one test method runs a table of cases and **reports each failing case separately**:

```python
import io
import unittest

def is_leap_year(year):
    return year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)

class TestLeapYear(unittest.TestCase):
    def test_known_years(self):
        cases = [
            (2024, True),       # ordinary leap year
            (2023, False),      # ordinary year
            (1900, False),      # divisible by 100 but not 400
            (2000, True),       # divisible by 400
            (1, False),         # smallest year
            (4, True),
        ]
        for year, expected in cases:
            with self.subTest(year=year):
                self.assertEqual(is_leap_year(year), expected)

suite = unittest.defaultTestLoader.loadTestsFromTestCase(TestLeapYear)
result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
print(result.testsRun, result.wasSuccessful())
```

```text
1 True
```

Without `subTest`, the first failing case would stop the loop and hide the rest. With it, every row is judged on its own, and the report names the failing `year`.

### Choosing good test cases

A table of cases is only as good as the cases in it. Think in **categories**:

- **The ordinary case** ("typical input").
- **Boundaries**: smallest, largest, zero, one, just below and just above a limit.
- **Empty and missing**: empty list, empty string, `None`.
- **The special rules**: the century exceptions in the leap year rule (1900 and 2000) are exactly where a wrong implementation breaks.
- **Errors**: what should be rejected, and with which exception.

A test suite that only checks the happy path gives false confidence. The leap-year bug "divisible by 4 only" passes 2024 and 2023 and fails only on 1900.

## Testing exceptions and messages

```python
import io
import unittest

def parse_age(text):
    if not text.strip().isdigit():
        raise ValueError(f"not a valid age: {text!r}")
    age = int(text)
    if age > 150:
        raise ValueError("age out of range")
    return age

class TestParseAge(unittest.TestCase):
    def test_valid(self):
        self.assertEqual(parse_age(" 42 "), 42)

    def test_rejects_text(self):
        with self.assertRaises(ValueError) as ctx:
            parse_age("abc")
        self.assertIn("not a valid age", str(ctx.exception))

    def test_rejects_huge(self):
        with self.assertRaisesRegex(ValueError, "out of range"):
            parse_age("200")

suite = unittest.defaultTestLoader.loadTestsFromTestCase(TestParseAge)
result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
print(result.testsRun, result.wasSuccessful())
```

```text
3 True
```

`assertRaises` as a context manager lets you inspect the exception afterwards (`ctx.exception`). `assertRaisesRegex` checks the message text.

## Test-driven development (TDD)

TDD flips the order: **write the failing test first, then write just enough code to pass it, then clean up.** The cycle is red, green, refactor:

1. **Red:** write a test for behaviour that does not exist. Run it. It fails (good: it proves the test can fail).
2. **Green:** write the simplest code that makes it pass.
3. **Refactor:** improve the code while the tests keep guarding you.

```python
import io
import re
import unittest

# Step 1: tests written first (they define what "slugify" must do)
class TestSlugify(unittest.TestCase):
    def test_lowercases(self):
        self.assertEqual(slugify("Hello"), "hello")

    def test_spaces_become_dashes(self):
        self.assertEqual(slugify("hello big world"), "hello-big-world")

    def test_removes_punctuation(self):
        self.assertEqual(slugify("Hello, World!"), "hello-world")

    def test_collapses_repeated_separators(self):
        self.assertEqual(slugify("a  --  b"), "a-b")

    def test_trims_the_ends(self):
        self.assertEqual(slugify("  Hi!  "), "hi")

# Step 2: the implementation grows until every test passes
def slugify(text):
    text = text.lower()
    text = re.sub(r"[^a-z0-9]+", "-", text)       # any run of other characters becomes one dash
    return text.strip("-")

suite = unittest.defaultTestLoader.loadTestsFromTestCase(TestSlugify)
result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
print(result.testsRun, result.wasSuccessful())
```

```text
5 True
```

Each test pins down one rule. A later "improvement" to `slugify` that breaks the trimming rule would be caught the moment the tests run. That safety net is what lets you **refactor fearlessly**.

## Tests that catch bugs: the mutation idea

How do you know your tests are any good? Break the code on purpose and see if a test notices. If you change `year % 400 == 0` to `year % 400 == 1` and no test fails, your tests are missing the century rule. This idea (**mutation testing**) is automated by tools, and it is how you judge test quality beyond "does it pass".

```python
def leap_good(year):
    return year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)

def leap_bug_no_century(year):
    return year % 4 == 0

def leap_bug_no_400(year):
    return year % 4 == 0 and year % 100 != 0

weak_cases = [(2024, True), (2023, False)]
strong_cases = weak_cases + [(1900, False), (2000, True)]

def catches(cases, implementation):
    return any(implementation(year) != expected for year, expected in cases)

for name, impl in (("no century rule", leap_bug_no_century), ("no 400 rule", leap_bug_no_400)):
    print(name, "| weak tests catch it:", catches(weak_cases, impl), "| strong tests catch it:", catches(strong_cases, impl))
print("correct code passes all:", not catches(strong_cases, leap_good))
```

```text
no century rule | weak tests catch it: False | strong tests catch it: True
no 400 rule | weak tests catch it: False | strong tests catch it: True
correct code passes all: True
```

Weak tests pass on the buggy code. Strong tests (with the special years) catch both bugs. Good tests are the ones that **would fail if the code were wrong**.

## pytest: the popular alternative

Most Python projects use **pytest**, which needs less ceremony: plain functions and plain `assert`, with rich failure messages. Install it with `pip install pytest` and run `pytest`:

```pytest
import pytest
from shop import ShoppingCart, is_leap_year

@pytest.fixture
def cart():
    return ShoppingCart()               # a fixture: a fresh cart passed in by name

def test_total_of_two_items(cart):
    cart.add("pen", 2.0, 3)
    cart.add("ink", 5.0)
    assert cart.total() == 11.0

@pytest.mark.parametrize("year, expected", [(2024, True), (2023, False), (1900, False), (2000, True)])
def test_leap_year(year, expected):
    assert is_leap_year(year) == expected

def test_rejects_zero_quantity(cart):
    with pytest.raises(ValueError):
        cart.add("pen", 2.0, 0)
```

The ideas are identical: arrange/act/assert, fixtures for setup, a table of parameters for many cases, a context manager for expected errors. Learn the ideas once and both tools are easy. (pytest also runs `unittest` tests unchanged.)

## What to test, and what to leave

- **Test behaviour, not implementation.** "Adding two items totals correctly" survives a rewrite. "The cart stores a dictionary of tuples" breaks when you change how it works inside.
- **Test public functions**, not private helpers.
- **One reason to fail per test.** A test with ten asserts hides which part broke.
- **Fast and deterministic.** A test that sometimes fails (a **flaky** test) teaches the team to ignore failures. Avoid real time, real randomness and real network (next lesson).
- **Do not chase 100% coverage.** Coverage tools (`coverage.py`) show which lines ran, which finds forgotten code. But covered is not the same as correct: a test that runs a line without asserting anything proves nothing.

## Common mistakes

- **Tests that depend on each other** or on run order. Use `setUp` for a fresh state.
- **Testing only the happy path.** Add boundaries, empties and errors.
- **Comparing floats with `assertEqual`.** Use `assertAlmostEqual`.
- **A test with no assertion,** which can never fail.
- **Catching the exception yourself** with `try`/`except` in a test. Use `assertRaises`, so a missing exception fails the test.
- **Testing the framework or the language** instead of your code.
- **Tests that use the real clock, network or randomness,** and so fail "sometimes".
- **Ignoring a failing test** by deleting or skipping it, instead of fixing the code or the test.

## Practice

1. Write a `TestCase` for `max_of(numbers)` covering a normal list, a single item, negatives, and an empty list (which should raise `ValueError`).
2. Use `subTest` to test `is_palindrome` with at least eight cases, including the empty string and mixed case.
3. Write the tests **first** for a function `title_case("hello big world")` that returns `"Hello Big World"`, then implement it.
4. Write a "weak" and a "strong" list of `(n, expected)` cases for `is_even`, and show that the buggy version `lambda n: n > 0 and n % 2 == 0` passes the weak cases but is caught by the strong ones.

+++ Solutions
```python
import io
import unittest

def max_of(numbers):
    if not numbers:
        raise ValueError("empty")
    return max(numbers)

def is_palindrome(text):
    cleaned = "".join(ch.lower() for ch in text if ch.isalnum())
    return cleaned == cleaned[::-1]

def title_case(text):
    return " ".join(word.capitalize() for word in text.split())

class TestAll(unittest.TestCase):
    def test_max_normal(self):
        self.assertEqual(max_of([3, 9, 2]), 9)

    def test_max_single_and_negatives(self):
        self.assertEqual(max_of([7]), 7)
        self.assertEqual(max_of([-5, -2, -9]), -2)

    def test_max_empty(self):
        with self.assertRaises(ValueError):
            max_of([])

    def test_palindromes(self):
        cases = [("", True), ("a", True), ("aba", True), ("abc", False), ("Racecar", True),
                 ("A man, a plan, a canal: Panama", True), ("ab", False), ("12321", True)]
        for text, expected in cases:
            with self.subTest(text=text):
                self.assertEqual(is_palindrome(text), expected)

    def test_title_case(self):
        self.assertEqual(title_case("hello big world"), "Hello Big World")
        self.assertEqual(title_case(""), "")

result = unittest.TextTestRunner(stream=io.StringIO()).run(unittest.defaultTestLoader.loadTestsFromTestCase(TestAll))
print(result.testsRun, result.wasSuccessful())   # 5 True
```

```python
def is_even_correct(n):
    return n % 2 == 0

def is_even_buggy(n):
    return n > 0 and n % 2 == 0

weak = [(2, True), (3, False)]
strong = weak + [(0, True), (-2, True)]

def caught(cases, impl):
    return any(impl(n) != expected for n, expected in cases)

print(caught(weak, is_even_buggy), caught(strong, is_even_buggy), caught(strong, is_even_correct))   # False True False
```

The buggy version only fails for zero and negative even numbers, which the weak cases never try. Bugs hide at the edges: zero, negatives, boundaries.

## Recap

- A **unit test** calls your code with known input and checks the result. In `unittest`, tests are `test_...` methods in a `TestCase`, and the **specific assertion methods** (`assertEqual`, `assertRaises`, `assertAlmostEqual`...) give clear failure reports.
- Structure each test as **Arrange, Act, Assert**, keep tests **small, independent and named for the behaviour**, and never depend on test order.
- **Fixtures** provide fresh setup: `setUp`/`tearDown` per test, `setUpClass` once, `addCleanup` for guaranteed cleanup, and `tempfile` for throwaway files. In pytest they are `@pytest.fixture` functions.
- **Parameterize** with `subTest` (or `@pytest.mark.parametrize`) to run a table of cases and report each failure separately. Choose cases for **boundaries, empties, special rules and errors**, not just the happy path.
- **TDD**: red (a failing test), green (simplest code that passes), refactor. Good tests are ones that **would fail if the code were wrong**, which you can check by introducing a bug on purpose.
- Keep tests fast and deterministic, test behaviour rather than implementation, and treat coverage as a guide, not a goal.
