# CPython Memory Internals & Profiling

You can write Python for years without asking how it manages memory. Then one day your program uses 8 GB, or takes forty seconds where it should take two, and you need to understand what is going on underneath. This lesson opens the hood of **CPython**, the standard implementation: what an object is, how reference counting and the garbage collector free memory, why some operations are cheap and others secretly expensive, and, most important of all, the **method** for fixing slowness: **measure with a profiler, find the hot spot, change one thing, measure again.**

> **Note:** Exact byte sizes and speeds vary between Python versions and machines. The examples therefore print **comparisons and relationships** (such as "the list is bigger than the generator") instead of raw numbers, so the lesson stays true wherever you run it.

## Everything is an object

Every value in Python, including numbers, functions and classes, is an **object** living on the **heap**. A variable is just a **name** that points to an object (lesson 1.1.2: labels, not boxes). Three facts describe any object:

- its **identity** (`id(obj)`, effectively its address in memory),
- its **type** (what it is, and what it can do),
- its **value** (what it contains).

```python
a = [1, 2, 3]
b = a                       # a second name for the SAME object
c = [1, 2, 3]               # a different object with an equal value

print(a is b, a is c, a == c)
print(id(a) == id(b), id(a) == id(c))
print(type(a).__name__, type(len).__name__, type(type).__name__)
```

```text
True False True
True False
list builtin_function_or_method type
```

`is` asks "is this the **same object**?", while `==` asks "do they have the **same value**?". Use `is` for `None` (`x is None`) and `==` for values. Do not use `is` to compare numbers or strings: whether two equal ints are the same object is an implementation detail of CPython (it caches small ones), and relying on it is a bug.

## Reference counting

CPython tracks memory with a simple idea: every object keeps a **count of how many references point at it**. When the count drops to **zero**, the object is freed **immediately**:

```python
import sys

class Resource:
    def __init__(self, name):
        self.name = name

    def __del__(self):
        print("freed", self.name)

obj = Resource("first")
base = sys.getrefcount(obj)            # includes one temporary reference for the call itself
alias = obj
print(sys.getrefcount(obj) - base)     # one more name, one more reference
alias = None
print(sys.getrefcount(obj) - base)

print("about to drop the last name")
obj = None                             # the count reaches zero: freed on the spot
print("after")
```

```text
1
0
about to drop the last name
freed first
after
```

Adding the name `alias` raised the count by one, and removing it lowered it again. When the **last** reference (`obj`) went away, `__del__` ran **immediately**, before the next line. This is a big difference from languages with a "garbage collector that runs sometime later": in CPython, most objects are cleaned up the instant they become unreachable, which is why `with open(...)` closing files promptly, and simple resource handling, mostly just works.

Things that add references: assignment, putting an object in a list or dictionary, passing it to a function (for the duration of the call), a closure that captures it. Things that remove them: `del name`, reassignment, leaving a function, removing from a container.

## When reference counting is not enough: cycles

If two objects point at **each other**, their counts never reach zero, even when nothing else can reach them:

```python
import gc

class Node:
    def __init__(self, name):
        self.name = name
        self.other = None

a = Node("a")
b = Node("b")
a.other = b
b.other = a                  # a cycle: each keeps the other alive

del a, b                     # no outside names remain, yet the counts are not zero
print("unreachable objects found:", gc.collect() >= 2)
```

```text
unreachable objects found: True
```

After `del a, b` the two nodes are garbage, but each still holds a reference to the other, so reference counting alone would **never** free them. For this, CPython has a second system: the **cyclic garbage collector** (`gc` module). It periodically scans the objects that can hold references to other objects (containers, instances), finds groups that are only reachable from each other, and frees them. `gc.collect()` forces a scan and returns how many unreachable objects it found.

Practical points:

- The collector runs **automatically** based on allocation counts, so you rarely call it. It works in **generations**: new objects are checked often, long-lived ones rarely.
- Objects without cycles never need it. Avoid cycles when convenient, but do not fear them.
- Before Python 3.4, objects with `__del__` in cycles could never be collected. Today they can, but `__del__` is still best avoided. Use context managers for cleanup (lesson 3.3.2).

## Weak references: pointers that do not keep things alive

A **weak reference** refers to an object **without increasing its count**. When the object dies, the weak reference quietly becomes `None`. It is the tool for caches and observer lists that must not prevent cleanup:

```python
import weakref

class Image:
    def __init__(self, name):
        self.name = name

img = Image("photo.png")
ref = weakref.ref(img)
print(ref() is img)            # alive: the weak reference returns the object

del img                        # the only strong reference is gone
print(ref())                   # the object was freed, so the weak reference now gives None

cache = weakref.WeakValueDictionary()
big = Image("big.png")
cache["big"] = big
print("big" in cache)
del big
print("big" in cache)         # the cache entry vanished with the object
```

```text
True
None
True
False
```

A normal dictionary cache keeps its values alive forever, which is a classic **memory leak**. A `WeakValueDictionary` lets the cache forget objects that nobody else is using.

## How big are things?

`sys.getsizeof(obj)` reports the size of an object **itself**, not of everything it points to:

```python
import sys

numbers = list(range(1000))
print(sys.getsizeof(numbers) < sys.getsizeof(list(range(100_000))))
print(sys.getsizeof(tuple(numbers)) < sys.getsizeof(numbers))            # tuples are more compact than lists
print(sys.getsizeof([]) < sys.getsizeof([1]))
print(sys.getsizeof((x for x in range(1_000_000))) < sys.getsizeof(list(range(100))))   # a generator is tiny
print(sys.getsizeof("a") < sys.getsizeof("a" * 1000))

nested = [[1, 2, 3]] * 100
print("getsizeof counts only the outer list:", sys.getsizeof(nested) < sys.getsizeof(nested[0]) * 100)
```

```text
True
True
True
True
True
getsizeof counts only the outer list: True
```

Two lessons. First, **the container is not its contents**: the outer list of 100 inner lists reports only its own pointer array, not the lists it points to. To measure a whole structure you need a recursive tool (or `tracemalloc`, below). Second, even tiny objects have overhead: Python's convenience costs memory. An `int` is a full object, so a list of a million ints holds a million pointers **plus** a million int objects.

### Lists over-allocate

A list grows by **reserving extra room**, so most `append` calls cost nothing (this is the amortised O(1) of lesson 2.1.2):

```python
import sys

lst = []
sizes = []
for i in range(40):
    lst.append(i)
    sizes.append(sys.getsizeof(lst))

distinct = len(set(sizes))
print("appends:", len(sizes), "| times memory was re-allocated:", distinct < len(sizes) // 2)
print(sizes == sorted(sizes))
```

```text
appends: 40 | times memory was re-allocated: True
True
```

The size jumped only occasionally, in steps. Memory is allocated in **chunks** ahead of need. That is why a list is a little bigger than its contents strictly require.

### `__slots__` saves per-instance memory

A normal instance carries a dictionary of attributes (lesson 3.2.2). `__slots__` removes it. For millions of small objects the saving is large:

```python
import tracemalloc

class Plain:
    def __init__(self, x, y):
        self.x, self.y = x, y

class Slotted:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

def memory_of(cls, n=20_000):
    tracemalloc.start()
    objects = [cls(i, i) for i in range(n)]
    current, _ = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return current, len(objects)

plain_bytes, _ = memory_of(Plain)
slotted_bytes, _ = memory_of(Slotted)
print("slotted instances use less memory:", slotted_bytes < plain_bytes)
```

```text
slotted instances use less memory: True
```

`tracemalloc` is the standard library's **memory profiler**. It records every allocation made while it is on, so it measures the **real total**, including everything an object points to, which `getsizeof` cannot.

## Finding where memory goes: tracemalloc

```python
import tracemalloc

def build_lookup(n):
    return {i: str(i) * 10 for i in range(n)}

def build_total(n):
    return sum(i for i in range(n))

def peak_of(func, *args):
    tracemalloc.start()
    func(*args)
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return peak

print(peak_of(build_lookup, 20_000) > peak_of(build_total, 20_000) * 100)

tracemalloc.start()
data = build_lookup(5_000)
snapshot = tracemalloc.take_snapshot()
top = snapshot.statistics("lineno")[0]
print(top.size > 0, top.count > 0)
tracemalloc.stop()
```

```text
True
True True
```

`get_traced_memory()` returns `(current, peak)`: the **peak** tells you the most memory the code needed at any moment, which is what decides whether it fits in RAM. A **snapshot** can be grouped by source line (`"lineno"`) to name the exact line that allocates the most.

## Common memory leaks in a garbage-collected language

"Leak" in Python rarely means forgotten `free()`. It means **objects you did not realise are still referenced**:

- **A global cache or list that only grows** (`results.append(...)` forever, an unbounded `lru_cache(maxsize=None)`).
- **Closures and callbacks** that keep large objects alive. An event handler registered but never removed.
- **A traceback or exception stored** in a variable, holding every local variable of every frame.
- **Cycles with `__del__`** in very old code.
- **Reading a whole huge file or result set** instead of streaming (lesson 3.1.3).

The diagnostic is always the same: measure with `tracemalloc`, compare two snapshots, and look for what **grew**:

```python
import tracemalloc

registry = []                     # a global that quietly keeps everything

def handle_request(n):
    payload = "x" * 10_000
    registry.append(payload)      # the leak: nothing ever removes these
    return len(payload)

tracemalloc.start()
before = tracemalloc.take_snapshot()
for i in range(200):
    handle_request(i)
after = tracemalloc.take_snapshot()
growth = sum(stat.size_diff for stat in after.compare_to(before, "lineno"))
tracemalloc.stop()
print("memory grew by about 2 MB:", growth > 1_500_000)
```

```text
memory grew by about 2 MB: True
```

## Copying: shallow versus deep

Because names are references, `b = a` copies nothing, and `a.copy()` copies **one level**:

```python
import copy

original = {"name": "Ada", "scores": [90, 85]}
alias = original
shallow = original.copy()
deep = copy.deepcopy(original)

original["scores"].append(70)
original["name"] = "Changed"

print(alias["name"], "|", shallow["name"], "|", deep["name"])
print(shallow["scores"], deep["scores"])
```

```text
Changed | Ada | Ada
[90, 85, 70] [90, 85]
```

The shallow copy duplicated the dictionary but **shares** the inner list, so the appended `70` shows up in it too. `deepcopy` duplicates everything recursively. This is the aliasing trap of lesson 1.4.4, seen from the memory side.

## Profiling speed: measure before you optimise

> *"Premature optimisation is the root of all evil."* (Donald Knuth) Programmers are famously bad at guessing where their programs are slow. **Measure.**

### timeit: compare small snippets

`timeit` runs a snippet many times and reports the total, removing noise:

```python
import timeit

setup = "data = list(range(5000)); lookup = set(data)"
list_time = timeit.timeit("4999 in data", setup=setup, number=2000)
set_time = timeit.timeit("4999 in lookup", setup=setup, number=2000)
print("set lookup is much faster than list lookup:", set_time * 5 < list_time)

join_time = timeit.timeit("''.join(str(i) for i in range(500))", number=300)
concat_time = timeit.timeit("s=''\nfor i in range(500):\n    s += str(i)", number=300)
print("both ways produce the same text:", ''.join(str(i) for i in range(5)) == "01234")
print(join_time > 0, concat_time > 0)
```

```text
set lookup is much faster than list lookup: True
both ways produce the same text: True
True True
```

The set membership test is dramatically faster because it is O(1) hashing against O(n) scanning (lesson 2.3.3). This is the kind of difference that matters. (String concatenation in a loop is also a classic, but CPython optimises it so well in simple cases that the gap is small. `join` remains the clear, safe choice.)

### cProfile: where does the time go?

`timeit` compares snippets. A **profiler** examines a whole program and reports **which functions** consume the time:

```python
import cProfile
import io
import pstats

def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

def helper():
    return sum(range(1000))

def program():
    fib(18)
    for _ in range(50):
        helper()

profiler = cProfile.Profile()
profiler.enable()
program()
profiler.disable()

stream = io.StringIO()
stats = pstats.Stats(profiler, stream=stream)
stats.sort_stats("cumulative")
stats.print_stats(8)
report = stream.getvalue()

print("fib appears in the report:", "fib" in report)
def calls(name):
    key = next(k for k in stats.stats if k[2] == name)
    return stats.stats[key][1]                      # the total number of calls

print("fib was called", calls("fib"), "times")
print("helper was called", calls("helper"), "times")
```

```text
fib appears in the report: True
fib was called 8361 times
helper was called 50 times
```

The profiler counted every call: `fib(18)` made 8,361 calls, while `helper` was called 50 times. The full report has columns for **ncalls** (how many calls), **tottime** (time inside the function itself, excluding callees) and **cumtime** (including callees). Sort by `cumulative` to find the biggest overall consumers, or by `tottime` to find the functions doing the real work.

The report points straight at `fib` as the hot spot, and we know the cure from lesson 2.6.3: **memoize**.

```python
import timeit
from functools import lru_cache

def fib_slow(n):
    return n if n < 2 else fib_slow(n - 1) + fib_slow(n - 2)

@lru_cache(maxsize=None)
def fib_fast(n):
    return n if n < 2 else fib_fast(n - 1) + fib_fast(n - 2)

slow = timeit.timeit("fib_slow(22)", globals=globals(), number=3)
fib_fast(22)
fast = timeit.timeit("fib_fast(22)", globals=globals(), number=3)
print(fib_slow(22) == fib_fast(22), fast * 50 < slow)
```

```text
True True
```

That is the whole method in miniature: **profile, find the hot spot, apply a better algorithm, measure again** to confirm.

On your own computer, profile an entire script from the terminal with no code changes:

```bash
python3 -m cProfile -s cumulative my_script.py
python3 -m timeit "sum(range(1000))"
python3 -X importtime my_script.py          # which imports are slow to load
```

## The optimisation workflow

1. **Make it correct first,** and write tests (lesson 3.5.2) that pin down the behaviour.
2. **Measure** with a realistic workload (`cProfile`, `timeit`, `tracemalloc`).
3. **Find the hot spot.** Usually one or two functions dominate. Ignore the rest.
4. **Fix the algorithm or data structure first.** An O(n²) to O(n) change beats any micro-optimisation (module 2).
5. **Then the cheap wins:** use built-ins and comprehensions (they run in C), cache repeated work, avoid repeated attribute lookups in hot loops, stream instead of materialising.
6. **Measure again.** Keep the change only if it helped, and re-run the tests.
7. **Stop** when it is fast enough.

If pure Python is still too slow, the next steps are NumPy (loops in C), Cython, Numba, or rewriting the hot function in Rust or C. Because you profiled, you know exactly which function to move.

## A glimpse of bytecode

Python compiles your code to **bytecode**, a list of simple instructions that the interpreter runs. The `dis` module shows it:

```python
import dis

def add(a, b):
    return a + b

instructions = [ins.opname for ins in dis.get_instructions(add)]
print(len(instructions) >= 3, "RETURN_VALUE" in instructions)
print(add.__code__.co_varnames, add.__code__.co_argcount)
```

```text
True True
('a', 'b') 2
```

Each Python-level operation turns into several bytecode instructions, and each instruction costs a little time. This is why one built-in call (`sum(data)`, which loops in C) beats an explicit Python `for` loop doing the same thing. It also explains why the GIL (lesson 3.4.1) can switch threads **between instructions**, which is what makes `counter += 1` unsafe.

## Common mistakes

- **Optimising without measuring,** and speeding up code that was not the bottleneck.
- **Using `is` to compare values** (numbers, strings). Use `==`.
- **Assuming `getsizeof` measures a whole structure.** It measures the container only. Use `tracemalloc`.
- **Unbounded caches and global lists** that grow forever.
- **Shallow copies of nested data,** sharing inner objects by accident.
- **Relying on `__del__` for cleanup.** Use context managers.
- **Benchmarking once, or on tiny data,** where noise dominates. Repeat, and use realistic sizes.
- **Micro-optimising** (caching `len`, avoiding a function call) before fixing an O(n²) algorithm.

## Recap

- Every value is an **object** with identity, type and value. Names are references. `is` tests identity, `==` tests equality (use `is` only for `None`).
- CPython frees an object **immediately** when its **reference count** hits zero (`sys.getrefcount`). **Cycles** keep counts above zero, so a **cyclic garbage collector** (`gc`) finds and frees unreachable groups. **Weak references** (`weakref`) point at objects without keeping them alive, perfect for caches.
- `sys.getsizeof` measures only the object itself. Use **`tracemalloc`** (peak, snapshots by line, comparing snapshots) to find the real memory cost and the lines that allocate. Lists over-allocate in chunks, tuples and generators are compact, and `__slots__` shrinks instances.
- Python "leaks" are usually **references you forgot**: unbounded caches, growing global lists, retained callbacks and tracebacks. Shallow copies share inner objects. Use `copy.deepcopy` for nested data.
- **Measure before optimising.** `timeit` compares snippets, `cProfile`/`pstats` shows which functions consume time (`ncalls`, `tottime`, `cumtime`), and `python3 -m cProfile` profiles a whole script.
- The workflow: make it **correct** and tested, **profile**, fix the **hot spot's algorithm or data structure** first, then take cheap wins, **measure again**, and stop when it is fast enough.
- Bytecode (`dis`) explains why built-ins beat Python loops, and why thread switches between instructions make `counter += 1` unsafe.
