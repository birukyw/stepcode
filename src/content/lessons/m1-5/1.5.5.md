# Pure Functions vs. Side Effects

Some functions are like calculators: the same inputs always give the same output, and nothing else in the world changes. Others print, write files, or modify the data you passed in. Both kinds are necessary, but knowing which one you are writing, and keeping them apart, is what separates code that is easy to trust from code that surprises you.

## Pure functions

A function is **pure** when:

1. Its result depends only on its arguments, so the same inputs always give the same output.
2. It has no **side effects**: it does not print, modify its arguments, change global variables, or touch files.

```python
def area(width, height):
    return width * height

print(area(3, 4))
print(area(3, 4))
```

```text
12
12
```

You can call `area` a thousand times in any order and nothing else changes. That property is called **referential transparency**: you could replace any call `area(3, 4)` with the value `12` and the program would behave identically.

## Side effects

A **side effect** is any change a function makes beyond returning a value.

```python
log = []

def area_logged(width, height):
    log.append(f"area({width}, {height})")
    print("computing...")
    return width * height

area_logged(3, 4)
area_logged(5, 2)
print(log)
```

```text
computing...
computing...
['area(3, 4)', 'area(5, 2)']
```

Printing and appending to `log` are side effects. Side effects are not bad in themselves, since every useful program eventually prints or saves something. The problem is **hidden** side effects, where a caller has no reason to expect them.

## The most dangerous side effect: changing your arguments

Lists are passed to functions by reference, just like assignment. The parameter is a second name for the caller's list, so a function that mutates it changes the caller's data.

```python
def top_three(scores):
    scores.sort(reverse=True)
    return scores[:3]

tournament = [52, 91, 77, 64, 88]
best = top_three(tournament)

print(best)
print(tournament)
```

```text
[91, 88, 77]
[91, 88, 77, 64, 52]
```

The function returned the right answer and, as a hidden side effect, reordered the caller's master list. If another part of the program relied on the original order, for example to know who entered first, it is now broken, and nothing in the call `top_three(tournament)` warned anyone.

The pure version works on a copy and leaves the input alone:

```python
def top_three(scores):
    return sorted(scores, reverse=True)[:3]

tournament = [52, 91, 77, 64, 88]
best = top_three(tournament)

print(best)
print(tournament)
```

```text
[91, 88, 77]
[52, 91, 77, 64, 88]
```

`sorted()` builds a new list, so the caller's list is untouched.

> **Remember:** By default, a function should **not** modify the objects passed to it. If modifying in place is the point, say so in the name and return `None`, as Python's own `list.sort()` does.

## Return new data instead of editing old data

The pure style builds and returns a new object.

```python
def add_bonus(scores, bonus):
    result = []
    for s in scores:
        result.append(s + bonus)
    return result

original = [10, 20, 30]
boosted = add_bonus(original, 5)

print(original)
print(boosted)
```

```text
[10, 20, 30]
[15, 25, 35]
```

Building a new list costs a little memory, and in exchange you get predictability. When a list has millions of items and performance matters, in-place updates can be the right choice. Make that choice deliberately, and make it visible.

## Why pure functions are easier

- **Testing.** Call the function and compare the result. There is no setup and nothing to clean up afterwards.
- **Reasoning.** You only need to read the function itself, not the rest of the program.
- **Reuse.** A pure function works anywhere, because it does not depend on or change anything outside.
- **Debugging.** If a pure function returns the wrong value for some input, the bug is inside that function. Always.

A quick test is easy to write:

```python
def clamp(value, low, high):
    return max(low, min(value, high))

assert clamp(5, 0, 10) == 5
assert clamp(-3, 0, 10) == 0
assert clamp(42, 0, 10) == 10
print("all clamp tests passed")
```

```text
all clamp tests passed
```

`assert condition` does nothing when the condition is true and stops the program with an `AssertionError` when it is false. It is the simplest form of automated test, and Track 3 builds on it.

## Functional core, imperative shell

A practical way to organise a program: keep the **logic** in pure functions, and keep the **effects**, such as input, printing and saving, in a thin outer layer that calls them.

```python
def parse_scores(text):
    scores = []
    for part in text.split(","):
        scores.append(int(part))
    return scores

def summarize(scores):
    return len(scores), max(scores), sum(scores) / len(scores)

def format_summary(count, best, average):
    return f"{count} scores, best {best}, average {average:.1f}"

# The shell: the only place with side effects
raw = "52,91,77,64,88"
print(format_summary(*summarize(parse_scores(raw))))
```

```text
5 scores, best 91, average 74.4
```

Every function above `# The shell` is pure and easy to test. Only the final line touches the outside world. Notice `*summarize(...)`, which unpacks the returned tuple into the three parameters of `format_summary`.

## Common mistakes

- **Mutating a parameter by accident.** `.sort()`, `.append()` and `.remove()` on an argument change the caller's data.
- **Hiding prints in logic functions.** Return values and let the caller decide what to print.
- **Depending on global variables that change.** The same call can give different results.
- **Assuming a function is pure because it returns a value.** It can return and also mutate.

def remove_negatives(numbers):

def normalize(scores):
    top = max(scores)
    result = []
    for s in scores:

def normalize(scores):
    top = max(scores)
    result = []
    for s in scores:
        result.append(s / top)
    return result

data = [2, 4, 8]
assert normalize(data) == [0.25, 0.5, 1.0]
assert data == [2, 4, 8]

## Recap

- A pure function depends only on its arguments and changes nothing else.
- Side effects include printing, mutating arguments, changing globals and touching files.
- Mutating an argument is the most dangerous side effect, because the caller sees it.
- Prefer returning new data. If in-place change is the point, name it clearly and return `None`.
- Keep logic in pure functions and effects in a thin outer shell. `assert` makes quick tests.
