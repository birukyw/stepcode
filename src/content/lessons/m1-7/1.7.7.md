# Python Beyond the Browser: Scripts, pip & Virtual Environments

Everything so far ran in the editor next to each lesson. That is a great place to learn, but real Python lives on **your own computer**: in files you save, scripts you run from a terminal, and packages you install. This lesson is a practical guide to taking the code you write here and running it for real. It is the bridge from "I can follow a course" to "I can build my own project".

> **Tip:** The commands in this lesson are typed into a **terminal** (also called a command line or shell), not into the course editor, so they are shown as plain code and are not runnable here. Try them on your own computer.

## 1. Installing Python

Download Python 3 from **python.org** (Windows, macOS, Linux), or use your system's package manager. During the Windows installer, tick **"Add Python to PATH"**. Then open a terminal and check:

```bash
python3 --version
```

On Windows the command is often `python --version` or `py --version`. You should see something like `Python 3.12.x`. If you see Python 2, or "command not found", the install or PATH step needs fixing.

## 2. The interactive prompt (REPL)

Type `python3` alone and you land in the **REPL** (read-eval-print loop), a place to try one line at a time:

```bash
python3
>>> 2 + 3
5
>>> name = "Ada"
>>> name.upper()
'ADA'
>>> exit()
```

It is the best scratchpad there is. Use it to test small ideas, check what a function returns, or look at help: `help(str.split)`.

## 3. Running a script

A **script** is a plain text file ending in `.py`. Save this as `hello.py`:

```python
name = input("Your name? ")
print("Hello,", name)
```

Run it from the folder it is in:

```bash
python3 hello.py
```

Use any text editor you like, but a code editor such as **VS Code** (with the Python extension) or **PyCharm** adds colours, error hints and a Run button. Python reads the file from top to bottom, just as it did in the course.

## 4. Command-line arguments

Scripts can take input from the command line, which is how many tools work:

```python
import sys

print("script name:", sys.argv[0])
print("arguments:", sys.argv[1:])
```

Run `python3 greet.py Ada Linus` and `sys.argv[1:]` will be `['Ada', 'Linus']`. For anything fancier (flags such as `--verbose`), the standard `argparse` module does the parsing for you.

## 5. Where Python looks for modules

When you write `import geometry`, Python looks in the folder of the running script, then in the installed packages. That is why naming your own file `random.py` breaks things (lesson 1.7.4): it is found first.

A folder of modules becomes a **package** when it holds an `__init__.py` file (often empty). A typical small project looks like this:

```tree
my_project/
    main.py
    utils.py
    tests/
        test_utils.py
    requirements.txt
```

`main.py` can `import utils` directly, because they sit in the same folder.

## 6. Installing packages with pip

**pip** is Python's package installer. It downloads libraries from **PyPI**, the public index.

```bash
pip install requests
pip list
pip uninstall requests
```

If `pip` is not found, use `python3 -m pip install requests`, which always uses the same Python you run.

After installing, you `import` the package like a standard module:

```python
import requests            # needs: pip install requests

reply = requests.get("https://example.com")
print(reply.status_code)
```

## 7. Virtual environments: one box per project

Installing everything into one global Python becomes a mess: project A needs `numpy` 1.x and project B needs 2.x. A **virtual environment** is a private folder holding its own Python and packages for **one project**.

```bash
python3 -m venv .venv                 # create it, once per project
source .venv/bin/activate             # activate (macOS and Linux)
.venv\Scripts\activate                # activate (Windows)

pip install requests numpy            # installs into .venv only
pip freeze > requirements.txt         # record exactly what you installed
deactivate                            # leave the environment
```

A teammate (or you, on a new computer) rebuilds the same setup with:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

**Rule of thumb:** one virtual environment per project, and never commit the `.venv` folder itself. Commit `requirements.txt`.

## 8. Reading error messages in a terminal

Everything from lesson 1.7.1 applies. A traceback in a real terminal shows your **real file name and line number**:

```text
Traceback (most recent call last):
  File "/home/me/my_project/main.py", line 4, in <module>
    total = add(1, "2")
  File "/home/me/my_project/utils.py", line 2, in add
    return a + b
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

Read it from the bottom: the error, then `utils.py` line 2, called from `main.py` line 4. Most editors let you click such lines to jump straight to the code.

## 9. Testing your code

Rather than checking by eye, write small tests that fail loudly. The simplest version uses `assert`:

```python
def add(a, b):
    return a + b

def test_add():
    assert add(2, 3) == 5
    assert add(-1, 1) == 0
    assert add(0, 0) == 0

test_add()
print("all tests passed")
```

```text
all tests passed
```

Real projects use the **pytest** library (`pip install pytest`), which finds every function named `test_*` and reports exactly which assertion failed. Writing a test *before* fixing a bug proves the bug is gone and stops it coming back.

## 10. Where to go from here

You now have the practical toolkit:

- **Version control:** learn **git** to save the history of your project and share it (git-scm.com, and GitHub for hosting).
- **Style:** the **PEP 8** guide describes how Python code is usually formatted. Tools such as `black` and `ruff` apply it automatically.
- **Docs:** docs.python.org is excellent, and `help(thing)` works anywhere.
- **Projects:** build something small that you actually want. A budget tracker, a quiz game, a script that renames your photos. Real problems teach faster than exercises.

When the foundations feel comfortable, the second course, **Speak Python**, takes you into data structures, algorithms and real software design.

## Common mistakes

- **Running a script from the wrong folder,** then wondering why it cannot find its data files.
- **Installing packages globally** and creating version clashes. Use a virtual environment per project.
- **Forgetting to activate the environment** before `pip install`. Check that your prompt shows `(.venv)`.
- **Naming a file after a library** you import (`requests.py`, `random.py`).
- **Committing `.venv`** to version control. Commit `requirements.txt` instead.

## Recap

- Install Python 3 from python.org and check it with `python3 --version`. The **REPL** (`python3` alone) is a scratchpad for single lines.
- A script is a `.py` file run with `python3 file.py`. Arguments arrive in `sys.argv`.
- **pip** installs packages from PyPI, and a **virtual environment** (`python3 -m venv .venv`) keeps each project's packages separate. Record them in `requirements.txt`.
- Tracebacks in a terminal show real file names and line numbers. Read them from the bottom, as before.
- Test with `assert` and later **pytest**, use **git** for history, and build small projects of your own.
