# Reading Errors & Debugging Like a Detective

Every programmer, from a first-week student to the engineer who wrote your operating system, spends a large part of the day looking at things that do not work. The difference between a beginner and an expert is not that experts make fewer mistakes. It is that they **read the error message** instead of panicking at it. This lesson teaches you to read what Python is telling you, and then gives you a method for the bugs that come with no message at all.

## An error is a message, not an insult

When Python cannot continue, it stops and prints a **traceback**: a report of what it was doing when it failed.

```python error
def average(numbers):
    return sum(numbers) / len(numbers)

def report(scores):
    return "Average: " + str(average(scores))

print(report([]))
```

```text
Traceback (most recent call last):
  File "main.py", line 7, in <module>
    print(report([]))
  File "main.py", line 5, in report
    return "Average: " + str(average(scores))
  File "main.py", line 2, in average
    return sum(numbers) / len(numbers)
ZeroDivisionError: division by zero
```

Read a traceback **from the bottom up**:

1. **The last line** names the error type and explains it: `ZeroDivisionError: division by zero`. That is the *what*.
2. **The line above it** shows the exact code that failed: `return sum(numbers) / len(numbers)`.
3. **Everything above** is the **call stack** (lesson 1.5.3), listing which function called which, oldest call first. It tells you *how you got there*: `report` called `average`, which divided by `len(numbers)`, which was 0 because the list was empty.

The bug is not in `average`'s arithmetic. It is that someone passed an empty list. The traceback gave you the whole story in five lines.

## The errors you will meet most

Each error type is a precise word. Learn the common ones and you will recognise most bugs on sight.

```python error
print(totla)
```

```text
Traceback (most recent call last):
  File "main.py", line 1, in <module>
    print(totla)
NameError: name 'totla' is not defined
```

**`NameError`**: a name that does not exist. Usually a typo, or a variable used before it is created.

```python error
numbers = [10, 20, 30]
print(numbers[3])
```

```text
Traceback (most recent call last):
  File "main.py", line 2, in <module>
    print(numbers[3])
IndexError: list index out of range
```

**`IndexError`**: an index past the end of a list. Remember a list of 3 has indexes 0, 1 and 2.

```python error
person = {"name": "Ada"}
print(person["age"])
```

```text
Traceback (most recent call last):
  File "main.py", line 2, in <module>
    print(person["age"])
KeyError: 'age'
```

**`KeyError`**: a dictionary key that is not there. `person.get("age")` would have returned `None` instead of failing.

```python error
print("Age: " + 36)
```

```text
Traceback (most recent call last):
  File "main.py", line 1, in <module>
    print("Age: " + 36)
TypeError: can only concatenate str (not "int") to str
```

**`TypeError`**: the right operation on the wrong kind of value.

```python error
number = int("12abc")
```

```text
Traceback (most recent call last):
  File "main.py", line 1, in <module>
    number = int("12abc")
ValueError: invalid literal for int() with base 10: '12abc'
```

**`ValueError`**: the right kind of value, but an unusable one.

```python error
def broken():
    if True
        return 1
```

```text
  File "main.py", line 2
    if True
           ^
SyntaxError: expected ':'
```

**`SyntaxError`**: Python cannot even read your code, so nothing runs. The caret `^` points near the problem, and a missing colon, bracket or quote is the usual cause. Note that the real mistake is sometimes on the **line before** the one shown.

| Error | Usual cause |
|---|---|
| `SyntaxError` | A typo in the code's shape: missing `:`, `)` or quote |
| `NameError` | A misspelled or not-yet-defined name |
| `TypeError` | Mixing incompatible types, wrong number of arguments |
| `ValueError` | Right type, wrong content (`int("abc")`) |
| `IndexError` | Index outside the list |
| `KeyError` | Missing dictionary key |
| `AttributeError` | A value does not have that method or attribute |
| `ZeroDivisionError` | Dividing by zero |

## When there is no error, but the answer is wrong

The hardest bugs print nothing at all. The program runs happily and gives the **wrong result**. For these you need a method, not a message.

```python
def total_with_tax(prices, rate):
    total = 0
    for price in prices:
        total += price
        total * (1 + rate)
    return total

print(total_with_tax([10, 20, 30], 0.1))
```

```text
60
```

The answer should be 66.0, but it printed 60. Do not stare at it. Debug it.

### The method

1. **Reproduce it.** Find the smallest input that shows the bug.
2. **State what you expected** and what you got.
3. **Look at the values** while the program runs, not just at the code.
4. **Change one thing at a time** and run again.
5. **Find the first place** where reality differs from your expectation.

## Debugging tool 1: print what is happening

The simplest tool is the best one. Print the values at each step:

```python
def total_with_tax(prices, rate):
    total = 0
    for price in prices:
        total += price
        print("after adding", price, "total is", total)
        total * (1 + rate)
        print("after tax step, total is", total)
    return total

total_with_tax([10, 20], 0.1)
```

```text
after adding 10 total is 10
after tax step, total is 10
after adding 20 total is 30
after tax step, total is 30
```

The "tax step" does not change `total` at all. The line `total * (1 + rate)` calculates a number and **throws it away**, because nothing stores it. (It was also the wrong plan: the tax belongs after the loop, once.) The prints made the problem visible in seconds.

```python
def total_with_tax(prices, rate):
    subtotal = sum(prices)
    return subtotal * (1 + rate)

print(round(total_with_tax([10, 20, 30], 0.1), 2))
```

```text
66.0
```

Remove the debugging prints once you have found the bug. A good habit is to prefix them (`print("DEBUG", x)`) so that they are easy to find and delete.

## Debugging tool 2: assert your assumptions

An `assert` states something that must be true. If it is not, Python stops right there with an `AssertionError`:

```python error
def percent(part, whole):
    assert whole > 0, "whole must be positive"
    return part / whole * 100

print(percent(5, 0))
```

```text
Traceback (most recent call last):
  File "main.py", line 5, in <module>
    print(percent(5, 0))
  File "main.py", line 2, in percent
    assert whole > 0, "whole must be positive"
AssertionError: whole must be positive
```

Asserts catch a bug **at its source** instead of letting a bad value travel through the program and cause a confusing failure far away. Use them for things that should never happen, such as a wrong internal state. For bad input from users, use proper error handling (the next lesson).

## Debugging tool 3: divide and conquer

If the bug could be anywhere in 40 lines, **cut the problem in half**. Check the value in the middle. If it is already wrong, the bug is in the first half. Otherwise, it is in the second. Repeat. You have met this idea before: it is binary search, applied to code. It is far faster than reading every line.

```python
def clean(words):
    return [w.strip().lower() for w in words]

def count(words):
    counts = {}
    for w in words:
        counts[w] = counts.get(w, 0) + 1
    return counts

raw = [" Apple", "apple ", "BANANA", "banana", "Apple"]
middle = clean(raw)
print(middle)
print(count(middle))
```

```text
['apple', 'apple', 'banana', 'banana', 'apple']
{'apple': 3, 'banana': 2}
```

Checking `middle` shows that the cleaning step worked, so if the final counts were wrong, the bug would have to be in `count`.

## Debugging tool 4: rubber ducks

Explain your code, line by line, out loud, to a rubber duck (or a patient friend, or a cat). It sounds silly and it works constantly. When you are forced to say what each line *really* does instead of what you *meant* it to do, you notice the gap.

## Reading code before running it

A final habit: **trace by hand**. Pick a tiny input, and write down the value of each variable after each line, as in lesson 1.3.1. The computer is just following rules, and so can you.

## Common mistakes

- **Ignoring the last line of the traceback** and reading the wall of text above it instead.
- **Changing many things at once.** If it starts working, you will not know why. If it gets worse, you will not know which change did it.
- **Assuming instead of checking.** "That variable must be 5" is exactly the belief to test with a `print`.
- **Fixing the symptom, not the cause.** Wrapping a crash in a silent workaround hides the real bug.
- **Leaving debug prints in** finished code.

## Practice

1. This code should print the largest number but prints `0`. Find and fix the bug: `best = 0` then a loop that checks `if n > best` over `[-5, -2, -9]`.
2. Predict the error type for each: `int("3.5")`, `[1, 2, 3][5]`, `"abc".upper(1)`, `len(5)`, `{}["x"]`.
3. Add an `assert` to `average` so that an empty list gives the message `"need at least one number"`.
4. Introduce a bug on purpose into a function you wrote earlier, then find it using only `print`.

+++ Solutions
```python
def largest(numbers):
    best = numbers[0]
    for n in numbers:
        if n > best:
            best = n
    return best

print(largest([-5, -2, -9]))   # -2
```

`int("3.5")` is a `ValueError` (not a whole number), `[1, 2, 3][5]` an `IndexError`, `"abc".upper(1)` a `TypeError` (too many arguments), `len(5)` a `TypeError` (an int has no length) and `{}["x"]` a `KeyError`.

```python
def average(numbers):
    assert len(numbers) > 0, "need at least one number"
    return sum(numbers) / len(numbers)

print(average([2, 4, 6]))   # 4.0
```
+++

## Recap

- A **traceback** reads from the bottom: the error type and message first, then the failing line, then the chain of calls that led there.
- Learn the common errors: `SyntaxError`, `NameError`, `TypeError`, `ValueError`, `IndexError`, `KeyError`, `AttributeError`, `ZeroDivisionError`.
- For wrong answers with no error: reproduce, state expected versus actual, **look at the values**, and change one thing at a time.
- Tools: `print` the values, `assert` your assumptions, **halve** the problem, and explain it out loud.
- Fix the cause, not the symptom, and remove the debugging prints when you are done.
