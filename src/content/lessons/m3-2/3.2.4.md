# Inheritance, MRO & Composition

Inheritance lets one class build on another: reuse what exists, override what differs. It looks simple, and it is also the most over-used feature in object-oriented programming. This lesson teaches how inheritance really works in Python (including `super()` and the method resolution order), the tools for defining **contracts** (abstract base classes), and the design rule that experienced programmers repeat: **prefer composition over inheritance**.

## The basics, with a purpose

A **subclass** gets everything its **parent** has, and can add or replace behaviour:

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    def pay(self):
        return self.salary

    def describe(self):
        return f"{self.name} earns {self.pay()}"

class Manager(Employee):
    def __init__(self, name, salary, bonus):
        super().__init__(name, salary)        # let the parent set up its part
        self.bonus = bonus

    def pay(self):                            # override
        return self.salary + self.bonus

staff = [Employee("Ada", 100), Manager("Grace", 150, 50)]
for person in staff:
    print(person.describe())
print(isinstance(staff[1], Employee), issubclass(Manager, Employee))
print(type(staff[1]).__name__)
```

```text
Ada earns 100
Grace earns 200
True True
Manager
```

Things to notice:

- `Manager` inherited `describe` without rewriting it. Inside it, `self.pay()` picks **`Manager.pay`** for a manager. That is **polymorphism**: the same call does the right thing for each type.
- `super().__init__(...)` calls the parent's constructor so the parent's part is set up. Forgetting this is a classic bug.
- `isinstance(x, Employee)` is true for a `Manager` too: a manager **is an** employee.

## super() and cooperating with the parent

`super()` does not only mean "my parent". It means "the **next class in line**". Use it to extend behaviour instead of replacing it:

```python
class Logger:
    def log(self, message):
        return "LOG: " + message

class TimestampLogger(Logger):
    def log(self, message):
        base = super().log(message)           # reuse the parent's work
        return "[t=0] " + base

print(TimestampLogger().log("started"))
```

```text
[t=0] LOG: started
```

## The method resolution order (MRO)

When you call a method, Python searches the class and its ancestors in a fixed order called the **MRO**. You can print it:

```python
class A:
    def who(self):
        return "A"

class B(A):
    def who(self):
        return "B"

class C(A):
    def who(self):
        return "C"

class D(B, C):
    pass

print([cls.__name__ for cls in D.__mro__])
print(D().who())
```

```text
['D', 'B', 'C', 'A', 'object']
B
```

`D` inherits from both `B` and `C`, which both inherit from `A`. Python's rule (**C3 linearization**) produces `D, B, C, A, object`: children before parents, and the parents appear in the order you listed them. So `D().who()` finds `B.who` first.

With `super()` in every class, each method calls the **next** one in the MRO, so all the classes get a turn:

```python
class Base:
    def setup(self):
        return ["Base"]

class Left(Base):
    def setup(self):
        return ["Left"] + super().setup()

class Right(Base):
    def setup(self):
        return ["Right"] + super().setup()

class Child(Left, Right):
    def setup(self):
        return ["Child"] + super().setup()

print(Child().setup())
```

```text
['Child', 'Left', 'Right', 'Base']
```

`Left` called `super().setup()` and got `Right`, not `Base`, because in `Child`'s MRO, `Right` follows `Left`. This is **cooperative multiple inheritance**.

## Mixins: small reusable behaviours

Multiple inheritance is safest in one pattern: **mixins**, tiny classes that add one capability and are not meant to stand alone:

```python
import json

class JsonMixin:
    def to_json(self):
        return json.dumps(self.__dict__, sort_keys=True)

class ReprMixin:
    def __repr__(self):
        fields = ", ".join(f"{k}={v!r}" for k, v in sorted(self.__dict__.items()))
        return f"{type(self).__name__}({fields})"

class User(JsonMixin, ReprMixin):
    def __init__(self, name, age):
        self.name = name
        self.age = age

u = User("Ada", 36)
print(u.to_json())
print(u)
```

```text
{"age": 36, "name": "Ada"}
User(age=36, name='Ada')
```

Each mixin is one idea, they do not overlap, and `User` gets both for free.

## Abstract base classes: contracts

Sometimes a parent class should say **"every child must provide this"** without providing it itself. An **abstract base class** (ABC) does that, and refuses to be instantiated until the gaps are filled:

```python
from abc import ABC, abstractmethod
import math

class Shape(ABC):
    @abstractmethod
    def area(self):
        ...

    @abstractmethod
    def perimeter(self):
        ...

    def describe(self):
        return f"{type(self).__name__}: area {self.area():.1f}, perimeter {self.perimeter():.1f}"

class Circle(Shape):
    def __init__(self, r):
        self.r = r

    def area(self):
        return math.pi * self.r ** 2

    def perimeter(self):
        return 2 * math.pi * self.r

class Rect(Shape):
    def __init__(self, w, h):
        self.w, self.h = w, h

    def area(self):
        return self.w * self.h

    def perimeter(self):
        return 2 * (self.w + self.h)

for shape in [Circle(1), Rect(2, 3)]:
    print(shape.describe())

try:
    Shape()
except TypeError:
    print("cannot instantiate an abstract class")

class Incomplete(Shape):
    def area(self):
        return 0

try:
    Incomplete()
except TypeError:
    print("missing perimeter, so it cannot be created")
```

```text
Circle: area 3.1, perimeter 6.3
Rect: area 6.0, perimeter 10.0
cannot instantiate an abstract class
missing perimeter, so it cannot be created
```

The ABC acts as a **checked contract**: forget to implement a method and Python tells you at creation time, not when something finally calls it. `describe` is a concrete method that uses the abstract ones, which is the **template method** idea: the parent defines the outline, children fill in the steps.

## Duck typing: the other kind of contract

Python does not require a shared parent for polymorphism. If an object has the right methods, it works. "If it walks like a duck and quacks like a duck...":

```python
class Dog:
    def speak(self):
        return "Woof"

class Robot:
    def speak(self):
        return "Beep"

def announce(thing):
    return thing.speak()          # needs only a .speak() method

print([announce(x) for x in (Dog(), Robot())])
```

```text
['Woof', 'Beep']
```

`Dog` and `Robot` share no parent, yet both work. Use an ABC when you want an **enforced** contract or `isinstance` checks. Use duck typing when a simple convention is enough. Lesson 3.5.1 adds a third way, protocols.

## The Liskov rule: do not break the promise

A subclass must be usable **anywhere its parent is**, without surprises. If a child changes what a method means, the parent's callers break:

```python
class Bird:
    def fly(self):
        return "flying"

class Penguin(Bird):
    def fly(self):
        raise NotImplementedError("penguins cannot fly")

def migrate(birds):
    return [b.fly() for b in birds]

try:
    migrate([Bird(), Penguin()])
except NotImplementedError:
    print("Penguin broke code written for Bird")
```

```text
Penguin broke code written for Bird
```

`Penguin` is a `Bird` in biology but not in **behaviour**: it cannot keep the `fly` promise. This is the **Liskov Substitution Principle**, and it is the test for good inheritance: *a child must honour everything the parent promised*. When it cannot, the inheritance model is wrong. Split the hierarchy (a `FlyingBird` and a `Bird`), or use composition.

## Composition: has-a instead of is-a

Instead of inheriting behaviour, **hold an object that has it**. A car does not inherit from an engine. It **has** one:

```python
class Engine:
    def __init__(self, horsepower):
        self.horsepower = horsepower

    def start(self):
        return f"engine {self.horsepower}hp running"

class Wheels:
    def __init__(self, count=4):
        self.count = count

class Car:
    def __init__(self, engine, wheels):
        self.engine = engine           # composition: Car HAS an Engine
        self.wheels = wheels

    def drive(self):
        return self.engine.start() + f" on {self.wheels.count} wheels"

print(Car(Engine(150), Wheels()).drive())
print(Car(Engine(300), Wheels(6)).drive())
```

```text
engine 150hp running on 4 wheels
engine 300hp running on 6 wheels
```

Why this often beats inheritance:

- **Flexibility:** swap the engine without making a new class (`Car(ElectricMotor(), ...)`).
- **Less coupling:** `Car` depends only on the engine's `start()` method, not on a whole parent class.
- **No fragile hierarchy:** changing the parent cannot silently break dozens of children.

A realistic comparison: a report that can be exported in different formats.

```python
# inheritance: a class explosion (PdfReport, CsvReport, PdfEmailReport, ...)
# composition: the report HAS an exporter

class CsvExporter:
    def export(self, rows):
        return "\n".join(",".join(map(str, r)) for r in rows)

class JsonExporter:
    def export(self, rows):
        import json
        return json.dumps(rows)

class Report:
    def __init__(self, rows, exporter):
        self.rows = rows
        self.exporter = exporter

    def render(self):
        return self.exporter.export(self.rows)

rows = [[1, "a"], [2, "b"]]
print(Report(rows, CsvExporter()).render())
print(Report(rows, JsonExporter()).render())
```

```text
1,a
2,b
[[1, "a"], [2, "b"]]
```

New formats are new small classes, and `Report` never changes. This is also the **Strategy** pattern, which lesson 3.2.6 names.

## A rule of thumb

- **Inherit** when the child truly **is a** specialised kind of the parent, and honours its whole contract (Liskov).
- **Compose** when you merely want to **reuse** some behaviour.
- Keep hierarchies **shallow**. Two or three levels is plenty.
- Use **mixins** for small orthogonal features, and **ABCs** for contracts.

## Common mistakes

- **Forgetting `super().__init__()`,** so the parent's attributes are never set.
- **Inheriting just to reuse code,** creating an "is-a" that is not true.
- **Deep hierarchies** that nobody can hold in their head.
- **Overriding a method with a different meaning,** breaking code that trusts the parent.
- **Multiple inheritance without `super()`** in all the classes, so some `__init__`s or methods are skipped.
- **Using `isinstance` chains** (`if isinstance(x, A): ... elif isinstance(x, B)`) instead of letting each class override a method.

```python
from abc import ABC, abstractmethod

class Notifier(ABC):
    @abstractmethod
    def send(self, message):
        ...

class EmailNotifier(Notifier):
    def send(self, message):
        return "email: " + message

class SmsNotifier(Notifier):
    def send(self, message):
        return "sms: " + message

print([n.send("hi") for n in (EmailNotifier(), SmsNotifier())])   # ['email: hi', 'sms: hi']

class Stack:
    def __init__(self):
        self._items = []          # composition: a hidden list

    def push(self, x):
        self._items.append(x)

    def pop(self):
        return self._items.pop()

    def peek(self):
        return self._items[-1]

    def __len__(self):
        return len(self._items)

s = Stack()
s.push(1); s.push(2)
print(s.pop(), len(s), s.peek())   # 2 1 1
```

## Recap

- A subclass reuses and **overrides** its parent. Call `super().__init__(...)` so the parent's setup runs, and `super().method()` to extend rather than replace.
- Python searches methods in the **MRO** (`Class.__mro__`), produced by C3 linearization. `super()` means the **next class in the MRO**, which makes cooperative multiple inheritance work.
- **Mixins** are small single-purpose classes that add a capability.
- **Abstract base classes** (`ABC`, `@abstractmethod`) declare a contract that is checked when you create an object. **Duck typing** needs only the right methods.
- The **Liskov rule**: a subclass must honour everything its parent promised. If it cannot, the hierarchy is wrong.
- **Prefer composition (has-a) over inheritance (is-a)** for reuse. Inherit only for true specialisation, and keep hierarchies shallow.
