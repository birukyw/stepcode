# SWE Design Patterns in Python

Experienced developers do not invent solutions from scratch. They recognise a **recurring problem** and reach for a known shape of answer, a **design pattern**. A pattern is a name for a solution: saying "use a strategy here" tells your teammates the whole idea in two words. This lesson first gives you the five **SOLID** principles that guide good class design, and then a toolbox of the patterns you will meet most. One honest caveat first: in Python many classic patterns shrink to a function, a module or a dictionary, because functions and modules are objects. We will point out where.

## SOLID: five design principles

SOLID is an acronym. You do not need to memorise the names. Each letter is a habit that keeps code easy to change.

### S: Single Responsibility

A class should have **one reason to change**. This one does three jobs:

```python
class ReportBad:
    def __init__(self, data):
        self.data = data

    def calculate(self):
        return sum(self.data) / len(self.data)

    def format(self):
        return f"Average: {self.calculate():.2f}"

    def save(self, path):
        with open(path, "w") as f:
            f.write(self.format())
```

Calculation, formatting and storage change for different reasons (a new statistic, a new layout, a new file format). Splitting them means a change in one cannot break the others:

```python
class Stats:
    @staticmethod
    def average(data):
        return sum(data) / len(data)

class Formatter:
    @staticmethod
    def render(value):
        return f"Average: {value:.2f}"

class Storage:
    def __init__(self):
        self.saved = {}

    def save(self, name, text):
        self.saved[name] = text

storage = Storage()
storage.save("report", Formatter.render(Stats.average([1, 2, 3, 4])))
print(storage.saved)
```

```text
{'report': 'Average: 2.50'}
```

### O: Open/Closed

Code should be **open for extension, closed for modification**: add new behaviour by adding code, not by editing working code. The classic smell is an `if`/`elif` ladder that grows with every new case:

```python
def area_bad(shape):
    if shape["kind"] == "circle":
        return 3.14159 * shape["r"] ** 2
    elif shape["kind"] == "rect":
        return shape["w"] * shape["h"]
    # every new shape means editing THIS function

class Circle:
    def __init__(self, r): self.r = r
    def area(self): return 3.14159 * self.r ** 2

class Rect:
    def __init__(self, w, h): self.w, self.h = w, h
    def area(self): return self.w * self.h

class Triangle:                      # a NEW shape: nothing existing was edited
    def __init__(self, b, h): self.b, self.h = b, h
    def area(self): return self.b * self.h / 2

def total_area(shapes):
    return sum(s.area() for s in shapes)

print(round(total_area([Circle(1), Rect(2, 3), Triangle(4, 5)]), 2))
```

```text
19.14
```

### L: Liskov Substitution

A subclass must work wherever its parent does, honouring the parent's promises. You saw the penguin example in lesson 3.2.4: if a child cannot keep a promise, the inheritance is wrong.

### I: Interface Segregation

Do not force a class to depend on methods it does not use. Prefer several **small** interfaces over one huge one:

```python
from abc import ABC, abstractmethod

class Printer(ABC):
    @abstractmethod
    def print_doc(self, doc): ...

class Scanner(ABC):
    @abstractmethod
    def scan(self): ...

class SimplePrinter(Printer):                 # only needs printing
    def print_doc(self, doc):
        return "printing " + doc

class OfficeMachine(Printer, Scanner):        # does both
    def print_doc(self, doc):
        return "printing " + doc

    def scan(self):
        return "scanned page"

print(SimplePrinter().print_doc("a"), OfficeMachine().scan())
```

```text
printing a scanned page
```

A single fat `Machine` interface with `print`, `scan` and `fax` would force `SimplePrinter` to implement methods that make no sense for it.

### D: Dependency Inversion

High-level code should depend on **abstractions**, not on concrete details. Instead of creating its own helper inside, a class should **receive** it. This is called **dependency injection**:

```python
class SmtpMailer:
    def send(self, to, text):
        return f"SMTP mail to {to}: {text}"

class FakeMailer:                     # a stand-in, perfect for tests
    def __init__(self):
        self.sent = []

    def send(self, to, text):
        self.sent.append((to, text))

class Signup:
    def __init__(self, mailer):       # the dependency is passed IN
        self.mailer = mailer

    def register(self, email):
        return self.mailer.send(email, "welcome!")

print(Signup(SmtpMailer()).register("ada@example.com"))
fake = FakeMailer()
Signup(fake).register("test@example.com")
print(fake.sent)
```

```text
SMTP mail to ada@example.com: welcome!
[('test@example.com', 'welcome!')]
```

`Signup` does not know or care which mailer it has. Real code uses SMTP, tests use the fake, and `Signup` never changes. Lesson 3.5.3 builds on exactly this idea for mocking.

## Pattern 1: Strategy

**Problem:** several interchangeable ways of doing one thing. **Solution:** put each way behind a common call and let the caller pick one. In Python, a function **is** the strategy:

```python
def by_price(item): return item["price"]
def by_name(item): return item["name"]
def by_rating_desc(item): return -item["rating"]

def sort_products(products, strategy):
    return sorted(products, key=strategy)

products = [
    {"name": "pen", "price": 3, "rating": 4},
    {"name": "ink", "price": 9, "rating": 5},
    {"name": "cap", "price": 1, "rating": 2},
]
for strategy in (by_price, by_name, by_rating_desc):
    print(strategy.__name__, [p["name"] for p in sort_products(products, strategy)])
```

```text
by_price ['cap', 'pen', 'ink']
by_name ['cap', 'ink', 'pen']
by_rating_desc ['ink', 'pen', 'cap']
```

This is exactly the `key=` argument of `sorted` (lesson 3.1.2). In languages without first-class functions, Strategy needs a class hierarchy. Here it needs nothing.

## Pattern 2: Factory

**Problem:** code should create objects without hard-coding which class. **Solution:** a function (or class method) that decides:

```python
class JsonParser:
    def parse(self, text): return "json:" + text

class CsvParser:
    def parse(self, text): return "csv:" + text

PARSERS = {"json": JsonParser, "csv": CsvParser}

def make_parser(kind):
    try:
        return PARSERS[kind]()
    except KeyError:
        raise ValueError("unknown format: " + kind) from None

print(make_parser("json").parse("{}"), make_parser("csv").parse("a,b"))
try:
    make_parser("xml")
except ValueError as err:
    print(err)
```

```text
json:{} csv:a,b
unknown format: xml
```

A dictionary from name to class is the whole factory, and a registry that new formats can add themselves to is **Open/Closed** in action:

```python
REGISTRY = {}

def register(name):
    def decorator(cls):
        REGISTRY[name] = cls
        return cls
    return decorator

@register("png")
class PngWriter:
    def write(self): return "writing png"

@register("svg")
class SvgWriter:
    def write(self): return "writing svg"

print(sorted(REGISTRY), REGISTRY["svg"]().write())
```

```text
['png', 'svg'] writing svg
```

That `@register` is a decorator (lesson 3.1.5). Adding a format means writing one decorated class, with no edits elsewhere.

## Pattern 3: Singleton (and why a module is better)

**Problem:** exactly one instance of something (a configuration, a connection pool). The textbook answer is a class that blocks a second instance. In Python, the simplest singleton is **a module-level object**: modules are imported only once.

```python
class Config:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.values = {}
        return cls._instance

a = Config()
b = Config()
a.values["debug"] = True
print(a is b, b.values)
```

```text
True {'debug': True}
```

Use this sparingly. A global instance is hidden shared state that makes testing harder. Passing the object in (dependency injection) is usually better.

## Pattern 4: Observer

**Problem:** when one object changes, others must react, without the subject knowing who is listening. **Solution:** subscribers register callbacks, and the subject calls them:

```python
class EventBus:
    def __init__(self):
        self._handlers = {}

    def subscribe(self, event, handler):
        self._handlers.setdefault(event, []).append(handler)

    def unsubscribe(self, event, handler):
        self._handlers.get(event, []).remove(handler)

    def publish(self, event, *args):
        for handler in list(self._handlers.get(event, [])):
            handler(*args)

log = []
bus = EventBus()
bus.subscribe("order", lambda order_id: log.append(f"email for {order_id}"))
bus.subscribe("order", lambda order_id: log.append(f"stock update for {order_id}"))
bus.publish("order", 42)
bus.publish("refund", 7)
print(log)
```

```text
['email for 42', 'stock update for 42']
```

The code that publishes an order knows nothing about emails or stock. New reactions are new subscribers, which again is Open/Closed. This pattern powers GUIs, game engines and message systems.

## Pattern 5: Adapter

**Problem:** you have a class with the **wrong interface** for what your code expects (often third-party code you cannot edit). **Solution:** wrap it so it looks like what you need:

```python
class LegacyTemperatureSensor:
    def read_fahrenheit(self):
        return 98.6

class CelsiusSensor:
    """The interface the rest of our code expects: .celsius()"""
    def __init__(self, legacy):
        self.legacy = legacy

    def celsius(self):
        return round((self.legacy.read_fahrenheit() - 32) * 5 / 9, 1)

def report(sensor):
    return f"{sensor.celsius()} C"

print(report(CelsiusSensor(LegacyTemperatureSensor())))
```

```text
37.0 C
```

## Pattern 6: Decorator (the object kind)

**Problem:** add behaviour to an object dynamically, without subclass explosion. **Solution:** wrap it in another object with the same interface:

```python
class Coffee:
    def cost(self): return 2.0
    def label(self): return "coffee"

class Milk:
    def __init__(self, drink): self.drink = drink
    def cost(self): return self.drink.cost() + 0.5
    def label(self): return self.drink.label() + " + milk"

class Sugar:
    def __init__(self, drink): self.drink = drink
    def cost(self): return self.drink.cost() + 0.2
    def label(self): return self.drink.label() + " + sugar"

order = Sugar(Milk(Coffee()))
print(order.label(), order.cost())
```

```text
coffee + milk + sugar 2.7
```

Do not confuse this with the `@decorator` syntax of lesson 3.1.5. They share an idea (wrap something to add behaviour), and Python's function decorators are the lightweight version of this pattern.

## Pattern 7: Command

**Problem:** treat an action as an **object**, so it can be queued, logged or undone. **Solution:** wrap each action with how to run it and how to reverse it:

```python
class Editor:
    def __init__(self):
        self.text = ""
        self.history = []

    def run(self, command):
        command.do(self)
        self.history.append(command)

    def undo(self):
        if self.history:
            self.history.pop().undo(self)

class Append:
    def __init__(self, s): self.s = s
    def do(self, editor): editor.text += self.s
    def undo(self, editor): editor.text = editor.text[:-len(self.s)]

ed = Editor()
ed.run(Append("Hello"))
ed.run(Append(", world"))
print(ed.text)
ed.undo()
print(ed.text)
ed.undo()
print(repr(ed.text))
```

```text
Hello, world
Hello
''
```

This is how every "undo" button, task queue and macro recorder works.

## Pattern 8: Template method

**Problem:** several procedures follow the same steps but differ in a few. **Solution:** a parent defines the **skeleton** and children fill in the steps (the abstract base class idea from lesson 3.2.4):

```python
class DataImporter:
    def run(self, source):
        raw = self.read(source)
        rows = self.parse(raw)
        return [self.clean(r) for r in rows]

    def read(self, source): return source
    def parse(self, raw): raise NotImplementedError
    def clean(self, row): return row

class CsvImporter(DataImporter):
    def parse(self, raw):
        return [line.split(",") for line in raw.splitlines()]

    def clean(self, row):
        return [cell.strip() for cell in row]

print(CsvImporter().run("a, b\nc ,d"))
```

```text
[['a', 'b'], ['c', 'd']]
```

## Choosing a pattern, and when not to

| Problem | Pattern | In Python it is often... |
|---|---|---|
| swap an algorithm | Strategy | a function passed in |
| create objects by name | Factory | a dict or `@register` |
| one shared instance | Singleton | a module-level object |
| react to changes | Observer | a list of callbacks |
| fix a mismatched interface | Adapter | a small wrapper class |
| add behaviour dynamically | Decorator | `@decorator` on functions |
| undo, queue, log actions | Command | an object with do/undo |
| shared skeleton, varying steps | Template method | an ABC with hooks |

The most important design skill is knowing when **not** to use a pattern. Patterns add indirection. If a simple function solves the problem, use it. Reach for a pattern when the **problem** it names actually appears, not because it looks professional.

## Common mistakes

- **Patterns for their own sake.** An abstract factory around one class is just noise.
- **Singletons everywhere.** They are global state in disguise and make tests hard.
- **Inheritance where composition fits.** Strategy and Decorator use **has-a**.
- **Class hierarchies for something a function does.** In Python, try a function or a dictionary first.
- **Forgetting that each observer runs inside the publisher's call,** so a slow or failing handler affects the rest.
- **Breaking Liskov.** A subclass that surprises the code using its parent defeats polymorphism.

```python
class FakeGateway:
    def __init__(self):
        self.charges = []

    def charge(self, amount):
        self.charges.append(amount)
        return True

class PaymentProcessor:
    def __init__(self, gateway):
        self.gateway = gateway

    def pay(self, amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
        return self.gateway.charge(amount)

fake = FakeGateway()
PaymentProcessor(fake).pay(25)
print(fake.charges)   # [25]

COMMANDS = {}

def command(name):
    def decorator(func):
        COMMANDS[name] = func
        return func
    return decorator

@command("double")
def double(n):
    return n * 2

def run(name, *args):
    return COMMANDS[name](*args)

print(run("double", 21))   # 42
```

```python
class EventBus:
    def __init__(self):
        self._handlers = {}

    def subscribe(self, event, handler):
        self._handlers.setdefault(event, []).append(handler)

    def unsubscribe(self, event, handler):
        handlers = self._handlers.get(event, [])
        if handler in handlers:
            handlers.remove(handler)

class Coffee:
    def cost(self): return 2.0

class Discount:
    def __init__(self, drink): self.drink = drink

print(Discount(Coffee()).cost())   # 1.8
```

## Recap

- **SOLID:** a class has one reason to change (Single Responsibility), is extended not edited (Open/Closed), subclasses keep the parent's promises (Liskov), interfaces stay small (Interface Segregation), and code depends on abstractions that are **injected** (Dependency Inversion).
- A **design pattern** is a named solution to a recurring problem. Python's functions, dictionaries and modules often replace the heavy class-based versions.
- **Strategy** (pass a function), **Factory** (dict or `@register`), **Singleton** (a module-level object, used sparingly), **Observer** (callbacks), **Adapter** (wrap a wrong interface), **Decorator** (wrap an object), **Command** (an action as an object, giving undo and queues), **Template method** (a skeleton with hooks).
- Prefer **composition and injection** over inheritance, and use a pattern only when its problem is really present.
