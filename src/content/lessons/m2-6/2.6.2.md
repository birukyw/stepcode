# Greedy Algorithms & Interval Scheduling

Backtracking tries everything. A **greedy** algorithm refuses to look back: at every step it takes the **best-looking choice right now** and never reconsiders. When that works, the result is wonderfully fast and short. The hard part, and the real skill of this lesson, is knowing **when** the greedy choice is actually safe.

## A greedy choice that works: making change

Pay 63 cents using the fewest coins from 25, 10, 5, 1. Take the biggest coin that fits, repeatedly:

```python
def make_change(amount, coins):
    result = []
    for coin in sorted(coins, reverse=True):
        while amount >= coin:
            amount -= coin
            result.append(coin)
    return result

print(make_change(63, [25, 10, 5, 1]))
```

```text
[25, 25, 10, 1, 1, 1]
```

Fast and correct for US coins. But greedy is a **bet**, and it can lose:

```python
def greedy_coins(amount, coins):
    count = 0
    for coin in sorted(coins, reverse=True):
        count += amount // coin
        amount %= coin
    return count

def best_coins(amount, coins):
    best = [0] + [float("inf")] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                best[a] = min(best[a], best[a - c] + 1)
    return best[amount]

print(greedy_coins(6, [4, 3, 1]), best_coins(6, [4, 3, 1]))
```

```text
3 2
```

With coins 4, 3, 1, greedy pays 6 as 4 + 1 + 1 (three coins), but 3 + 3 is two. The best choice *now* was not part of the best answer. So we never trust greedy on instinct: we trust it when we can **argue** why it is safe.

## What makes greedy safe

Two properties, in plain words:

- **Greedy-choice property:** some optimal solution contains the greedy first choice. (You can always swap the optimal solution's choice for the greedy one without making it worse.)
- **Optimal substructure:** after making that choice, what remains is the same kind of problem, smaller.

The usual proof is an **exchange argument**: take any optimal solution that does not use the greedy choice, swap one piece for the greedy choice, and show the result is no worse.

## Interval scheduling: the classic

You have meeting requests, each with a start and end. Pick the **most meetings** that do not overlap.

Which greedy rule? Earliest start? Shortest meeting? Fewest conflicts? Counterexamples kill all of those. The one that works: **always take the meeting that ends earliest** (among those that fit), because it leaves the most room for the rest.

```python
def max_meetings(intervals):
    chosen = []
    last_end = float("-inf")
    for start, end in sorted(intervals, key=lambda iv: iv[1]):    # by end time
        if start >= last_end:
            chosen.append((start, end))
            last_end = end
    return chosen

meetings = [(1, 4), (3, 5), (0, 6), (5, 7), (3, 9), (5, 9), (6, 10), (8, 11), (8, 12), (2, 14), (12, 16)]
picked = max_meetings(meetings)
print(len(picked), picked)
```

```text
4 [(1, 4), (5, 7), (8, 11), (12, 16)]
```

**Why it is safe (exchange argument).** Let `g` be the interval that ends earliest. Take any optimal schedule and look at its first meeting `f`. Since `g` ends no later than `f`, swapping `f` for `g` cannot create an overlap with the rest, and the schedule keeps the same size. So an optimal schedule that starts with `g` exists, and we repeat the argument on what remains. The cost is the sort: **O(n log n)**.

## Merging overlapping intervals

Sort by start, then sweep. Each interval either extends the current block or starts a new one:

```python
def merge_intervals(intervals):
    merged = []
    for start, end in sorted(intervals):
        if merged and start <= merged[-1][1]:
            merged[-1][1] = max(merged[-1][1], end)
        else:
            merged.append([start, end])
    return merged

print(merge_intervals([(1, 3), (2, 6), (8, 10), (15, 18), (17, 20)]))
print(merge_intervals([(1, 4), (4, 5)]))
```

```text
[[1, 6], [8, 10], [15, 20]]
[[1, 5]]
```

## How many rooms? The sweep line

If meetings may overlap, how many rooms do we need? Treat each start as +1 and each end as -1, walk through time in order, and track the maximum running total:

```python
def min_rooms(intervals):
    events = []
    for start, end in intervals:
        events.append((start, 1))
        events.append((end, -1))
    events.sort(key=lambda e: (e[0], e[1]))       # at equal times, endings (-1) come first
    rooms = best = 0
    for _, delta in events:
        rooms += delta
        best = max(best, rooms)
    return best

print(min_rooms([(0, 30), (5, 10), (15, 20)]))
print(min_rooms([(7, 10), (2, 4)]))
print(min_rooms([(1, 5), (5, 8)]))
```

```text
2
1
1
```

A heap gives the same answer by tracking the end time of each room in use (lesson 2.4.4).

## Greedy with a heap: task scheduling

Sometimes the best choice "right now" changes as time passes, so a heap keeps the best candidate on top. **Jobs with deadlines and profits**: each job takes one time slot, so choose jobs to maximize profit while meeting deadlines.

```python
import heapq

def max_profit(jobs):
    # jobs: (deadline, profit). Handle by deadline, keep the best profits in a min-heap.
    heap = []
    for deadline, profit in sorted(jobs):
        heapq.heappush(heap, profit)
        if len(heap) > deadline:
            heapq.heappop(heap)             # too many jobs for the slots: drop the least profitable
    return sum(heap)

print(max_profit([(2, 100), (1, 19), (2, 27), (1, 25), (3, 15)]))
```

```text
142
```

## Jump Game: greedy reachability

From each index you can jump up to `nums[i]` steps. Can you reach the end? Track the **farthest** index reachable so far:

```python
def can_jump(nums):
    farthest = 0
    for i, jump in enumerate(nums):
        if i > farthest:
            return False
        farthest = max(farthest, i + jump)
    return True

print(can_jump([2, 3, 1, 1, 4]), can_jump([3, 2, 1, 0, 4]))
```

```text
True False
```

One pass, O(n). The greedy insight: you do not need to know *how* to reach a position, only *whether* you can, and the farthest reachable index summarizes everything.

## Huffman coding: greedy compression

Give frequent letters short bit codes and rare letters long ones. Repeatedly merge the **two least frequent** items into one: the heap makes the greedy choice cheap.

```python
import heapq

def huffman_lengths(freq):
    heap = [(count, i, [ch]) for i, (ch, count) in enumerate(freq.items())]
    heapq.heapify(heap)
    depth = {ch: 0 for ch in freq}
    uid = len(heap)
    while len(heap) > 1:
        c1, _, g1 = heapq.heappop(heap)
        c2, _, g2 = heapq.heappop(heap)
        for ch in g1 + g2:
            depth[ch] += 1
        heapq.heappush(heap, (c1 + c2, uid, g1 + g2))
        uid += 1
    return depth

freq = {"a": 45, "b": 13, "c": 12, "d": 16, "e": 9, "f": 5}
lengths = huffman_lengths(freq)
print(lengths)
print(sum(freq[ch] * lengths[ch] for ch in freq))
```

```text
{'a': 1, 'b': 3, 'c': 3, 'd': 3, 'e': 4, 'f': 4}
224
```

The frequent `a` gets a 1-bit code and the rare `e` and `f` get 4 bits. The total, 224 bits for 100 letters, beats the 300 a fixed 3-bit code would use.

## Greedy or DP? A checklist

Try to **prove** the greedy rule (exchange argument) or find a counterexample on a tiny input. If a tiny case breaks it (like coins 4, 3, 1), you need **dynamic programming**, which considers all choices without redoing work. Test your rule against a brute force on small random inputs before trusting it.

## Common mistakes

- **Trusting a greedy rule without a proof or test.** Plausible is not correct.
- **Sorting by the wrong key.** Interval scheduling sorts by **end**, merging sorts by **start**.
- **Off-by-one on touching intervals.** `[1, 4]` and `[4, 5]`: do they overlap? Decide, and handle it in both the comparison and the tie order of events.
- **Forgetting to sort.** Most greedy algorithms are "sort, then sweep".
- **Using greedy where choices interact,** such as coin change with odd coins or knapsack.

            limit = end

def non_overlapping_removals(intervals):
    kept, last_end = 0, float("-inf")
    for start, end in sorted(intervals, key=lambda iv: iv[1]):
        if start >= last_end:
            kept += 1
            last_end = end
    return len(intervals) - kept

def can_attend_all(meetings):
    meetings = sorted(meetings)
    return all(a[1] <= b[0] for a, b in zip(meetings, meetings[1:]))

def min_jumps(nums):

    for i in range(len(nums) - 1):
        farthest = max(farthest, i + nums[i])
        if i == end:
            jumps += 1
            end = farthest
    return jumps

## Recap

- A **greedy** algorithm commits to the best-looking choice at each step and never undoes it. It is usually "sort, then sweep" and runs in O(n log n).
- It is only correct when the greedy choice is **safe**: prove it with an **exchange argument**, or find a counterexample on a tiny input.
- **Interval scheduling:** sort by **end** time and take every interval that fits. **Merging:** sort by start. **Rooms:** sweep line over +1 and -1 events.
- A heap lets greedy re-pick the best candidate as the situation changes (job deadlines, Huffman coding).
- When a small counterexample breaks the rule (coins 4, 3, 1), use dynamic programming instead.
