# Asymptotic Analysis & Big-O Intuition

Two programs can give the same answer and still differ by a factor of a million in how long they take. Computer scientists have a precise way to talk about that difference, and it is the vocabulary of everything in Track 2. You will not need heavy maths. You need one habit: **count the steps, then ask what happens when the input gets bigger.**

## Why not just time it?

You could run a function and read a stopwatch. The trouble is that the answer depends on your laptop, what else is running, and the size of the test input you happened to pick. A faster machine makes a slow algorithm look fine, until the data grows.

So instead of seconds, we count **operations**: comparisons, additions, loop iterations. Operations do not change when you change computers.

```python
def sum_to(n):
    total = 0
    steps = 0
    for i in range(1, n + 1):
        total += i
        steps += 1
    return total, steps

print(sum_to(10))
print(sum_to(100))
print(sum_to(1000))
```

```text
(55, 10)
(5050, 100)
(500500, 1000)
```

Ten times more input means ten times more steps. That relationship is what we care about.

## Growth rates

**Big-O notation** describes how the number of steps grows as the input size `n` grows. It ignores exact counts and keeps the shape of the curve. These are the shapes you will meet most.

### O(1): constant

The cost does not depend on `n` at all. Gauss's formula replaces the whole loop:

```python
def sum_formula(n):
    return n * (n + 1) // 2

print(sum_formula(10))
print(sum_formula(1_000_000))
```

```text
55
500000500000
```

A million-item answer in the same three operations as a ten-item one.

### O(n): linear

The cost grows in step with `n`. `sum_to` above is linear. Looking for a value in an unsorted list is linear too, because in the worst case you check every item.

### O(n²): quadratic

A loop inside a loop. Counting every pair of items:

```python
def count_pairs(n):
    steps = 0
    for i in range(n):
        for j in range(i + 1, n):
            steps += 1
    return steps

print(count_pairs(10))
print(count_pairs(100))
print(count_pairs(1000))
```

```text
45
4950
499500
```

Ten times more input means roughly **a hundred** times more steps. At 100,000 items you would be near five billion steps.

### O(log n): logarithmic

The cost grows very slowly, because each step throws away half of what is left. This is what binary search does, as you will see in module 2.3.

```python
def halvings(n):
    steps = 0
    while n > 1:
        n //= 2
        steps += 1
    return steps

print(halvings(1000))
print(halvings(1_000_000))
print(halvings(1_000_000_000))
```

```text
9
19
29
```

A billion items, and only 29 halvings. That is why logarithmic algorithms feel like magic.

### O(2ⁿ): exponential

The cost doubles every time `n` grows by one. The classic example is the naive recursive Fibonacci:

```python
def fib_calls(n):
    if n < 2:
        return 1
    return 1 + fib_calls(n - 1) + fib_calls(n - 2)

for n in (10, 20, 25):
    print(n, fib_calls(n))
```

```text
10 177
20 21891
25 242785
```

Adding 5 to `n` multiplied the work by more than eleven. At `n = 60` the computer would run for centuries.

## Comparing them side by side

| n | log n | n | n² | 2ⁿ |
|---|---|---|---|---|
| 10 | 3 | 10 | 100 | 1,024 |
| 100 | 7 | 100 | 10,000 | about 10³⁰ |
| 1,000 | 10 | 1,000 | 1,000,000 | astronomically large |

The rule of thumb: **O(log n) and O(n) scale to anything. O(n²) is fine for thousands and painful for millions. O(2ⁿ) only works for tiny inputs.**

## Dropping constants and small terms

Big-O keeps only the part that dominates when `n` is huge.

- `3n + 7` is **O(n)**. The `3` and the `7` do not change the shape.
- `n² + 5n + 20` is **O(n²)**. At large `n` the `n²` term swamps the rest.
- Two loops one after the other, each O(n), cost O(n) in total, not O(n²). Only **nested** loops multiply.

```python
def two_passes(items):
    steps = 0
    for x in items:       # n steps
        steps += 1
    for x in items:       # another n steps
        steps += 1
    return steps

print(two_passes(range(500)))
```

```text
1000
```

That is `2n`, still linear.

## Best, worst and average case

Searching a list for a value takes 1 step if it is first and `n` steps if it is last or missing. Big-O usually describes the **worst case**, because that is the guarantee: it will never be slower than this.

## Space complexity

Memory is a resource too. An algorithm that builds a copy of its input uses O(n) extra space. One that only keeps a few counters uses O(1). Trading space for time is one of the most common bargains in programming.

## Hidden costs

Operations that look cheap can hide a loop. Checking `x in some_list` scans the list, so it is O(n). Put that inside a loop over the list and you have accidentally written O(n²).

```python
def unique_slow(items):
    seen = []
    comparisons = 0
    for x in items:
        found = False
        for y in seen:
            comparisons += 1
            if y == x:
                found = True
                break
        if not found:
            seen.append(x)
    return len(seen), comparisons

def unique_fast(items):
    seen = set()
    lookups = 0
    for x in items:
        lookups += 1
        seen.add(x)
    return len(seen), lookups

data = list(range(1000))
print(unique_slow(data))
print(unique_fast(data))
```

```text
(1000, 499500)
(1000, 1000)
```

Same answer, 499,500 comparisons versus 1,000. A set lookup is O(1), so the fast version is linear. This single change, **swapping a list for a set or dictionary**, is the most valuable optimisation you will ever make.

## Common mistakes

- **Counting seconds instead of steps.** Measure growth, not one run.
- **Treating nested and sequential loops alike.** Nested multiply, sequential add.
- **Forgetting hidden loops** in `in`, `.index()`, `.count()`, `.insert(0, x)`, slicing and `sum()`.
- **Over-optimising.** If `n` is always 20, O(n²) is fine. Complexity matters when `n` can grow.

+++ Solutions
The inner loop always runs 10 times, a constant, so the whole thing is `10n`, which is **O(n)**.

```python
def count_triples(n):
    steps = 0
    for i in range(n):
        for j in range(n):
            for k in range(n):
                steps += 1
    return steps

print(count_triples(10), count_triples(20))   # 1000 8000
```

Doubling n multiplies the work by 8, which is O(n³).

Both are **O(n)**: you must look at every item once.

```python
big_list = list(range(100_000))
lookup = set(big_list)          # O(n) once
print(99_999 in lookup)         # O(1) each time
```

## Recap

- Count operations, not seconds, and ask how the count grows with `n`.
- Common shapes, fastest to slowest: O(1), O(log n), O(n), O(n²), O(2ⁿ).
- Drop constants and smaller terms. Sequential loops add, nested loops multiply.
- Big-O usually describes the worst case. Space matters as well as time.
- Watch for hidden linear work inside `in`, `.index()`, `.insert(0, x)` and slicing. A set or dictionary lookup is O(1).
